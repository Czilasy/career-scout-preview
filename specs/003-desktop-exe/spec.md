# 功能规格：Windows 桌面版（EXE 发行形态）

**功能目录**：`003-desktop-exe`

**创建日期**：2026-08-06

**状态**：Spec 冻结；按 speckit 流程推进（Research → Plan → Tasks 后交付实现）

**输入**：为 Career Scout 增加 Windows 桌面发行形态：用户从 GitHub Release 下载单个 EXE 文件，双击启动后看到与现有 Web 工作台完全一致的界面；无需安装 Python、Node 或任何依赖。抓取任务在 EXE 内直接执行，数据与源码版共用同一本地数据目录。打包配置（壳源码、构建脚本、清单）公开入库，任何人可自行构建验证，不改变项目的开源性质。

## 用户场景与测试

### 用户故事 1 - 下载即用（优先级：P1）

一个不懂编程的用户从 GitHub Release 下载 `CareerScout.exe`，双击启动，无需安装 Python、Node、npm 或任何依赖，直接进入与现有 Web 工作台完全一致的界面，开始使用全部既有功能。

**优先原因**：这是本功能的立身之本——把"需要装环境、跑命令"的开发者工具变成"双击即用"的普通软件；界面一致性决定用户迁移成本为零。

**独立测试**：在未安装 Python 和 Node.js 的 Windows 10/11 机器上双击 EXE，验证窗口出现、工作台可交互、环境检查面板中"Python 依赖"项显示为内置状态而不是失败。

**验收场景**：

1. **假如** 用户双击 EXE，**当** 应用启动完成，**那么** 出现桌面窗口且加载的是现有工作台界面，排版、配色、交互与浏览器版一致。
2. **假如** 机器未安装 Python 或 Node.js，**当** 应用启动并执行环境检查，**那么** 运行时组件显示为"已内置"，不出现环境缺失类失败。
3. **假如** 用户未安装 Python，**当** 用户发起抓取任务，**那么** 任务正常执行，不依赖外部 Python 解释器。
4. **假如** 机器上已存在源码版运行产生的数据，**当** 用户用 EXE 版启动，**那么** 既有数据、任务历史与设置全部可见且不被破坏。

### 用户故事 2 - 环境就绪检查与引导（优先级：P1）

用户在首次使用或遇到问题时，点击工作台顶部的"环境检查"按钮，面板逐项显示 Chrome/Edge 浏览器、专用浏览器启动状态、登录状态、AI Key、WebView2 运行时、数据目录等是否就绪，并可直接发起修复动作（启动专用浏览器、登录指引、打开 AI 设置）。

**优先原因**：EXE 版不捆绑浏览器，用户的真实门槛是"本机有浏览器并已登录"；环境检查面板是把门槛变成引导的关键入口，必须与源码版保持同一交互体验。

**独立测试**：在 EXE 内打开环境检查面板，验证三组检查项齐全、逐项点亮动画正常、重新检查可用、修复按钮行为正确；重点验证"Python 依赖"项语义和新增的 WebView2 项。

**验收场景**：

1. **假如** 用户在 EXE 内点击环境检查，**当** 面板打开并检查完成，**那么** 浏览器组（Chromium 浏览器/专用浏览器已启动/BOSS 登录状态）、AI 组、本地组（数据目录/前端构建产物/Python 依赖）均与源码版相同的检查项结构展示。
2. **假如** 用户在 EXE 内查看本地组，**当** 检查完成，**那么** "Python 依赖"项显示为内置通过状态（文案如"内置运行时"），不再要求外部 Python。
3. **假如** 机器缺少 WebView2 运行时，**当** 应用检测窗口宿主不可用，**那么** 环境检查中给出明确提示与安装指引。
4. **假如** Chromium 浏览器（Chrome 或 Edge）均未安装，**当** 用户查看浏览器组，**那么** 该项显示失败并给出可执行的引导。
5. **假如** 用户点击失败项的修复按钮，**当** 修复动作发起，**那么** 行为与源码版一致（启动专用浏览器/登录指引/打开 AI 设置）。

### 用户故事 3 - 桌面窗口体验（优先级：P2）

桌面窗口支持拖拽缩放，界面在任意窗口尺寸下自适应重排；窗口有合理的最小尺寸避免布局崩坏；关闭后再次启动恢复上次窗口大小与位置；重复启动时不会双开，而是聚焦已有实例。

**优先原因**：桌面形态与浏览器页面的关键差异就是窗口交互；窗口缩放体验直接决定"这是不是一个正经软件"的观感。

**独立测试**：在 EXE 内将窗口从默认尺寸拖拽缩放到最小尺寸、最大尺寸，并分别验证各断点布局；关闭窗口后重启验证尺寸记忆；启动第二个实例验证单实例行为。

**验收场景**：

1. **假如** 用户拖拽窗口边缘缩放，**当** 窗口尺寸跨过现有 CSS 断点（1050px/760px/640px），**那么** 布局按断点切换，无横向溢出、无重叠、无不可达操作。
2. **假如** 用户将窗口缩小，**当** 尺寸到达最小限制，**那么** 窗口停止缩小，界面保持在可用的桌面布局，不进入手机级布局。
3. **假如** 用户调整窗口大小与位置后关闭应用，**当** 再次启动，**那么** 窗口恢复上次的大小与位置。
4. **假如** 用户重复启动第二个实例，**当** 第二个 EXE 启动，**那么** 不出现第二个窗口和数据写入冲突，已有实例被聚焦到前台。
5. **假如** 用户在最小窗口（1024×700）中使用工作台，**当** 执行任务、查看提醒、打开抽屉等操作，**那么** 所有功能可用，无横向溢出或不可达操作。

### 用户故事 4 - 任务照常执行（优先级：P1）

EXE 内发起抓取任务、工作台搜索运行、AI 筛选等全部既有功能照常工作：进度与日志流式展示、可取消、可重试、断点续跑语义不变、结果落库。

**优先原因**：界面再一致，如果任务执行链路在 EXE 内不可用，产品就是空壳；这是本功能最大的技术风险点，必须作为一等公民验收。

**独立测试**：在 EXE 内分别发起 BOSS 与智联搜索任务，观察任务状态机（排队→运行→成功/失败/取消）、日志流、取消响应；在任务运行中关闭窗口再启动，验证中断与恢复语义；重启后验证任务历史与数据完整。

**验收场景**：

1. **假如** 用户在 EXE 内提交抓取任务，**当** 任务运行，**那么** 状态推进、日志流式展示、产物校验与源码版行为一致，最终结果可查看、可导出。
2. **假如** 任务运行中用户点击取消，**当** 取消生效，**那么** 任务进入取消状态，已写数据保留，可重新发起。
3. **假如** 任务运行中用户关闭窗口，**当** 应用退出，**那么** 进程树全部终止；重新启动后任务状态按既有恢复机制（断点续跑/恢复校验）处理，不损坏数据。
4. **假如** 抓取过程中遇到登录失效、限流或验证码，**当** 失败判定产生，**那么** 分类与既有实现一致（系统性阻断码），界面提示一致。

### 用户故事 5 - 源码模式零回归（优先级：P1）

打包配置与桌面壳入库后，源码开发模式（`python webui/app.py`、CLI 脚本、既有测试）行为完全不变；EXE 只是新增的一条执行路径，不替代、不改造现有路径。

**优先原因**：这是公开开源仓库的底线——EXE 化不能以牺牲开发者体验或引入回归为代价。

**独立测试**：实现完成后运行既有 Python 全量测试、前端全量测试、类型检查、构建与卫生测试，全部通过；再以源码模式手动启动工作台完成一次主链操作。

**验收场景**：

1. **假如** 打包相关代码入库后，**当** 以 `python webui/app.py` 启动，**那么** 行为与入库前一致，子进程执行链路不变。
2. **假如** 打包相关代码入库后，**当** 运行既有 CLI（如 `--check`、`--smoke-test`），**那么** 行为不变。
3. **假如** 实现完成，**当** 运行全量测试（Python unittest、前端 Vitest、类型检查、构建、卫生测试），**那么** 与基线相比零新增失败。

### 用户故事 6 - 构建可复现（优先级：P2）

打包配置（壳源码、PyInstaller 清单、构建脚本、构建文档）全部入库；任何人 clone 仓库后按文档步骤即可在本机构建出可用的 EXE，构建产物不进入 git。

**优先原因**：roadmap 方向三明确"EXE 只是构建产物，壳源码与打包脚本全部入库，任何人可自行构建验证，不改变开源性质"；可复现构建是开源信任的基础，也是后续自动化发布的前提。

**独立测试**：在干净克隆（或 CI 模拟环境）中按构建文档执行构建脚本，产出 EXE；随后检查 git status 确认无任何构建产物进入版本控制。

**验收场景**：

1. **假如** 用户 clone 仓库并按文档执行构建脚本，**当** 构建成功，**那么** 产出单个可启动的 EXE。
2. **假如** 构建完成，**当** 检查工作区 git 状态，**那么** 构建产物（EXE、中间目录）全部被 .gitignore 忽略，`git status` 干净。
3. **假如** 开发者查看仓库，**当** 浏览 packaging 相关目录，**那么** 能看到壳源码、构建脚本、清单与构建文档，文件组织清晰可循。

### 边界情况

- **端口冲突**：EXE 内后端不得固定占用 5000 端口；必须选择随机空闲端口，且对"端口选择失败"有明确失败反馈（不得无提示卡死）。
- **窗口关闭时任务运行中**：关闭窗口必须终止整个进程树（包括运行中的抓取线程），不得残留孤儿进程；中断后的恢复语义沿用既有"断点续跑/历史恢复"机制。
- **双开**：第二个实例不得写入数据（SQLite 并发写风险），必须通过单实例机制拦截并聚焦已有实例。
- **WebView2 缺失**：Windows 10/11 通常预装；缺失时启动必须给出可理解的错误提示（不是空白窗口或崩溃），环境检查中提供安装指引。
- **onefile 启动延迟**：单文件模式首启需要解压（数秒），此延迟可接受，但启动过程不得无反馈（窗口应在后端就绪前给出加载状态，或延迟出现后快速就绪）。
- **防病毒误报**：PyInstaller 产物可能被部分杀软误报，属于外部因素；文档中说明，功能上不处理。
- **数据目录不可写**：沿用现有环境检查"数据目录可写"项的检测与提示。
- **版本标识**：窗口标题或界面中必须能识别 EXE 版本号，便于用户反馈问题时对齐版本。
- **前端构建产物缺失**：打包必须包含前端 dist；若打包时前端未构建，构建脚本必须失败并给出明确提示（不得打出无界面的 EXE）。

## 需求

### 功能需求

- **FR-001**：系统必须以单个可执行的 Windows 桌面应用形式发布，用户无需安装 Python、Node.js 或任何运行时依赖即可启动并使用全部既有功能。
- **FR-002**：桌面应用内的界面必须与现有 Web 工作台为同一前端实现，排版、配色、交互与浏览器版一致；不允许维护第二套界面。
- **FR-003**：桌面应用的内置后端必须监听本地回环地址，并选择随机空闲端口启动；不得固定占用 5000 或任何特定端口。
- **FR-004**：桌面应用必须限制为单实例；重复启动时不得创建第二个窗口，必须聚焦已有实例，并避免并发数据写入。
- **FR-005**：桌面窗口必须支持拖拽缩放，界面在任意窗口尺寸下按现有响应式断点正常重排；窗口必须设置合理的最小尺寸，避免布局进入不可用状态。
- **FR-006**：桌面应用必须记忆窗口大小与位置，再次启动时恢复；恢复失败（如显示器变更）时必须回退到安全的默认尺寸。
- **FR-007**：关闭桌面窗口必须终止整个应用进程（含运行中的抓取执行），不得残留后台进程或孤儿进程。
- **FR-008**：环境检查功能在 EXE 模式下必须保持与源码版一致的检查项结构与交互；"Python 依赖"检查项必须按内置运行时语义显示为通过。
- **FR-009**：环境检查必须新增"WebView2 运行时"检查项（仅 EXE 模式显示），并在缺失时给出安装指引。
- **FR-010**：EXE 模式下抓取任务必须在应用进程内直接执行，不得依赖外部 Python 解释器或子进程 Python；任务状态机、日志流、取消、重试、断点续跑与产物校验语义必须与源码版一致。
- **FR-011**：源码模式（`python webui/app.py`、CLI 脚本）必须保留现有子进程执行链路，行为零回归；in-process 执行只能是 EXE 模式新增路径。
- **FR-012**：EXE 版与源码版必须共用同一数据目录（`~/.career-scout`），数据库、任务历史、设置、账号配置互通，不复制、不迁移、不破坏既有数据。
- **FR-013**：EXE 版必须携带可识别的版本标识（窗口标题或界面展示），与源码版本号一致。
- **FR-014**：打包配置必须入库：桌面壳源码、PyInstaller 清单、构建脚本、构建文档，任何人可按文档自行构建 EXE。
- **FR-015**：构建产物（EXE、中间目录、临时文件）必须全部被 .gitignore 忽略，构建过程不得向版本控制引入任何产物文件。
- **FR-016**：构建脚本必须在依赖缺失、前端未构建或打包失败时给出明确失败信息与退出码，不得产出残缺产物。
- **FR-017**：桌面应用启动失败（端口选择失败、WebView2 缺失、后端就绪超时等）时必须给出可理解的错误提示，不得无反馈卡死或静默退出。

### 关键实体

- **桌面应用**：以单个 EXE 文件分发的 Windows 应用形态，包含后端服务、前端资源、Python 运行时与任务执行能力。
- **桌面壳**：桌面应用的窗口宿主，负责窗口生命周期、单实例、窗口状态记忆，并将窗口指向内置后端地址。
- **内置运行时**：EXE 内嵌的 Python 运行时与依赖，替代源码模式下的外部解释器与虚拟环境。
- **in-process 执行器**：EXE 模式下在应用进程内执行抓取任务的执行路径，与源码模式的子进程执行器行为等价。
- **WebView2 运行时**：桌面窗口渲染网页内容所需的系统组件，Windows 10/11 通常预装。

## 成功标准

### 可衡量结果

- **SC-001**：在未安装 Python 与 Node.js 的 Windows 10/11 机器上，双击 EXE 后 10 秒内出现可交互的工作台窗口，无任何环境安装提示。
- **SC-002**：EXE 内界面与浏览器版为同一前端产物（同一 dist），逐页对比无差异。
- **SC-003**：EXE 内环境检查面板三组检查项齐全；"Python 依赖"显示内置通过；WebView2 检查项存在；Chrome/Edge 检测、登录状态、AI Key 检查行为与源码版一致。
- **SC-004**：EXE 内完成一次 BOSS 与一次智联抓取任务全流程（提交→运行→完成），日志流式、结果可查看导出；取消、重试、断点续跑语义与源码版一致。
- **SC-005**：关闭窗口后无残留进程；任务运行中关闭窗口再启动，数据与任务历史完好，恢复机制正常。
- **SC-006**：重复启动第二个实例 100% 被拦截并聚焦已有实例，无并发写入。
- **SC-007**：窗口缩放覆盖 1024×700 到 2560×1440 区间，无横向溢出、重叠或不可达操作；重启后窗口大小与位置恢复正确率 100%。
- **SC-008**：实现后既有 Python 全量测试、前端全量测试、类型检查、构建与卫生测试零新增失败；源码模式手动启动主链操作正常。
- **SC-009**：按 packaging 文档在干净克隆环境执行构建脚本，产出可启动 EXE；构建后 `git status` 无任何未忽略产物。
- **SC-010**：EXE 启动失败场景（端口冲突、WebView2 缺失、前端资源缺失）均有明确错误提示，无静默失败。

## 假设与依赖

- 目标平台为 Windows 10/11（WebView2 预装或可从系统更新获得）；本版本不发布 macOS/Linux 构建。
- 用户本机需安装 Chrome 或 Edge 浏览器并完成 BOSS/智联登录；EXE 不捆绑浏览器（roadmap 已定，等待真实用户反馈再评估）。
- 数据目录继续使用 `~/.career-scout`，与源码版完全互通；不引入新的数据存储。
- 现有前端为响应式设计（1050/760/640/430px 断点），桌面窗口缩放依赖现有断点体系，不做第二套布局。
- 桌面壳依赖系统 WebView2 渲染；渲染内核与 Chrome 同源（Chromium），不存在浏览器兼容性差异。
- 打包为单文件（onefile）形态，接受首启解压延迟；构建配置公开入库，任何人可复现构建。
- GitHub Actions 自动构建发布为后续事项（记入 roadmap 待办），本规格只要求本地构建可复现。

## 范围外

- 捆绑 Chromium 或其他浏览器（等待真实用户反馈再定，roadmap 决策）。
- 自动更新机制、崩溃上报、遥测。
- macOS / Linux 桌面版。
- GitHub Actions 自动构建发布流水线（roadmap 后续待办）。
- PyPI 发布与安装器（如 Inno Setup 向导）。
- 指纹伪装、风控对抗、绕过平台反爬。
- 多实例协作、多用户共享、服务端部署。
