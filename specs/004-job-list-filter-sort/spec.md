# 功能规格：岗位列表筛选与排序

**功能目录**：`004-job-list-filter-sort`

**创建日期**：2026-08-07

**状态**：Spec 冻结；按 speckit 流程推进（Research → Plan → Tasks 后交付实现）

**输入**：在结果页左侧岗位列表顶部新增「筛选」「排序」两个入口。筛选以浮层面板多选条件（薪资、经验、学历、福利）收窄当前列表显示范围；排序以浮层菜单调整当前列表排列顺序。筛选与排序均为悬浮弹窗，不占用页面空间，保持现有深色 UI 风格。BOSS 列表页已有的福利数据（welfareList）此前未被归一化与持久化，本次顺带补齐为 `extra.welfare_list`，使福利筛选可用。

## 用户场景与测试

### 用户故事 1 - 筛选岗位（优先级：P1）

用户在结果页看到岗位列表后，点击列表顶部右侧的「筛选」按钮（小图标，带已选数量徽标），浮层面板展开，按组多选条件，点「确定」生效，点「重置」清空；筛选收窄当前分类下的列表显示范围，不影响顶部分类计数。

**优先原因**：这是本功能的主体——需求全文围绕筛选交互展开；筛选是否好找、好懂决定功能成败。

**独立测试**：构造混合岗位数据（不同薪资/经验/学历/平台），验证面板开合、多选、徽标计数、确定/重置、筛选生效与清空、空态兜底。

**验收场景**：

1. **假如** 结果页存在岗位列表，**当** 用户点击「筛选」按钮，**那么** 浮层面板在按钮附近展开，不推挤或遮挡现有列表布局，深色风格与现有 UI 一致。
2. **假如** 用户勾选薪资「10-15K」与学历「本科」，**当** 点击「确定」，**那么** 面板关闭，列表只显示同时满足两个条件的岗位，顶部「匹配 32」等分类计数不变。
3. **假如** 用户已选择若干条件，**当** 查看「筛选」按钮，**那么** 按钮显示已选数量徽标（如「筛选 3」）；计数规则为各组非「不限」选中项之和。
4. **假如** 用户点击「重置」，**当** 面板关闭，**那么** 所有条件回到默认（全部为「不限」），列表恢复全量显示，徽标消失。
5. **假如** 筛选后当前列表为空，**当** 用户查看列表区，**那么** 显示「没有符合条件的岗位」与「清除筛选」按钮，点击后恢复全量列表。
6. **假如** 用户未选择任何条件点击「确定」，**当** 面板关闭，**那么** 列表不发生变化。

---

### 用户故事 2 - 排序岗位（优先级：P1）

用户点击「排序」按钮，浮层菜单列出排序方式，点击一项立即生效；「综合排序」「薪资最高」「薪资最低」可用，「最新发布」「匹配度最高」置灰不可选（数据暂缺）。

**优先原因**：排序与筛选并列为本功能两个入口；薪资排序是高频诉求。

**独立测试**：构造已知薪资的岗位数据，验证三种可用排序的顺序正确；验证置灰项不可点、有提示文案；验证排序后滚动、选中、详情联动正常。

**验收场景**：

1. **假如** 用户点击「排序」按钮，**当** 菜单展开，**那么** 显示五项：综合排序、薪资最高、薪资最低、最新发布（置灰）、匹配度最高（置灰）。
2. **假如** 用户点击「薪资最高」，**当** 菜单关闭，**那么** 列表按薪资从高到低排列，薪资「面议」岗位恒排最后；排序只在当前分类列表内生效，不改变分类计数。
3. **假如** 用户点击「综合排序」，**当** 菜单关闭，**那么** 列表恢复原始结果顺序。
4. **假如** 用户将鼠标悬停置灰的「最新发布」，**当** 查看提示，**那么** 显示「数据补齐后开放」类提示，点击无效果。
5. **假如** 用户对列表排序后选中某个岗位，**当** 查看右侧详情，**那么** 详情与排序后选中的岗位一致，不串位。

---

### 用户故事 3 - 筛选边界行为（优先级：P2）

薪资「面议」岗位、经验档位边界、「不限」互斥、智联福利缺失提示等边界行为符合约定，不出现误导性结果。

**优先原因**：边界行为决定筛选结果的诚实性——宁可藏起来，不可给错误预期。

**独立测试**：用「面议」薪资、多档经验文本、智联无福利数据等边界样本验证行为一致。

**验收场景**：

1. **假如** 用户未选任何薪资档位，**当** 查看列表，**那么** 薪资「面议」的岗位正常显示；**假如** 用户选了任一薪资档位（如「10-15K」），**当** 筛选生效，**那么** 「面议」岗位被隐藏，且不被归入「5K以下」等任何档位。
2. **假如** 用户在「工作经验」组选中「不限」，**当** 同时选中「1-3年」，**那么** 「不限」自动取消；反之选中「1-3年」时「不限」自动取消，二者互斥。打开面板时「不限」默认选中（该组不筛选）。
3. **假如** 岗位经验文本为「5-10年」「10年以上」，**当** 用户选中「5-10年」或「10年以上」档位，**那么** 对应岗位被正确筛出；文本不匹配任何档位（如「无经验」）的岗位仅在选择「不限」时显示。
4. **假如** 用户在「福利」组勾选「五险一金」，**当** 查看面板，**那么** 组下方显示灰色小字提示「智联岗位暂不支持福利筛选」；智联岗位因无福利数据被过滤属预期行为。
5. **假如** 用户对「已筛除」分类列表使用筛选与排序，**当** 操作生效，**那么** 行为与其它分类一致（dropped 岗位同样携带薪资/经验/学历/extra 快照）。

### 用户故事 4 - BOSS 福利数据补齐（优先级：P1，后端）

BOSS 列表抓取已有的福利字段（welfareList，形如「五险一金 | 双休」）在归一化时被保留为 `extra.welfare_list` 字符串数组，随岗位快照持久化并经 API 返回；旧结果与智联岗位缺失该键时不编造。

**优先原因**：福利筛选依赖该数据；当前链路（抓取→归一化→持久化→API）中 welfare 在归一化后丢失，必须先补齐才能支撑故事 1 的福利组。

**独立测试**：构造 BOSS 列表产物（含 welfare），走归一化与持久化链路，验证 `extra.welfare_list` 出现在结果快照与 API 岗位对象中；旧字段缺失时不报错、不填充。

**验收场景**：

1. **假如** BOSS 列表岗位带 `welfare`（如「五险一金 | 双休」），**当** 岗位进入结果快照，**那么** `extra.welfare_list` 为 `["五险一金", "双休"]`。
2. **假如** BOSS 列表岗位无 `welfare` 或为空，**当** 岗位进入结果快照，**那么** `extra` 不含 `welfare_list` 键，不编造值。
3. **假如** 智联岗位进入结果快照，**当** 查看其 `extra`，**那么** 不含 `welfare_list`（智联无此数据），前端福利筛选对智联岗位自然过滤。
4. **假如** 历史结果无 `welfare_list`，**当** 前端展示与筛选，**那么** 不报错、福利筛选视为不满足，与「缺失即不满足」约定一致。

---

### 用户故事 5 - 筛选与排序状态生命周期（优先级：P2）

筛选与排序状态在会话内（切换平台、切换分类）保留；刷新页面或重新跑搜索后回到默认（全「不限」+ 综合排序）。

**优先原因**：状态生命周期决定「切换平台后条件还在不在」的体验一致性，是容易出岔子的隐性问题。

**独立测试**：依次验证切分类、切平台、刷新、重新搜索四种场景下的状态保持与重置。

**验收场景**：

1. **假如** 用户在「匹配」分类选了「10-15K」，**当** 切换到「待确认」分类，**那么** 筛选条件保留，「待确认」列表同样按该条件收窄。
2. **假如** 用户在 BOSS 平台选了「五险一金」，**当** 切换到「全部」或「智联」，**那么** 筛选条件保留，智联岗位因无福利数据被过滤（面板提示可见）。
3. **假如** 用户设置了筛选与排序，**当** 刷新页面或重新发起搜索，**那么** 筛选回到全「不限」、排序回到「综合排序」，徽标消失。
4. **假如** 用户设置了筛选与排序，**当** 切换到其它分类再切回，**那么** 条件与顺序保持，不重置。
