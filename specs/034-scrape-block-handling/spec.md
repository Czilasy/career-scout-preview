# Feature Specification: 抓取阻断正确化（验证码/限流/风控/登录失效）

**Feature Branch**: `034-scrape-block-handling`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "抓取中遇到账号层面被拦（验证码、限流、风控、登录失效），系统必须：停下来（不许继续空跑、不许把岗位全丢进'待确认'）；说清楚（界面友好中文提示，如'触发验证码，请在浏览器处理后点继续'，不是一堆'未知抓取错误'）；能续跑（保留已抓结果和断点，用户点'继续'从断点接着抓，不丢已抓）。关键边界：对外友好 ≠ 对内不留记录，系统内部必须保留真实原因（是什么错、在哪、当时在干嘛）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 账号被拦时停下并说清楚 (Priority: P1)

用户跑抓取任务时遇到账号层面被拦（验证码、限流、风控、登录失效）。系统应当认出这是账号级阻断，**停下任务**，并给出一句**用户看得懂的中文提示**（如"触发验证码/滑块，需手动完成"、"登录已失效，需重新登录"），而不是让任务继续空跑、最后展示一堆"未知抓取错误"。

**Why this priority**: 这是用户原始需求的核心——被拦时第一时间明确告知并停止，直接决定用户对报错的信任；当前缺陷正是"真遇到拦截但系统认不出、静默继续"。

**Independent Test**: 用构造的受限样本（验证码页/限流提示页/登录墙/请求上限信号）回归：系统能正确识别为账号级阻断并触发暂停、提示对应中文文案，可独立验证。

**Acceptance Scenarios**:

1. **Given** 脚本抓取中途遇到验证码页面，**When** 脚本退出并带回真实原因，**Then** 任务暂停，提示"触发验证码/滑块，需手动完成"之类友好中文文案，且已抓内容与断点保留。
2. **Given** 脚本抓取中途检测到登录失效，**When** 脚本退出并带回真实原因，**Then** 任务暂停，提示"登录已失效，需重新登录"，不显示"未知抓取错误"。
3. **Given** 脚本抓取中途触发请求数上限，**When** 脚本退出，**Then** 任务暂停并提示请求上限相关友好文案，而不是静默继续或笼统报未知错误。
4. **Given** 账号级阻断样本，**When** 系统识别，**Then** 提示文案与停止原因一致（验证码就是验证码、限流就是限流），不出现"原因不明"或互相矛盾的说法。

---

### User Story 2 - 账号级阻断不再静默进"待确认" (Priority: P1)

账号被拦时，系统不得把这一批岗位全部塞进"待确认"假装继续。修复后，**账号级阻断**（验证码/限流/登录失效/请求上限）的失败不进入"待确认"，而是触发暂停；只有**带明确原因的单条软失败**（如单条详情解析失败、单条超时）才允许进入"待确认"，且每条必须能查到真实原因。

**Why this priority**: 这是用户原始需求"不许把岗位全丢进待确认"的直接落点，也是判定修复是否成功的核心证据。

**Independent Test**: 构造"一批全被账号级拦截"与"个别单条软失败"两类样本，分别验证前者整批暂停、后者按条带原因进待确认。

**Acceptance Scenarios**:

1. **Given** 一批岗位因账号级阻断失败，**When** 任务结束判定，**Then** 该批不进入"待确认"，任务以暂停收场并附真实原因。
2. **Given** 单个岗位真实抓取失败（如页面解析异常），**When** 该条落库，**Then** 进入"待确认"且带有明确原因（真实错误码与可读说明），可被后续操作（补抓/忽略）处置。
3. **Given** 账号级阻断与单条软失败混合出现，**When** 系统归类，**Then** 两者严格分流：账号级阻断不落"待确认"，单条软失败落"待确认"且带原因。

---

### User Story 3 - 暂停后能从断点续跑，不丢已抓 (Priority: P2)

任务因账号级阻断暂停后，用户到浏览器处理完问题（如完成验证码、重新登录），点"继续"，任务从断点接着抓，**已抓结果保留、不重复、不丢失**。

**Why this priority**: 续跑机制已有（025 断点保全、013 继续链路），本次只需保证"两处断线"修复后真实原因能正确驱动这条既有路径，故为 P2（机制已存在，本次接线）。

**Independent Test**: 暂停后点"继续"，验证续跑从断点开始、已抓岗位不重复也不丢失。

**Acceptance Scenarios**:

1. **Given** 任务因账号级阻断暂停，**When** 用户在浏览器处理后点"继续"，**Then** 任务从断点续跑，已抓岗位结果保留，不重复抓取已抓岗位。
2. **Given** 暂停时已抓部分结果，**When** 续跑，**Then** 已抓内容与断点进度均不归零、不丢失。

---

### Edge Cases

- 脚本退出时**没有**输出结构化失败行（异常路径/旧版本产物）→ 系统不得把真实原因判丢，按既有兜底规则（退出码粗分 + 高置信短语）归类，不得静默标成"未知抓取错误"而跳过暂停。
- 事件文件**不存在或读不到**（旧版本脚本未写事件）→ 系统不崩溃，回退按退出码分类，仍尽量给出可读原因。
- 账号级阻断与单条软失败在**同一批**混合出现 → 按真实逐条原因严格分流，不互相污染。
- 用户暂停后**一直不点继续** → 任务保持暂停态（既有暂停语义），不做超时自动丢弃。
- 多账号并行（若有）不涉及：本次任务为单账号、暂停为任务级。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 脚本抓取遇到账号级阻断（验证码、限流、风控/账号受限、登录失效、请求数上限）时，MUST 向系统传递**精确的真实错误原因**（结构化失败行携带注册表错误码），不得只留通用退出码或裸异常。
- **FR-002**: 系统收到账号级阻断信号时 MUST 触发任务暂停，并展示该错误码对应的**友好中文提示**（复用既有错误码注册表文案，不新建文案）。
- **FR-003**: 详情批子进程**非零退出**时，系统 MUST 读取脚本逐岗位记录的真实原因（事件文件），按真实错误码归类岗位失败；不得只用退出码粗分类把真实原因二次丢弃。
- **FR-004**: 账号级阻断（blocking + systemic 语义的错误码）的失败岗位 MUST NOT 进入"待确认"；"待确认"中只允许出现**带明确原因的单条软失败**。
- **FR-005**: 暂停时 MUST 保留已抓结果与断点；用户点"继续"后从断点续跑，不丢已抓、不重复抓取（复用既有暂停/续跑机制，不新建）。
- **FR-006**: 系统内部 MUST 保留真实失败原因（错误码、发生位置、上下文），供日志与诊断查询；对外友好提示不替代对内记录。
- **FR-007**: 事件文件缺失或读不到时，系统 MUST 正常回退按退出码分类，不得崩溃、不得伪造原因。
- **FR-008**: 脚本新增异常捕获的退出码 MUST 沿用既有约定（10=风控/限流/验证码类、11=请求上限类），不新建退出码。

### Key Entities *(include if feature involves data)*

- **抓取任务（run）**：一次完整抓取，单账号、任务级暂停；含断点进度与已抓结果。
- **岗位抓取记录**：逐岗位的成功/失败状态；失败记录携带真实错误码与可读原因。
- **错误码（source_* 注册表）**：系统唯一的错误分类与文案来源，区分账号级阻断（blocking+systemic）与单条软失败。
- **事件文件**：脚本逐岗位记录的真实 safe_code 明细，供 webui 非零退出时归类。
- **暂停/继续状态**：任务暂停态、断点保留、用户"继续"入口。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 构造样本回归下，验证码/限流/登录失效/请求上限样本 **100%** 触发任务暂停并显示对应友好中文提示，**0** 条账号级阻断岗位进入"待确认"。
- **SC-002**: 构造样本回归下，单条软失败样本 **100%** 以带明确原因的形式进入"待确认"，任务不因单条软失败中断。
- **SC-003**: 暂停后续跑场景，已抓岗位 **不丢失、不重复**，断点进度不归零。
- **SC-004**: 事件文件缺失场景，系统正常兜底运行，无崩溃、无伪造原因。
- **SC-005**: 真实账号跑一次正常抓取冒烟通过，基本盘无回归。

## Verification Scope *(mandatory)*

- 功能交付：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。

## Assumptions

- 报错中文文案已由既有错误码注册表提供，本次不新增文案、不修改文案。
- "误报"（正常的被抓成验证码/限流）已在 016 处理完毕，本次不重复处理；若仍出现误报需另立条目。
- 历史堆积在"待确认"的测试数据（如 MOM 那批 48 条）不处理、不迁移。
- 暂停/续跑机制本身（025 断点保全、013 继续链路）已存在且有效，本次只接线不重造。
- 详情批与列表批共用脚本主入口，异常捕获补一处、两侧受益（实现时核实）。
- 事件文件缺失/读不到时回退按退出码分类（FR-007）。
- 本 Spec 不改变暂停机制、前端交互、报错文案、历史数据与数据库结构。
