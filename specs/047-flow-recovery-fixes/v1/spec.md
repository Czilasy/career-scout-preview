# Feature Specification: 多平台流程异常恢复与状态切换一致性修复

**编号**：047

**Created**：2026-10-06

**Status**：六项修复目标冻结；后续实施及 2026-10-07 继续复核、发现问题直接返修已获用户授权。实现与验收进度见 tasks.md，未测场景不视作通过。

**适用原则**：复用现有项目宪法 1.4.0，无本轮原则修订。

**Input**：用户要求组合修复错误提示、继续入口、抽屉收拢、按钮展示、同类异步状态问题，并将已结束流程误拒绝历史删除纳入第 6 项；用户明确指定创建 047。

## 用户原话与范围来源

### A 组：用户原话与已确认边界

1. 错误原因：用户要求只读找原因，并指出“没登录应该要展示没登录的错误”。本轮核查只确认程序当时的登录判断为未知，不能把用户观察自动改写成程序已确认未登录。
2. 继续入口：用户指出报错之后无法继续，没有按钮。后续明确选择“允许失败轨道单独重试”，并确认在当前流程内保留另一轨道的进度和结果。
3. 抽屉收拢：用户要求从第二页开始出现抓取进度条、第三页出现筛选进度条时，对应抽屉自动收拢。
4. 按钮展示：用户要求“优化一下按钮的大小和展示”，解决按钮尺寸及排版偏大的问题。
5. 异步一致性：用户以立即停止后短暂闪红色错误再进入 04 为例，明确要求覆盖类似的逻辑耦合、并发及执行先后问题，不只修该单个案例。
6. 历史删除：用户确认流程已经结束，却被提示先结束或取消流程，要求查清原因后纳入第 6 个修复项并加入 SPEC。
7. 范围主体仍是当前流程；一条平台线的恢复与操作不能影响另一条线既有进度和结果。
8. 用户最终明确指定“创建047”，本规格依此采用 047，不建立此前建议的 046 v3。

### B 组：AI 候选建议，未冻结

- 桌面进度按钮高 32px、字号 13px、页面主按钮高 36px，以及具体强调样式，属于视觉候选，不是用户指定参数。
- 抽屉收拢后手动展开如何跨轮询、第二条轨道到达与刷新保留，属于建议中的细化规则，尚未单独确认。
- 聚合页外层提供删除整个流程、平台页保留单轨删除，属于新增删除层级建议，用户本轮未确认。
- 单轨重试的任务身份、检查点选择、结果替换方式和持久化机制由后续 Plan 提出；本规格不预设具体实现。

B 组不转成必须满足的产品约束，不阻塞已确认目标的规格记录；进入相应细节的冻结前应单独确认涉及体验或数据语义的决定。

## 目标与边界

用户在当前流程中能理解真实错误、处理问题后继续或单独重试平台轨道，看到适当收拢的条件和清楚紧凑的操作按钮；操作与阶段推进过程中状态一致，已结束历史能够按现有删除范围清理。

本轮覆盖同一主体内的错误、恢复、02/03/04 阶段展示、停止与保存、异步回调和历史删除。单平台与组合流程复用已有通用规则。046 v1/v2 的既有行为与 033 v2 的真实原因和完成证据要求继续作为基线；本规格明确变化处按用户最新确认执行。

不包含全项目异步重构、新主题、新平台、跨平台去重策略改写、正式历史数据批量修补、历史删除范围变更、打包、提交、推送或发布。

## User Scenarios & Testing

### User Story 1 - 看懂真实错误原因（Priority: P1）

用户启动任务后，能区分明确未登录、登录状态无法判断和完成证据不足，得到与实际原因一致的提示。

**Why this priority**：错误原因决定用户能否正确处理问题。

**Independent Test**：分别观察明确未登录、状态未知和独立证据缺失的任务，核对提示及可查询诊断。

**Acceptance Scenarios**：

1. **Given** 已确认未登录或登录失效，**When** 抓取受阻，**Then** 界面展示登录错误及处理建议，具体原因可追踪。
2. **Given** 登录探测没有明确结论，**When** 任务停止推进，**Then** 如实展示状态暂无法确认，不声称已确认未登录或浏览器未启动。
3. **Given** 已知具体执行失败且任务结果证据不完整，**When** 用户查看原因，**Then** 具体失败原因仍可见，完整性结论不覆盖或丢失它。
4. **Given** 登录识别链路收到可判定的未登录事实，**When** 经过探测、平台适配、任务收口及界面展示，**Then** 全链路保持登录错误；不能只更换为“状态未知”的文案而留下识别或传递缺陷。确实缺少判定证据时仍如实保留未知。

### User Story 2 - 在原流程恢复或单轨重试（Priority: P1）

用户处理可恢复问题后继续原轨道；已失败的轨道也可在当前流程内单独重试，另一轨道进度和结果保留。

**Why this priority**：避免一个平台的问题让整轮结果作废或没有下一步操作。

**Independent Test**：分别让任一平台暂停或失败，处理原因后从用户入口继续或重试，核对另一轨道前后状态和结果。

**Acceptance Scenarios**：

1. **Given** 轨道因可恢复问题暂停，**When** 用户处理原因后点击继续，**Then** 重新检查条件并继续该轨道；条件仍不满足时提示真实原因，入口保持可理解。
2. **Given** 一条轨道真正失败、另一条正在运行，**When** 用户单独重试失败轨道，**Then** 重试归属当前流程，不停止、清空或重置另一条轨道。
3. **Given** 一条轨道真正失败、另一条已经结束并保存结果，**When** 用户单独重试失败轨道，**Then** 已保存的另一平台结果保留，重试结果归属本流程。

### User Story 3 - 进度出现后收拢对应抽屉（Priority: P2）

用户看到第二页抓取或第三页筛选进度时，对应配置抽屉自动收拢，让执行现场可见。

**Why this priority**：减少配置区域对实际执行信息的遮挡。

**Independent Test**：分别从单平台和全部流程进入第二、第三页执行，观察进度出现时对应抽屉状态。

**Acceptance Scenarios**：

1. **Given** 第二页配置抽屉展开，**When** 本阶段执行进度出现，**Then** 对应抽屉自动收拢。
2. **Given** 第三页筛选条件展开，**When** 本阶段筛选进度出现，**Then** 对应抽屉自动收拢；自动进入筛选与手动启动都覆盖。

### User Story 4 - 使用紧凑且清楚的操作按钮（Priority: P2）

用户在进度卡及相关操作区看到更紧凑的按钮与清楚的操作层级，保留已提供的操作能力。

**Why this priority**：当前尺寸和排列过于突出，影响阅读进度和操作判断。

**Independent Test**：观察第二、第三页在桌面下的操作展示，核对按钮大小、排列和可点击性。

**Acceptance Scenarios**：

1. **Given** 进度卡有多个操作按钮，**When** 查看修复后页面，**Then** 按钮尺寸和排列紧凑，操作含义及层级清楚，原有能力可达。
2. **Given** 桌面页面处于操作忙态，**When** 用户查看和操作，**Then** 文案可读、按钮可用，无重叠或内容遮挡。

### User Story 5 - 操作和状态推进保持一致（Priority: P1）

用户在停止、暂停、继续、单轨重试、保存和阶段交接期间，看到与已确认事实一致的状态、提示、按钮、结果和页面。

**Why this priority**：短暂的错误状态和迟到回调会误导用户，影响已结束结果的可信度。

**Independent Test**：经用户入口观察这些操作与后台回调不同先后顺序下的完整页面变化，不只检查最终落点。

**Acceptance Scenarios**：

1. **Given** 用户操作现有“终止本轨”入口，**When** 终止正常完成，**Then** 保持该入口现有终止语义，过程中不误报硬失败，不影响另一轨道；不能把终止改成结束保存。
2. **Given** 用户操作“结束并保存结果”并选择立即执行，**When** 操作正常完成并进入 04，**Then** 正常收尾期间不先展示错误的硬失败提示，保留已完成结果；不强制等待当前批次抓完。
3. **Given** 操作与批次完成、后台回调或轮询响应先后交错，**When** 显示执行现场及推进页面，**Then** 不出现由混合新旧事实造成的状态矛盾，旧响应不覆盖新状态。
4. **Given** 轨道已结束，**When** 旧批次稍后返回，**Then** 用户已结束状态和结果不被错误回调改写，诊断可追踪。
5. **Given** 停止或保存确实失败，**When** 操作返回，**Then** 展示真实失败原因与可用处理入口，不把真实失败掩盖为正常完成。

### User Story 6 - 已结束历史不被残留状态错误拦截（Priority: P1）

用户看到流程已结束、平台轨道失败或已停止后，可按现有删除范围清理历史，不被内部残留排队状态错误要求再次结束流程。

**Why this priority**：当前删除按钮允许操作，后端却以另一份旧状态拒绝，用户无法清理已结束记录。

**Independent Test**：构造轨道已终结、关联记录残留排队的历史，以及真正活动中的历史，经界面观察删除可用性、响应和作用范围。

**Acceptance Scenarios**：

1. **Given** 流程已结束且目标轨道失败或已停止，**When** 用户按现有入口删除其历史，**Then** 不因已结束任务的残留排队状态误报“请先结束或取消流程”，删除范围与入口含义一致。
2. **Given** 目标确实仍在排队、运行或暂停，**When** 用户查看或尝试删除，**Then** 前后端对删除资格判定一致，继续保护实际未结束任务。
3. **Given** 用户删除某平台轮次，**When** 删除成功，**Then** 按现有单轨删除边界处理，不误删另一平台进度、结果或其他流程历史。
4. **Given** 流程已结束但含失败轨道，**When** 计算历史是否可删除，**Then** 不把“全部成功”当成“已经结束”的必要条件。

### Edge Cases

- 浏览器已启动但登录探测未知；明确未登录与未知必须保持区别。
- 一方失败、另一方运行、暂停或已经保存结果时的恢复和单轨重试。
- 自动筛选交接、页面切换或刷新导致的抽屉状态读取；手动展开保留策略属于 B 组待确认细化。
- 用户动作和任务自然完成同时发生；旧轮响应晚于新状态返回。
- 正常立即停止与真实保存失败；诊断事实和用户终态不能相互冒充。
- 零岗位失败历史、失败与已停止共存的聚合历史，以及关联记录残留活动状态。
- 历史删除时实际任务活动状态变化；不得为了通过删除而直接绕过运行保护。

## Requirements

### Functional Requirements

- **FR-001**：具体错误原因必须正确识别、保留并展示；检查并修复登录探测、平台适配及原因传递链路，不能只改错误文案；明确未登录、状态未知和证据缺失不得混为同一错误。
- **FR-002**：已知执行失败原因不得被任务完整性汇总结论覆盖；诊断可追踪到对应流程、平台与阶段。
- **FR-003**：可恢复问题必须提供可用的处理后继续入口，继续前核对问题是否解除。
- **FR-004**：已失败轨道必须支持在当前流程内单独重试，保留另一轨道的进度和结果。
- **FR-005**：第二页抓取与第三页筛选出现对应阶段进度条时，对应条件抽屉自动收拢；单平台和全部流程都适用。
- **FR-006**：相关操作按钮大小与排列更紧凑，操作层级清楚；保持已提供能力可达及桌面可用。
- **FR-007**：当前流程中的停止、暂停、继续、重试、保存与阶段交接必须保持用户状态、提示、操作与结果的一致性，不只修复某个闪红场景；分别覆盖“终止本轨”与“结束并保存结果”，保持各自既有语义。
- **FR-008**：正常收尾不误显示硬失败；真实操作失败必须明确呈现，不能用延迟、隐藏或成功提示消除实际错误。
- **FR-009**：过期响应与结束后的旧回调不得改写当前已确认的用户状态和已保存结果；诊断仍可查询。
- **FR-010**：失败、停止与成功都是可能的结束结果；历史删除资格不能以全部成功作为前提。
- **FR-011**：结束状态及关联记录保持一致；对于已终结任务的残留活动状态，删除资格不得错误拒绝已结束历史，也不得直接绕过真正活动任务的保护。
- **FR-012**：删除入口可用性、服务端删除资格及提示使用一致的任务生命周期事实，实际仍未结束时明确说明阻断原因。
- **FR-013**：历史删除继续采用现有作用范围，删除某平台轮次不得误删另一平台或其他流程；新增聚合整流程删除不属于已确认范围。
- **FR-014**：通用错误、恢复、状态及操作规则在单平台和多平台流程中统一复用，平台专属识别仍由各平台适配。

### Key Entities

- **流程**：用户一次启动形成的运行边界，容纳平台轨道及其结果、诊断和历史。
- **平台轨道**：可独立操作、继续或失败重试的一条平台运行线。
- **阶段现场**：抓取、筛选和结果阶段的条件、进度及操作展示。
- **操作与尝试**：用户的暂停、继续、停止、保存或重试意图及其实际结果。
- **历史轮次**：用户可查看、按既有范围删除的已结束记录。
- **错误与完整性事实**：具体失败原因和任务是否有足够完成证据，两者需同时保留。

## Success Criteria

### Measurable Outcomes

- **SC-001**：明确登录错误、状态未知和独立证据缺失验收场景的提示均与实际事实相符；已知原始原因不丢失。
- **SC-002**：任一平台的可恢复继续和失败单轨重试场景均可从界面完成，另一轨道进度及结果不受损。
- **SC-003**：单平台及全部流程的第二、第三页进度出现后，对应抽屉自动收拢场景均满足用户要求。
- **SC-004**：桌面及忙态场景按钮紧凑可读，原有操作能力可达，无重叠遮挡。
- **SC-005**：覆盖用户动作与后台结果不同先后顺序的验收场景，正常动作误闪硬错误、状态矛盾、旧响应覆盖新状态的次数为零；真实失败仍可见。
- **SC-006**：已结束且存在残留活动记录的历史场景不被错误拦截；真正未结束任务仍受保护，单轨删除不影响另一轨道。

## Verification Scope

- 初始规划轮只授权规格、Plan 与详细 Tasks；后续用户已明确授权实施、复核与直接返修。正式删除仍按具体测试对象与写入边界确认；不包含提交、推送、发布。
- 后续实施先做原失败用例、聚焦回归和必要相邻检查；整条交付链收敛后再按项目规定做一次最终后端全量、前端测试、构建和卫生检查，不逐项重复全量。
- 后端最终命令：`uv run python -m unittest discover -s tests`；前端在 `webui/` 执行 `npm test` 与 `npm run build`；卫生检查为 `uv run python -m unittest tests.test_repo_hygiene`、`git diff --check` 与 `git status`。
- 最终验证包含真实用户入口下的错误恢复、单轨重试、进度与抽屉、立即停止到结果页的全过程，以及历史删除行为。正式删除属于明确数据写入，应在测试执行前确认环境及写入边界。
- 临时数据库、桩或测试客户端检查只能报告相应自动化等级，不能称为真实账号和真实数据端到端验收；无法执行真实环境时明确报告未验证。
- 全量失败保留清单，相关修复及聚焦通过前不重复全量；测试日志写系统临时目录，遵守项目清理纪律。

## Assumptions

- 保留已确认的多平台流程归属、平台独立操作、结果合流和历史边界，修复其错误行为。
- 单轨重试的内部身份及数据处理方案由 Plan 定义，不在本规格猜测；涉及新增用户体验或结果取舍时先确认。
- 第 6 项已核实的现象是轨道已结束与关联搜索记录残留排队状态不一致；修复需处理一致性，不把残留记录当成真实运行证据。
- 具体登录响应为何为未知、闪红瞬间的浏览器响应序列尚未完整取证；不得把定位线索写成已重现或已修复。
- 本文档及检查清单不代表实现授权、测试通过或产品验收完成。
