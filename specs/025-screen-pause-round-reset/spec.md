# Feature Specification: 批中暂停二选一 + 暂停断点保全 + 完成态自动新一轮

**Feature Branch**: `025-screen-pause-round-reset`

**Created**: 2026-08-27 | **Status**: Draft（grill-me 冻结需求，3 条：B076 优化 / B077 Bug / B078 优化）

**Input**: 用户冻结需求（grill-me 确认，3 条）：

1. **B076（优化）· 暂停 AI 筛选体验**：JD 详情抓取批次进行中（一批 15~30 条 × 8~15 秒/条 + 批间 30 秒冷却）点「暂停」不再干等当前批抓完（5~6 分钟）——批中暂停弹二选一：「立即停止」（默认选中、回车触发，当前批作废、继续后该批重头抓、最终数据不丢）/「等这批抓完」（现状批边界停、数据完整）；弹窗平实提示「立即停止将放弃当前批次已抓取的内容，下次继续时需要重新抓取这一批」（不渲染严重性），并展示当前批进度（第几批/共几批）；粗筛/精筛阶段、批间间隙点暂停不弹窗直接停；立即停止 → 落「已暂停」（非取消）、调试浏览器关闭、之前已抓结果保留、已暂停再点幂等不报错；批间冷却分段响应停止信号（批间暂停不用干等冷却结束）；停止时清理卡死防护批次登记（避免「继续」被误判卡死重抓三次）。
2. **B077（Bug）· 暂停导致已抓 JD 断点丢失、继续后从头重抓**：暂停时若当前批抓取超 5 分钟且批内无动静（被判卡死），已抓 JD 全丢、断点文件被写成空，继续后从第一批重头抓（实测一批 8 个重复岗位）。根因（读代码核实，`fetch_job_details` 批循环）：①卡死防护把"批内无心跳"误判为卡死（BOSS 子进程模式条级进度只在批返回时一次性报）；②子进程被 kill 后 `fetch_details_batch` 的抢救逻辑（returncode≠0 时从产物文件捡回已抓，`source_boss_cdp_detail.py` 286-307 行）确实把已抓结果放进了返回值，但 `fetch_job_details` 的卡死重抓分支（`guard.should_retry` 命中后 `continue`）**跳过**了批返回后的结果处理（340-381 行），抢救出的已抓结果从未进入 `jd_by_idx` 就被丢弃；③暂停恰落在"批已返回、正要重抓"窗口 → 重抓未开始就停止 → 返回空结果 → 断点无该批已抓 → 已抓 JD 全丢；④继续时断点为空 → 从第一批重头抓，重抓整批导致已抓岗位重复抓。触发条件（两个同时满足）：①暂停时当前批已抓超 5 分钟且批内无动静（已被判卡死）；②暂停恰好落在"批已返回、正要重抓"窗口。修复：**不动卡死防护判定，只做断点保全**——批返回后**立即**处理结果（把抢救出的已抓并入 jd_by_idx，不再被重抓分支丢弃）；卡死重抓时剔除已抓成功的岗位（只重抓缺失，避免重复抓）；暂停返回时绝不把空结果写进断点；断点保留已抓 JD。与 B076 边界（已确认）：立即停止 = 一律作废当前批（弹窗已告知）；B077 断点保全只管正常暂停路径（等批完 / 批间 / 其他暂停）。
3. **B078（优化）· 启动/刷新恢复策略**：流程正常完成后刷新/重启还"糊脸"（自动加载上一轮结果到 04 页）。方案：启动/刷新区分两种状态——有未完成流程（运行中/暂停/中断，未落历史）→ 恢复现场糊脸继续（**B068 行为保留不改**）；无进行中任务且上一轮已正常走完、结果已落历史 → 执行「开始新一轮」按钮背后逻辑（01 页开放、02/03/04 自然灰色、上一轮结果/草稿/进度全不出现，想看结论去历史）。实现：**复用「开始新一轮」现有逻辑（`resetWorkflow`），不设计新机制、不新写恢复/重置代码**；01 页不涉及"清空草稿"决策（关键词/城市/画像在锁定页面里，不存在该问题）。纯前端，后端零改动。

## User Scenarios & Testing

### User Story 1 - 批中暂停弹二选一：立即停止 / 等这批抓完 (P1)

用户正处 JD 详情抓取批次中（一批 15~30 条 × 8~15 秒/条，抓一批要几分钟），点「暂停」→ 弹窗二选一：「立即停止」默认选中、回车即触发；「等这批抓完」按现状批边界停止。弹窗展示当前批进度（第几批/共几批）与平实提示「立即停止将放弃当前批次已抓取的内容，下次继续时需要重新抓取这一批」——普通提示，不渲染严重性、不吓用户。

**为什么是 P1**：本次需求主体，直接解决"点了暂停干等 5~6 分钟"。

**独立测试**：前端测试——批中（stage=fetch_jd 且批内信号）暂停触发弹窗、默认按钮聚焦、回车触发立即停止、进度文案正确、批间/粗筛/精筛暂停不弹窗；后端测试——暂停 API immediate 模式（状态 paused、浏览器关闭信号、幂等）。

**验收场景**：

1. **Given** 任务正处抓 JD 批次中（progress.stage=fetch_jd 且批内信号），**When** 用户点「暂停」，**Then** 弹出二选一弹窗，展示第几批/共几批，文案为平实提示。
2. **Given** 弹窗打开，**When** 用户直接按回车（不移动焦点），**Then** 触发「立即停止」（默认按钮聚焦）。
3. **Given** 用户选「立即停止」，**When** 停止完成，**Then** 1 秒内任务状态为「已暂停」（非取消）、调试浏览器关闭、之前已抓的结果保留。
4. **Given** 任务已暂停，**When** 用户再次点「立即停止」，**Then** 幂等不报错。
5. **Given** 用户选「等这批抓完」，**When** 批次继续运行，**Then** 当前批抓完后停止，数据完整（不丢当前批）。
6. **Given** 任务处于粗筛/精筛阶段或批间间隙，**When** 用户点「暂停」，**Then** 不弹窗，直接停止。

### User Story 2 - 配套行为：批间冷却分段响应 + 停止清理批次登记 (P1)

批间冷却（默认约 30 秒）期间点暂停，不再干等冷却结束——冷却改为分段响应停止信号，stop_event 置位即提前退出冷却、立即停止。停止（立即停止/正常暂停/取消）时清理卡死防护的批次登记，避免「继续」后被误判卡死重抓三次。

**为什么是 P1**：B076 冻结需求 6/7 的配套项，与 US1 同批交付。

**独立测试**：后端测试——冷却 sleep 分段（注入短冷却 + 提前置 stop_event → 提前退出、不 sleep 满）；guard 停止清理（停止后 batch 登记清空，新 run 同 key 不残留 stalled 状态）。

**验收场景**：

1. **Given** 批间冷却 sleep 中，**When** 用户点暂停，**Then** 立即响应停止（不 sleep 满 30 秒）。
2. **Given** 任务停止（暂停/取消），**When** 检查 guard 批次登记，**Then** 该任务批次登记已清理，无残留 stalled 批次。
3. **Given** 用户点「继续」，**When** 新一轮批次开始，**Then** 不被旧批次登记误判卡死（不触发额外重抓）。

### User Story 3 - 暂停断点保全：重抓不丢已抓、空结果不写断点 (P1)

卡死防护把"批内无心跳"误判为卡死并重抓该批时，已抓结果不再被丢弃（从子进程产物文件捡回）；暂停（正常路径：等批完/批间/其他暂停，含卡死重抓窗口）返回时绝不把空结果写进断点文件，断点保留已抓 JD。继续后只补抓未抓岗位、不重复已抓岗位。**卡死防护判定逻辑本身不动**（300 秒无心跳判定、3 次重试、环境分流全部保持现状）。

**为什么是 P1**：数据丢失 Bug（实测一批 8 个岗位重复抓），数据安全优先。

**独立测试**：后端测试——注入"批返回后 stop_event 置位"（卡死重抓窗口暂停）：产物文件有已抓 detail → 捡回并入 jd_map → 断点文件保留已抓 JD；注入"重抓路径"：重抓前捡回产物已抓、重抓只抓缺失、结果合并不重复；注入"immediate 停止"：当前批作废（不捡回、不写断点）；断言卡死判定参数未改动。

**验收场景**：

1. **Given** 某批已被判卡死（300 秒无心跳）、产物文件存有已抓 detail，**When** 用户暂停落在"批已返回、正要重抓"窗口，**Then** 断点文件保留已抓 JD（该批产物捡回并入断点），不写成空。
2. **Given** 上述暂停后点「继续」，**When** 新一轮批次开始，**Then** 只补抓未抓岗位，不重复已抓岗位（实测的"一批 8 个重复岗位"不再出现）。
3. **Given** 卡死重抓路径（`should_retry` 命中），**When** 批返回后处理结果，**Then** 抢救出的已抓并入 jd_by_idx、重抓列表剔除已抓成功岗位（只重抓缺失、结果合并不重复）。
4. **Given** 用户选「立即停止」（B076），**When** 停止完成，**Then** 当前批一律作废（批返回后先检查立即信号、该批结果不并入），断点保留之前批已抓结果。
5. **Given** 卡死防护运行，**When** 检查判定参数，**Then** 300 秒判定、3 次重试、环境分流逻辑全部保持不变。

### User Story 4 - 完成态启动/刷新自动「开始新一轮」 (P2)

流程正常完成后，刷新/重启软件不再"糊脸"——自动执行「开始新一轮」背后的逻辑：01 页（上传简历页）开放，02/03/04 因没有任何内容自然灰色，上一轮的结果、草稿、进度全不出现；想看上一轮结论去历史。有未完成流程（运行中/暂停/中断）时行为不变（恢复现场继续，B068 保留）。

**为什么是 P2**：纯前端体验优化，复用现有 `resetWorkflow`，无新机制。

**独立测试**：前端测试——mock 无进行中任务 + 最新历史轮为已完成 → onMounted 后调用 resetWorkflow（界面干净 01 页、无上一轮残留）；mock 有未完成流程（运行中/暂停/中断）→ 不调用 resetWorkflow、恢复现场（B068 不变）。

**验收场景**：

1. **Given** 上一轮已正常走完、结果已落历史、无进行中任务，**When** 刷新/重启应用，**Then** 界面与点过「开始新一轮」一致：干净 01 页、无上一轮结果/草稿/进度残留。
2. **Given** 上一轮结果已落历史，**When** 用户在历史抽屉查看，**Then** 上一轮结论仍可查看（仅界面不糊脸，数据不删）。
3. **Given** 有一轮暂停/中断未完成，**When** 刷新/重启应用，**Then** 恢复现场可继续（与现状一致，B068 行为不变）。

## Requirements

### Functional Requirements

- **FR-001**: 暂停 AI 筛选时，若正处抓 JD 批次中（progress.stage=fetch_jd 且批内信号为真），前端 MUST 弹出二选一弹窗（「立即停止」默认选中、回车触发；「等这批抓完」）。
- **FR-002**: 弹窗 MUST 展示当前批进度（第几批/共几批），并展示平实提示文案「立即停止将放弃当前批次已抓取的内容，下次继续时需要重新抓取这一批」——普通提示，MUST NOT 渲染严重性/警告风格。
- **FR-003**: 选「立即停止」MUST 触发立即停止：当前批作废（下次继续从该批重头抓）、任务落「已暂停」（非取消）、调试浏览器关闭、之前已抓结果保留、1 秒内生效。
- **FR-004**: 选「等这批抓完」MUST 保持现状批边界停止语义，当前批数据完整。
- **FR-005**: 粗筛（screen_a/ai_rough）/精筛（ai_fine）阶段、批间间隙点暂停 MUST NOT 弹窗，直接停止。
- **FR-006**: 批间冷却 MUST 分段响应停止信号：stop_event 置位后提前退出冷却，批间暂停立即生效（不再干等冷却结束）。
- **FR-007**: 任务停止（立即停止/正常暂停/取消）时 MUST 清理该任务在卡死防护中的批次登记，避免「继续」后被误判卡死触发额外重抓。
- **FR-008**: 暂停 API（POST /api/task/pause/<run_id>）MUST 支持 mode 参数（immediate / graceful，缺省 graceful 保持旧前端兼容）；immediate 模式对已暂停任务 MUST 幂等不报错。
- **FR-009**: 卡死重抓路径 MUST NOT 丢弃当前批已抓结果：批返回后立即处理结果（`fetch_details_batch` 抢救出的已抓并入 jd_by_idx），卡死重抓时剔除已抓成功岗位、只重抓缺失、结果合并（不重复已抓岗位）。
- **FR-010**: 暂停（正常路径，含卡死重抓窗口）返回时 MUST NOT 把空结果写进断点文件；断点 MUST 保留已抓 JD（即使该批被判过卡死）。
- **FR-011**: 卡死防护判定逻辑 MUST NOT 改动（300 秒无心跳判定、3 次重试、环境/偶发分流均保持现状）。
- **FR-012**: B076/B077 边界 MUST 生效：立即停止一律作废当前批（不捡回该批产物）；断点保全只作用于正常暂停路径（等批完 / 批间 / 其他暂停）。
- **FR-013**: 启动/刷新时，无进行中任务（无 running/queued/paused/interrupted 任务；含「latest-running-task 无活动任务」与「latest-running-task 返回已完成终态任务」两种情况）且上一轮已正常走完、结果已落历史，前端 MUST 自动执行「开始新一轮」逻辑（复用现有 `resetWorkflow`，MUST NOT 新写恢复/重置代码）：01 页开放、02/03/04 自然灰色、上一轮结果/草稿/进度不出现。
- **FR-014**: 有未完成流程（运行中/暂停/中断，未落历史）时启动/刷新 MUST 恢复现场（B068 行为保留，不改）。
- **FR-015**: B078 为纯前端实现，后端零改动。
- **FR-016**: 新增文件（PauseBatchChoiceDialog 组件 / task_pause_support 模块）MUST 登记进 constitution 模块地图；门面文件（webui/app.py、webui/store.py、webui/source.py、scripts/boss_cdp_raw.py）不追加逻辑。

### Key Entities

- **PauseBatchChoiceDialog（新组件，webui/src/components/PauseBatchChoiceDialog.vue）**：批中暂停二选一弹窗——立即停止（默认聚焦、回车触发）/ 等这批抓完、平实提示文案、当前批进度（第几批/共几批）。
- **task_pause_support（新模块，webui/task_pause_support.py）**：暂停编排助手——immediate/graceful 分支编排、immediate 幂等判定、批中立即停止信号标记（stop_event 挂属性）、与 guard 的联动（immediate_stop_task / 取消清理）。`task_continue_api.py` 的 `api_task_pause` 仅做参数解析与响应组装（该文件存量 791 行已超 600 预警线，禁止继续膨胀，见 plan Constitution Check）。
- **PipelineGuard 停止清理（webui/pipeline_guard.py）**：新增 `immediate_stop_task(task_id)`——终止该任务活动批次子进程（复用 `ScraperExecutor._terminate_tree` 语义）+ 批次置 terminal 并清理登记，供暂停/取消调用；判定/监控逻辑零改动。
- **fetch_job_details 断点保全（webui/pipeline_exec_details.py）**：批返回后立即处理结果（抢救的已抓并入 jd_by_idx，不再被重抓分支丢弃）、卡死重抓剔除已抓成功岗位（只抓缺失）、批返回窗口停止时保全（普通）或作废（immediate）、冷却分段响应、批内信号回调。

### Edge Cases

- 批中暂停弹窗打开期间，批次可能自然完成或任务已停（弹窗与任务状态竞态）：弹窗 MUST 监听任务状态——批内信号消失（批次完成）或任务已 paused/终态时自动关闭，避免对已完成批次弹"立即停止"。
- 立即停止恰落在"批刚开始、子进程尚未 spawn"的微窗口：无法 kill（guard 无登记进程），但 stop_event 已置位，任务线程在批前检查（现有 158 行）即停，不产生已抓内容可作废，行为等价、无损。
- 卡死重抓窗口选「等这批抓完」：该批已判卡死、等不到"抓完"，实际为"重抓窗口过后停在批边界"，该批已抓由 B077 捡回保全（与弹窗文案的细微偏差，用户已确认边界）。
- 重抓剔除已抓后剩余为空（卡死前该批已全部抓完）：直接完成该批、不重抓（避免无谓重复抓）。
- 「等这批抓完」在正常批次：stop_event 置位不打断进行中的批（批内无检查点），当前批完整抓完后、下一批开始前停止，数据完整。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 后端聚焦测试通过：暂停 API immediate 模式（状态 paused、浏览器关闭、幂等）；guard 停止清理；冷却分段响应；重抓捡回不丢已抓、只抓缺失；immediate 作废当前批；空结果不写断点；卡死判定参数未变。
- **SC-002**: 前端测试通过：批中暂停弹窗（二选一、默认聚焦、回车触发、进度与文案）；粗筛/精筛/批间不弹窗；完成态启动自动「开始新一轮」；未完成态恢复现场不变。
- **SC-003**: `npm run build` 通过；后端全量测试通过；仓库卫生检查（`tests.test_repo_hygiene` + hooks）通过。
