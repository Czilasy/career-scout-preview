# Close Confirm Bridge Contract: 045 v2

本契约定义桌面壳与前端之间关于「关闭确认」的双向约定。两端都按本契约实现，任一侧变更需同步更新本文件。

## 通道

壳侧通过 pywebview 内置的 `window.evaluate_js(script, callback)` 调用前端；前端入口返回 Promise，pywebview 在 Promise resolve 后回调壳侧（research D1）。

壳侧不再使用任何系统原生弹窗。

## 壳 → 前端

**入口**：`window.__csCloseConfirm(payload)` — 返回 `Promise<CloseConfirmResult>`

**payload**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `scenario` | `"idle_save" \| "running_stop"` | 由壳侧按最新流程状态判定后传入，前端不自判 |

- `idle_save`：流程存在、有已落盘岗位、当前未在运行。
- `running_stop`：流程正在运行（排队中或运行中）且有已落盘岗位。

**前置条件**：壳侧只在「有流程且岗位数 > 0」时才调用本入口；无流程或岗位数为 0 时壳侧直接放行关闭，不经过前端。

## 前端 → 壳

**resolve 值**：

| 字段 | 类型 | 说明 |
|---|---|---|
| `action` | `"confirm" \| "cancel"` | `confirm` = 用户选择结束（保存后关闭）；`cancel` = 用户放弃关闭 |

**reject / 未挂载 / 抛错**：壳侧一律按「不可用」处理——不弹框、直接放行关闭并写桌面日志（research D6）。

## 壳侧行为约定

| 结果 | 壳侧动作 |
|---|---|
| `confirm` + `idle_save` | `finish` 落轮 → 置关闭守卫 → 关窗 |
| `confirm` + `running_stop` | `pause(mode="immediate")` → `finish` 落轮 → 置关闭守卫 → 关窗 |
| `cancel` | 不关窗、不改流程状态、不置守卫 |
| 不可用 | 不弹框、记日志、放行关闭 |

**关闭守卫**：收尾完成准备关窗前置位；`closing` 事件命中守卫时直接放行，用于阻断 `destroy()` 二次触发弹框（research D2）。守卫在所有关闭入口（原生 X、自绘 X、`quit_app`）上一致生效。

**线程**：Promise 回调在 UI 线程，收尾（暂停 + 落轮）必须转后台线程执行，不得冻结界面（research D3）。

## 前端行为约定

| 场景 | 标题 | 说明行 | 动作键 | 取消 |
|---|---|---|---|---|
| `idle_save` | 结束并保存结果 | （沿用既有口径） | 结束并保存 | 右上 ✕ / Esc |
| `running_stop` | 还有任务正在进行中 | 立即结束只保存已抓到的，这一批会丢弃；不着急可以先暂停，落盘后再关闭 | 立即结束 | 右上 ✕ / Esc |

- `running_stop` **不得**出现等待类选项（如「等这批抓完」）。
- 动作键点击后：动作键置灰 + 显示等待指示，两个出口都禁用，期间重复触发无效。
- 等待期间右上 ✕ 保持可用，用于中途放弃。

## 不变量

1. 关闭判定（有没有流程、有没有岗位、是否在跑）由壳侧单一负责，前端只按传入场景呈现。
2. 收尾逻辑复用既有暂停与落轮链路，本契约不引入新的保存机制。
3. 浏览器模式下前端不注册任何关闭拦截，壳侧入口不存在亦不影响前端功能。
