# Feature Specification: 日志白箱（log-whitebox）

**Feature Branch**: `033-log-whitebox`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "白箱：任何一次失败，事后必能在日志查到真实原因。不允许'出事了但什么都没留下'。所有日志都必须落脚，不允许出现抓不到原因的错误。本次范围=白箱接线+卫生强制检查；抓取阻断（验证码/限流/登录失效要停下说人话）另行单独做。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 任何一次失败，事后都能查到真实原因（Priority: P1）

用户遇到一次抓取或筛选失败，事后（哪怕隔天）打开日志查看页，能查到这次失败当时的真实情况：是什么类型的错、发生在哪个阶段、对应哪次任务，而不是只有一句"未知错误"或"抓取执行失败"。

**Why this priority**: 这是白箱的核心目标，也是用户最初要解决的问题：出事后能复盘、能定位、能修。其余故事都围绕它展开。

**Independent Test**: 可以独立验证：人为制造一次任务失败（包括"没认出来的异常"这条路径），在日志查看页检索对应任务编号，能看到异常类型、阶段、任务编号三要素齐全。

**Acceptance Scenarios**:

1. **Given** 一次真实抓取任务以失败告终，**When** 我在日志查看页按任务编号检索，**Then** 能看到这次失败的异常类型、发生阶段、任务编号，而非仅一句"未知抓取错误"。
2. **Given** 失败发生在进程内执行路径（不经外部进程），**When** 我查看日志，**Then** 同样能看到异常详情，而不是只有"抓取执行失败"四个字。
3. **Given** 失败原因是登录失效/限流/验证码/网络等已识别的类型，**When** 我查看日志，**Then** 原因与现场线索均可查。

---

### User Story 2 - 抓取脚本的"现场"能被记录和查询（Priority: P2）

抓取脚本是另开进程在干活的，它抓每页列表、打开每个岗位详情、检查登录、判断风控的过程，是判断"当时发生了什么"的关键现场。这些现场要能被记下来，并且在日志查看页查得到。

**Why this priority**: 很多失败的真实原因只在脚本侧发生过一次（例如某岗位详情页被拦），主进程只看到"整批失败"的结论。没有现场，结论就无从验证。这是"所有错误都能查到"里最难接的一段。

**Independent Test**: 可以独立验证：跑一次真实小抓取（成功或失败均可），在日志查看页能看到脚本侧的抓取记录（详情页访问、登录检查、风控事件），且带任务编号与时间。

**Acceptance Scenarios**:

1. **Given** 一次真实抓取（含详情页抓取）正在运行，**When** 任务结束后我在日志查看页检索，**Then** 能看到脚本侧的现场记录（详情页、登录检查、风控判断），而非只有主进程的汇总结论。
2. **Given** 脚本侧发生风控/限流判断，**When** 任务结束后查询日志，**Then** 该判断及依据可查。
3. **Given** 主进程因故异常退出，**When** 事后单独查看日志文件，**Then** 脚本侧已记录的内容仍然存在（不被主进程拖累丢失）。

---

### User Story 3 - 卫生机制保证"不再出现没落点的日志"（Priority: P3）

引入防回归机制：以后任何人（人或 AI）新增代码时，若写出"日志本子没接上"或"出错却什么都不留"的代码，仓库自检直接拦下并报错，从源头杜绝再次出现"白写日志"。

**Why this priority**: 用户要求的是"永恒的白箱"——不是修完这一轮就完事。接线是一次性的，机制是长期的。没有这道机制，下一轮重构随时可能再断。

**Independent Test**: 可以独立验证：在代码里故意新增一处"使用裸日志"或"捕获异常但不留痕"的写法，跑仓库自检必须失败；修复后再跑必须通过。

**Acceptance Scenarios**:

1. **Given** 仓库自检已启用新规则，**When** 我新增一处"直接用系统日志本子"的代码，**Then** 自检失败并指明文件与位置。
2. **Given** 仓库自检已启用新规则，**When** 我新增一处"捕获异常但既不记录、也不抛出、也不显式返回"的代码，**Then** 自检失败并指明文件与位置。
3. **Given** 存量不合规处已全部整改，**When** 运行全量仓库自检，**Then** 通过且无白名单豁免。

---

### Edge Cases

- 两个进程（主进程与子进程）同时写同一个日志文件，日志轮转（文件满 5MB 自动滚动）时会不会互相干扰、丢行？
- 日志文件被外部删除或设为只读时，程序不能因此崩溃，且要有可感知的降级（如自动重建或明确告警）。
- 子进程刚启动、日志尚未就绪就出错时，这条错误本身不能被吞掉。
- 用户数据目录不可写/被占用时，日志要有明确落点或明确失败提示，不能"静默无记录"。
- 测试模式（自动化测试跑动）不应把测试噪音灌进正式日志文件。
- 长任务输出超过存储上限时，日志要截断但保留尾部，不能整体丢弃。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 主进程所有业务模块的日志必须统一走项目封装的日志通道，禁止直接使用系统级日志本子（`logging.getLogger`）记账。
- **FR-002**: 抓取脚本子进程必须初始化日志并写入与主进程同一个日志文件，使脚本侧记录（含低级别的详情记录）都能被查询到。
- **FR-003**: 抓取脚本子进程的现场输出（详情页访问、登录检查、风控判断等）必须被持久化，事后可在日志查看页查询，且带任务编号；风控判断需覆盖"首次判定与重试后最终结论"全过程；智联平台的风险信号（验证码/限流/登录失效等）与 BOSS 同规则留痕。
- **FR-004**: 任何进程、任何启动入口（源码模式、桌面版、脚本子进程、命令行直跑）只要使用日志，就必须自动确保日志有落点；不允许"用了日志但没接上账本"的静默状态。
- **FR-005**: 运行时审计在日志尚未就绪时不得无声跳过，必须自动就绪或至少留下可感知的降级标记。
- **FR-006**: 仓库卫生自检必须拦截两类回归：直接使用系统日志本子；捕获异常后既不记录、也不抛出、也不显式返回。
- **FR-007**: 现存"引用了未定义日志对象"的隐患必须移除，确保日志代码本身不会成为崩溃来源。
- **FR-008**: AI 调用失败的原因必须能在日志中查到（原始响应原文有专门记录通道，属设计内，保留；失败原因另须有记录）。
- **FR-009**: 任务级未预期异常（外层兜底捕获）必须留痕到主日志，含异常类型与堆栈；不得只写任务数据库日志而跳过主日志。
- **FR-010**: 抓取子进程非 0 退出时，其现场原文（结构化失败行、异常类型与消息、stderr 尾部）必须写入主日志 `career-scout.log`；失败信息只进数据库任务事件或只留对外友好文案，均视为未留痕。
- **FR-011**: 抓取脚本主入口必须兜底"未识别异常"：产生结构化失败行（`code=source_unknown_error`）并输出完整堆栈，禁止裸 traceback 静默退出后由主进程按退出码猜测原因。

### Key Entities

本功能不引入新的业务数据实体；涉及的既有对象为：日志记录（含时间、级别、模块、任务编号、内容）与日志文件（含滚动备份）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 跑一次真实小抓取后，脚本子进程的现场日志出现在日志查看页，且每条带任务编号与时间戳。
- **SC-002**: 人为制造一次失败（含"未识别异常"路径），日志中能查到异常类型、发生阶段、任务编号三要素，而非仅一句"抓取执行失败"。
- **SC-003**: 仓库自检在现有全绿基础上继续通过；故意加入违规写法时自检必须失败并指出位置。
- **SC-004**: 全部既有日志通道（主进程、子进程、审计、AI 失败原因）在日志查看页均可查询，不存在"记录了但查不到"的通道。
- **SC-005**: 日志文件轮转、删除、只读等异常场景下程序不崩溃，且行为可感知。
- **SC-006**: 抓取子进程失败后，日志查看页能查到子进程 stderr 的现场原文（异常类型、消息与关键上下文），而非只有对外友好文案或错误码。

## Verification Scope *(mandatory)*

- 功能/重构/拆分交付：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求“全量/全部测试/完整验证”时，收口任务才执行全量测试。

## Assumptions

- 子进程日志接入方案已由用户确认：子进程直接初始化日志并写同一个主日志文件（做法甲）；对"两个进程写同一文件"的轮转竞态采取防护措施。
- 本轮只做白箱（接线 + 卫生机制），不触碰抓取阻断（验证码/限流/登录失效的停下说人话、断点续跑）逻辑；那是后续单独任务。
- AI 原始响应日志（`ai_raw.log`）独立于主日志属既有设计，保留；本轮只补"AI 失败原因"的记录通道。
- 存量不合规日志写法优先一次性整改完毕，再启用硬性自检规则，避免依赖白名单豁免。
- 卫生自检的"不留痕"判定以现有"静默吞异常"检查为基础扩展，规则需兼顾可执行性与低误伤，具体边界在 Plan 阶段明确。

## 审查返修记录（2026-09-01）

实现完成后做了一轮对照用户原话的验收审查，发现下列缺口并已修复。FR-010、FR-011 与 SC-006 为本次补写的验收条款——用户原话本已覆盖这些要求，此处只是落成可逐条打勾的形式，避免下次验收被"功能清单没写"绕过。

| 缺口 | 原有依据 | 修复 |
| --- | --- | --- |
| 抓取子进程失败只有对外文案与错误码进主日志，现场原文只进数据库任务事件 | 用户原话（补为 FR-010 / SC-006） | 列表、单条详情、批量详情三条子进程出口均补主日志留痕，含 stderr 尾部 |
| 脚本主入口未兜底未识别异常，裸 traceback 退出后靠退出码猜测原因 | 用户原话（补为 FR-011） | 补通用兜底：结构化失败行 + 完整堆栈 |
| 子进程现场日志缺任务编号 | SC-001 已要求，实现未做到 | 子进程 env 注入任务编号，懒初始化时恢复到日志上下文 |
| 卫生自检漏拦「先导入再直接调用」的裸日志写法 | T019 已要求，实现未覆盖 | AST 检查同时匹配属性调用与直接调用两种形式 |
| AI 失败留痕只覆盖"重试耗尽"一条路径 | FR-008 覆盖不全 | 补网络失败、鉴权失败、服务端拒绝、响应截断、响应无法解析五条路径 |

拆分（用户直接授权，未单独立 Spec；等价搬运 + 全量回归验证）：

- `webui/source_boss_cdp_detail.py` 由 800 行（抵宪法红线）拆至 567 行：in-process 执行专用逻辑（stdout 收集、argv 翻译、库式调用执行）整体等价搬运至新文件 `webui/source_boss_cdp_inprocess.py`（`_BossCdpInProcessMixin`，264 行）。对外接口与行为不变，in-process 聚焦测试 40 个与后端全量 2782 个通过。
- 拆出空间后，补上此前受红线约束未加的批量详情子进程整体退出留痕（stage=detail_batch，与列表/单详情一致）。

测试噪音治理（2026-09-01，第三件收尾）：

- 根因：测试 spawn 的子进程不识别测试上下文（`_is_test_context` 只看主进程 sys.modules），日志懒初始化落到正式目录。
- 修复（测试侧喂环境，不污染生产语义）：
  1. `webui/logging_setup.py`：测试上下文且未显式指定目录时，`configure_logging` 一律落到系统临时目录（覆盖测试进程内启动应用的路径）；
  2. `webui/source_boss_cdp.py`：测试上下文构造抓取子进程时，env 注入 `CAREER_SCOUT_LOG_DIR=临时目录`（覆盖抓取子进程路径）；
  3. `tests/chrome_setup/harness.py`：顶层设置 `CAREER_SCOUT_LOG_DIR=临时目录`（覆盖测试 spawn 的 CLI 子进程）。
- 验证：`chrome_setup` 单跑零新增；后端全量 2783 个通过，期间正式日志零新增；日志正确落在系统临时目录。

未处理项（需另行安排）：

- 前端 `webui/src/` 下"六类→七类"文案改动混入 033 的实现改动，与本功能无关，未在本轮处理。
- Windows 下"日志文件被外部删除后自动重建"仍无自动化覆盖（该用例仅在非 Windows 平台执行）。
- 抓取阶段业务失败（非 Python 异常）不经过任务兜底分支，其留痕依赖本轮新增的子进程出口日志，已在测试中覆盖，但尚无真实运行证据。
