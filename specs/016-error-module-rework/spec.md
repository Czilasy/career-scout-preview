# Feature Specification: 报错模块整体修复与优化

**Feature Branch**: `016-error-module-rework`

**Created**: 2026-08-22

**Status**: Draft

**Input**: User description: "报错模块整体修复与优化：硬阻断就停、软失败记录继续、错误码统一一套、冷却功能删除、受限判定分层、进度条无跳变（B069 治理）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 硬阻断正确停止，软失败不再误报 (Priority: P1)

用户跑抓取任务时，系统只在流程真的进行不下去时才停：浏览器崩溃、调试连接断开、登录失效、确认受限四种情况。任务暂停时断点和已抓内容全部保留，停止原因如实写明（是验证码就写验证码，是操作频繁就写操作频繁）并附一句建议动作。除此之外的一切失败——单次访问拦截、页面结构异常、空响应、正常空结果——都不暂停任务，也绝不把账号标成"受限"、绝不提示"限流/账号受限"。判定遵循实锤标准：验证码/滑块页面本身、明确限流提示页、平台明确"请求受限"信号、连续两次（含复探）访问拦截才算确认受限；单次异常永远不定罪。

**Why this priority**: 这是 B069 的核心痛点——误报把没被封的账号标成受限并锁死任务；同时真受限时用户需要明确知道发生了什么。这一条直接决定用户对系统报错的信任。

**Independent Test**: 用构造的探测/抓取样本回归：正常空结果、单次 403、正文含"滑块/验证码"词汇的任务运行后，账号无任何受限标记、任务无"受限"提示；验证码页与连续两次拦截样本正确触发暂停且文案如实。

**Acceptance Scenarios**:

1. **Given** 任务运行中单次请求返回 403，**When** 系统复探一次后正常，**Then** 任务继续运行，账号无受限标记，不出现"限流/账号受限"提示。
2. **Given** 登录探测返回正常已登录的岗位数据（岗位描述里含"滑块""验证码"字样），**When** 探测完成，**Then** 判定为已登录，岗位内容词汇不影响判定结果。
3. **Given** 任务运行中出现真实验证码页面，**When** 系统识别，**Then** 任务暂停、断点与已抓内容保留、停止原因如实写"触发验证码"并给出建议动作。
4. **Given** 连续翻页出现空白，**When** 空白页属于正常无结果或翻完，**Then** 正常停止翻页；**When** 空白页结构异常，**Then** 先原地重试该页一次，仍异常才停止翻页并如实报告"原因无法确认"，绝不报告"大概率被风控限制"。
5. **Given** 登录状态探测一次受限，**When** 复探通过，**Then** 按正常继续；只有连续两次（含复探）拦截才判确认受限。

### User Story 2 - 软失败记录继续，全程可查 (Priority: P1)

凡是不会让流程进行不下去的失败（单次异常、无法确认、组合级失败），任务照常继续跑下一个组合，已抓内容照常保存。每一次软失败都按组合落库留痕：失败原因码、可读原因、出现时间。用户在任务详情里能看到哪些组合失败了、为什么失败。只有所有组合都因"无法确认"失败且一无所获时，任务才以失败收场，文案如实说"多组搜索均无法确认状态，请到自动化浏览器检查后重试"。

**Why this priority**: "软就记录继续"是用户原始需求的后半句；留痕让用户事后能核查每一次失败，而不是只在进度条上一闪而过。

**Independent Test**: 构造部分组合软失败的任务运行，断言任务不暂停、其他组合正常完成、失败组合的记录（原因码/可读原因/时间）落库且任务详情接口可查。

**Acceptance Scenarios**:

1. **Given** 10 个搜索组合中 3 个因页面异常软失败，**When** 任务继续，**Then** 其余 7 个组合正常完成，任务整体成功收尾，3 条失败记录落库可在任务详情查看。
2. **Given** 所有组合均软失败且无任何抓取结果，**When** 任务结束，**Then** 任务以失败收场，文案如实说明"均无法确认状态"并建议到自动化浏览器检查。
3. **Given** 软失败发生，**When** 用户打开任务详情，**Then** 能看到每个失败组合的原因码、可读原因与出现时间。

### User Story 3 - 全系统一套错误码 (Priority: P1)

抓取（BOSS）、抓取（智联）、AI 调用三个域共用同一套错误码注册表：同一个语义只有一个码、只有一份用户文案；哪些码属于"硬阻断"、哪些"可重试"由注册表里的标记统一推导，不再手工维护重复清单。BOSS 与智联不再各自维护一份风控关键词表，判定口径收敛到单一来源。历史任务记录里的旧码不迁移数据库，展示时按别名兼容解析。错误分类以抓取脚本输出的结构化失败信号为唯一权威来源，不再对输出全文做关键词扫描定类。

**Why this priority**: 双套码 + 三处关键词表是"请求受限漏判、文案漂移、IP 风控误标"的根源；统一是"正确的逻辑"的地基。

**Independent Test**: 一致性测试断言注册表内无重复语义码、硬阻断集合与注册表标记完全一致；历史记录展示旧码时经别名解析出正确文案；分类测试断言只有结构化失败行决定错误类型。

**Acceptance Scenarios**:

1. **Given** 任一错误发生（BOSS/智联/AI），**When** 错误码产生并展示，**Then** 同一语义在任务状态、任务详情、环境检查里显示同一个码与同一份文案。
2. **Given** 历史任务记录里存有旧版错误码，**When** 用户查看历史结果，**Then** 展示经别名解析的正确可读文案，不出现原始英文码直出或"未知错误"误报。
3. **Given** 抓取脚本失败退出，**When** 后端分类错误，**Then** 只依据脚本输出的结构化失败信号定类；输出全文中的岗位标题、薪资、正文词汇不影响分类结果。
4. **Given** 平台返回明确的"请求受限"结构化信号，**When** 后端分类，**Then** 正确映射为受限类错误码，不再漏判成"未知错误"。

### User Story 4 - 冷却功能彻底移除 (Priority: P2)

风控冷却功能整体删除：不再记录冷却、任务提交不再被冷却拦截、"解除冷却"接口与按钮移除、环境检查面板不再显示"建议等待至 XX 点"。误报的最重后果从"锁账号 4 小时"降为"这一次任务暂停"。账号是否碰到风控，用户自己到自动化浏览器里看。

**Why this priority**: 冷却时间预测总是不准，拦截价值为负；删除后误报不再有持久惩罚。

**Independent Test**: 全库检索无冷却相关代码残留；提交任务路径无冷却检查；前端无冷却展示与解除入口；相关测试全部移除或改写。

**Acceptance Scenarios**:

1. **Given** 系统检测到确认受限并暂停任务，**When** 用户查看账号状态与提交入口，**Then** 没有任何冷却倒计时、"建议等待"提示或解除冷却按钮。
2. **Given** 此前存在冷却记录文件，**When** 新版本运行，**Then** 不再读取、不再写入该数据。

---

### User Story 5 - 登录状态缓存只存事实 (Priority: P2)

登录状态缓存只存两个事实态："已登录"与"未登录"。命中"已登录"跳过探测省时间；命中"未登录"提示去登录。"受限"不再作为可缓存状态持久化——受限判定只在当次任务内实时生效，不产生任何跨任务的假拦截。

**Why this priority**: 15 分钟的受限缓存曾是"解除后仍被拦"的直接原因；删掉它之后，受限判定永远反映当下。

**Independent Test**: 探测到受限后断言缓存中无受限态写入；任务提交与续跑前置检查不再因缓存受限态被拦截。

**Acceptance Scenarios**:

1. **Given** 一次任务中探测到确认受限，**When** 任务暂停后用户稍后重新提交，**Then** 系统当场重新探测，不沿用任何旧受限状态。
2. **Given** 缓存中存有"已登录"，**When** 下次任务开始，**Then** 跳过登录探测直接就绪。

---

### User Story 6 - 中断后进度无跳变 (Priority: P2)

暂停续跑、报错续跑、刷新页面恢复三种路径下，列表抓取、JD 抓取、AI 筛选三条进度线都必须从持久化断点位置直接起步：恢复瞬间显示的就是断点值，不出现"从 0 开始再猛跳到正确位置"。

**Why this priority**: 进度跳变让用户以为任务从头重跑，直接破坏对续跑功能的信任。

**Independent Test**: 自动化测试对 3 条进度线 × 3 种恢复路径断言恢复后的首个进度值等于持久断点值，不出现 0 起步。

**Acceptance Scenarios**:

1. **Given** 任务在 60% 处暂停，**When** 用户点继续，**Then** 进度条从 60% 附近直接起步并继续推进，无归零。
2. **Given** 任务报错暂停后用户刷新页面，**When** 页面恢复，**Then** 各进度线立即显示断点位置。
3. **Given** JD 抓取进行到一半时续跑，**When** 恢复执行，**Then** 已抓 JD 数量计数延续，不从头计数。

### Edge Cases

- 探测一次受限、复探通过：按正常继续，不留任何受限痕迹。
- 硬阻断发生在 JD 批次中途：已抓到的 JD 与列表结果全部保留，续跑从断点继续。
- 历史结果页展示旧错误码：别名解析出正确文案；无法解析的旧码显示明确兜底文案，不静默。
- 本机遗留旧的冷却数据文件：新版本不读不写，允许残留不报错。
- 所有组合因登录失效被跳过：保留现有中性提示文案，不冒充风控。
- AI 侧错误：本次只并码统一注册表，AI 的重试与退避策略行为不变。
- 结构化失败信号缺失（旧版脚本产物/异常路径）：分类兜底到"暂时无法判断"，不定罪。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须只在四种硬阻断时暂停任务：浏览器不可用、调试连接断开、登录失效、确认受限；暂停时必须保留断点与已抓结果，并显示具体原因与建议动作。
- **FR-002**: "确认受限"必须且只能由以下实锤信号判定：验证码/滑块页面本身、明确限流提示页、平台明确的"请求受限"结构化信号、连续两次（含复探）的访问拦截；单次异常不得判为确认受限。
- **FR-003**: 暂时无法判断类信号（单次拦截、平台环境异常码、空响应、结构异常、连接抖动）不得标记账号受限、不得提示"限流/账号受限"，必须以中性文案呈现。
- **FR-004**: 登录探测必须先判定"是否正常已登录返回"，是则直接通过；风控关键词判定只对异常响应生效，正常返回中的岗位内容词汇不得影响判定。
- **FR-005**: 连续空页只能作为停止翻页的条件，不得作为风控/限流的定性理由；结构异常的空页必须先原地重试一次；"大概率被风控限制"类模糊定性文案必须移除。
- **FR-006**: 错误分类必须以抓取脚本输出的结构化失败信号为唯一权威来源；输出全文关键词扫描不得作为主分类手段（仅允许高置信短语兜底）。
- **FR-007**: 软失败不得暂停任务，必须按组合落库留痕（失败原因码、可读原因、出现时间），并在任务详情中可查。
- **FR-008**: 所有组合均软失败且无任何结果时，任务必须以失败收场并如实说明"无法确认状态"。
- **FR-009**: 全系统必须只维护一套错误码注册表（BOSS 抓取、智联抓取、AI 三域共用）：同一语义同一码同一文案；硬阻断集合必须由注册表标记自动推导；两平台的风控判定口径必须收敛到单一来源；历史记录旧码以别名兼容展示，不迁移数据库。
- **FR-010**: 冷却功能必须整体移除：无冷却记录写入、无提交拦截、无相关接口与界面。
- **FR-011**: 登录状态缓存必须只存"已登录/未登录"两个事实态；受限状态不得持久化、不得作为跨任务拦截依据。
- **FR-012**: 中断后继续（暂停续跑、报错续跑、刷新恢复）时，三条进度线（列表、JD 抓取、AI 筛选）必须从持久断点直接起步，不得归零后跳变。
- **FR-013**: AI 侧错误码并入统一注册表，但 AI 重试与退避策略行为必须保持不变。

### Key Entities *(include if feature involves data)*

- **错误码注册表**: 全系统唯一；每个码含语义类别、是否硬阻断、是否可重试、用户文案、恢复建议；含旧码别名。
- **组合失败记录**: 组合键、失败原因码、可读原因、出现时间；随任务持久化，任务详情可查。
- **登录状态缓存**: 账号 × 平台；仅"已登录/未登录"两态。
- **任务断点**: 列表页级、JD 批次级、AI 筛选进度的持久化位置，恢复时作为进度起点。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 构造回归样本下（正常空结果、单次拦截、正文含风控词汇、登录探测含敏感词的正常返回），100% 不产生"账号受限"标记与"限流/账号受限"提示。
- **SC-002**: 确认受限样本（验证码页、明确限流页、平台请求受限信号、连续两次拦截）100% 触发任务暂停，原因文案与建议动作正确。
- **SC-003**: 软失败 100% 落库且任务详情可查，任务不因软失败中断。
- **SC-004**: 注册表一致性测试通过：无重复语义码，硬阻断集合与注册表标记 100% 一致，平台"请求受限"信号映射正确。
- **SC-005**: 冷却相关代码、接口、界面、测试残留为 0。
- **SC-006**: 3 条进度线 × 3 种恢复路径的自动化断言全部通过：恢复后首个进度值等于持久断点值。

## Verification Scope *(mandatory)*

- 功能/重构/拆分交付：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。

## Assumptions

- BOSS/智联平台的风控页面与信号特征以 2026-08 调查样本为准；实锤分档不追求覆盖未来所有平台变体，出现新样本时按同一分档原则补充。
- 历史任务数据不迁移，靠别名兼容展示。
- 前端改动完成后需要重建 dist 并一并提交（pre-push 钩子校验 dist 同步）。
- 本 Spec 不改变 AI 重试/退避行为，不改变抓取速度配置，不重构与报错无关的模块。
- 超大文件（`webui/app.py`、`webui/source.py`、`webui/pipeline_exec.py`、`scripts/boss_cdp_raw.py`）只允许修改既有行为与删除代码；新增逻辑落入既有小模块（错误注册表、纯分类信号模块）或新文件。
