## 用户场景与测试

### 用户故事 1 - AI 空响应自动重试，不再直接报错或转待确认（优先级：P1）

AI 端点间歇性返回 HTTP 200 但流式内容为空时，系统第一次直接抛 `invalid_response`：简历分析立即 502 弹「AI 返回了无法解析的内容」，精筛单岗位重试 1 次仍失败后转「待人工确认」。本故事把「空 body」识别为可重试传输失败，在统一调用层自动重试，重试成功用户无感；连续重试仍空才报错。

**优先原因**：这是当前最痛的 Bug，已有真实数据佐证（8/14~8/17 共 78 条 `original_length=0`，占同期调用 6.7%），且 8/17 两次简历分析因此失败。

**独立测试**：mocked 端点首次 200 空 body、二次返回正常 JSON，断言 `call_ai` 返回正常结果且重试计数为 1；两次都空时断言最终抛错且带 `empty_response` 诊断。

**验收场景**：

1. **假如** AI 端点返回 200 但内容为空，**当** 本轮调用进入重试循环，**那么** 自动重试（默认最多 2 次），不立即抛 `invalid_response`。
2. **假如** 重试后拿到正常 JSON，**当** 调用返回，**那么** 调用方（简历分析/粗筛/精筛）正常继续，用户无感。
3. **假如** 连续多次空响应耗尽重试次数，**当** 最终失败，**那么** 仍抛 `invalid_response`（带 `failure_phase=empty_response` 诊断），行为与现状一致。
4. **假如** 端点返回 200 且内容是 JSON 解析失败的垃圾文本，**当** 调用失败，**那么** 不因本故事重试（json_decode 型 invalid 不重试），保持现状。
5. **假如** 空响应发生在任意环节（简历分析/粗筛/精筛/其它），**当** 记录日志，**那么** `ai_raw.log` 每条记录带操作类型字段，可区分环节。

### 用户故事 2 - 移除代码写死的默认偏好，改由简历事实与宽松匹配（优先级：P1）

`match_jds` 第四层把「只找全职、不要实习、默认双休、不接受996」当作默认偏好硬编码。本故事删除该层，把相关维度收口为第三层 `profile_facts` 的显式字段；简历分析阶段新增字段并给 AI 填写说明书；主观偏好未体现时取「最大接受度」默认，匹配宁宽勿漏，拿不准的进匹配 + caveats，不自动判不匹配。

**优先原因**：代码写死的默认偏好会在简历未体现时误杀匹配岗位，且与用户可编辑画像语义重叠；收口到显式字段后，匹配放开、交由用户确认。

**独立测试**：构造「简历未体现 week_off」的 profile_facts，JD 明确单休/大小周，断言岗位进匹配且 caveats 含提醒；JD 明确「统招本科」而候选人 degree_type 未体现时断言进匹配 + caveats；高危 flag 命中仍断言 not_match。

**验收场景**：

1. **假如** 简历分析完成，**当** 输出 profile_facts，**那么** 新字段 `degree_type` / `week_off` / `overtime` 出现且值合法；简历未体现时按说明书默认（week_off=单休、overtime=能够加班、job_type=不限雇佣形式）或「未体现」。
2. **假如** `match_jds` 收到 profile_facts，**当** 构建提示词，**那么** 第四层「默认偏好」整段移除，不再出现「只找全职/不接受996」等硬默认措辞。
3. **假如** JD 明确要求而候选人维度未确认（如 JD 写「统招本科」、候选人 degree_type 未体现），**当** 判定，**那么** 该岗位进匹配 + caveats 注明需用户确认，不直接判不匹配。
4. **假如** JD 明确兼职且候选人 job_type 未体现（默认不限雇佣形式），**当** 判定，**那么** 兼职可进匹配并留 caveats，不再默认判不匹配（与旧行为相反，由用户确认取舍）。
5. **假如** 命中骗局/风控高危 flag，**当** 判定，**那么** 照常强制 not_match，宽松原则不覆盖安全例外。
6. **假如** 用户勾选的六类硬条件（薪资/经验/学历/规模/融资/行业）真冲突，**当** 判定，**那么** 照常 not_match，宽松原则不推翻用户硬约束。

### 用户故事 3 - AI 判定卡片「判断说明 + 软性要求」桌面端左右双栏（优先级：P2）

详情面板 AI 判定卡片下方红框区域，当前「AI 判断说明」与「软性要求提醒」上下排列。改为桌面向左右两栏、各占 50% 宽度；移动端保持现状上下排列。只改该红框区域排版，不动标题行、判定标签、颜色语义与数据结构。

**优先原因**：纯 UI 优化，不改变行为；可与前两个故事独立交付。

**独立测试**：组件测试 mock 判定数据，桌面视口断言两栏并排（宽度 50/50、字号一致），移动视口断言仍为上下排列。

**验收场景**：

1. **假如** 桌面端打开岗位详情且 AI 判定卡非空，**当** 查看红框区域，**那么** 左栏「AI 判断说明」、右栏「软性要求提醒」左右排列，各占 50% 宽度。
2. **假如** 桌面端两栏内容较长，**当** 排版，**那么** 允许自然换行，不截断、不横向滚动。
3. **假如** 移动端打开岗位详情，**当** 查看，**那么** 布局保持现状上下排列，不受双栏影响。
4. **假如** 两栏字号、颜色检查，**那么** 字号一致且整体缩小；右栏保留黄色底块/黄字样式，左栏保留原说明文字色。

## 边界情况

- **空响应 vs JSON 垃圾**：只有 HTTP 200 + 流式内容为空才按可重试处理；200 + 内容非空但 JSON 解析失败不重试。
- **重试上限**：默认最多 2 次（含首次=3 次尝试），总等待受现有 60s 上限约束，不新增无限重试。
- **tuning 路径**：`AI_TRANSPORT_RETRY_CODES` 加入空响应码后，manifest 可覆盖其重试次数；没配置时走默认 2 次。
- **旧数据**：不迁移历史 `profile_facts`；旧轮次缺新字段时视为「未体现」，走宽松匹配语义。
- **安全例外**：骗局/风控高危 flag 不因宽松而放开，照常硬不匹配。
- **六类硬条件**：用户勾选的薪资/经验/学历/规模/融资/行业仍是最高优先级硬约束，宽松原则只作用于未选择维度。
- **移动端**：B058 双栏只在桌面端生效；移动端保持上下排列。
- **运行中热改**：本故事不涉及速度字段热改，无运行中配置变更。

## 需求

### 功能需求

- **FR-001**：`call_ai` 对 HTTP 200 + 空流式内容（`failure_phase=empty_response`）按可重试错误处理，默认最多重试 2 次。
- **FR-002**：空响应重试只针对 `empty_response` 型 invalid；json_decode 型 invalid 不重试。
- **FR-003**：`AI_TRANSPORT_RETRY_CODES` 加入空响应错误码，manifest 可覆盖；默认策略缺省时使用 2 次重试。
- **FR-004**：`ai_raw.log` 记录增加操作类型字段（如 `op=resume|screen|fine|...`），correlation_id 仍为 run 级。
- **FR-005**：第三层 `profile_facts` 契约扩展字段：`degree_type`、`week_off`、`overtime`（保留 `core_skills`/`projects`/`job_type`/`degree`/`languages`，`languages` 从 `core_skills` 拆出），可选 `age`/`gender`。
- **FR-006**：简历分析提示词增加「字段填写说明书」（格式：字段：段落描述），指导 AI 从简历找信号、判断写法、可否为空；`degree_type` 只按「统招 / 非统招」两值填写，默认统招，仅出现明确非统招标志（自考/成考/函授/夜校等）才填非统招；专升本属于统招范畴，毕业时间/双校信息不作为非统招依据。
- **FR-007**：客观事实字段按简历证据严格推断，**识别不到具体值时留空/「未体现」，不推断、不编造**：
  - `core_skills`：简历明确列出的技能，最多 10 个；无明确技能列表 → 空数组。
  - `projects`：简历明确的项目/工作经历，name 必填、role/stack/summary 有则填；无 → 空数组。
  - `degree`：简历明确写出的最高学历层次（如 本科）；没写明 → 不填（未体现）。
  - `degree_type`：只区分统招 / 非统招（自考/成考/函授/夜校等）。**默认「统招」**；仅当简历明确出现非统招标志（自考/成考/函授/夜校等）时填「非统招」。专升本（含先专后本）属于统招范畴，不算非统招信号；毕业时间仅两年不构成非统招依据。此默认是事实认定，不是「匹配放行兜底」。
  - `languages`：简历明确的外语等级与证书（从 `core_skills` 拆出）；无 → 空数组。
- **FR-008**：主观偏好字段（`week_off`/`overtime`/`job_type`）简历未体现时默认取「最大接受度」：`week_off`=单休、`overtime`=能够加班、`job_type`=不限雇佣形式。
- **FR-009**：`match_jds` 提示词删除第四层「代码写死的默认偏好」整段，原语义由第三层 profile_facts + 默认值承担。
- **FR-010**：匹配宽松总原则：拿不准的维度 → 进匹配 + caveats 提醒，不进不匹配；只有用户勾选六类硬条件真冲突才判不匹配。
- **FR-011**：骗局/风控高危 flag 仍强制 not_match，不因宽松原则放开。
- **FR-012**：`_validate_profile_facts` 与 `_build_profile_facts_description` 支持新字段；旧字段缺省按「未体现」处理。
- **FR-013**：桌面端 AI 判定卡片下方红框区域左右两栏、各 50% 宽度；两栏字号一致且整体缩小。
- **FR-014**：移动端保持上下排列，不受双栏影响。
- **FR-015**：B058 只改红框区域排版，不动标题行与「AI 判定 / 匹配」标签。

### 关键实体

- **AI 调用记录**：correlation_id（run 级）、attempt_index、operation 类型、original_length、body、重试次数。存 `ai_raw.log`。
- **画像事实 profile_facts**：core_skills[] / projects[]（name/role/stack/summary）/ job_type / degree / degree_type / languages[] / week_off / overtime（可选 age/gender）。存 screening_runs JSON 快照，不新增列。
- **重试策略**：按错误码的 max_retries / backoff / jitter / total_wait，manifest 可覆盖。
- **AI 判定卡片区块**：verdict-reason（AI 判断说明）与 caveats-list（软性要求提醒）两个 UI 块；桌面 vw 级双栏类。
- **硬条件 criteria**：薪资/经验/学历/规模/融资/行业六类已选字段，宽松原则不覆盖。

## 假设

- `webui/ai.py`（2265 行）与 `webui/app.py`（9482 行）已超宪法上限：本故事的新逻辑、新提示词文本与画像事实校验改造进入新模块，`ai.py` 只做最小接线；不把大段文字塞回 `ai.py`。
