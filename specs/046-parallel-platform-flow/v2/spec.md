# Feature Specification: 多平台主流程分轨合流与统一条件映射（B096 V2）

**Feature Branch**: `codex/feature/b096-parallel-platform-flow`
**Created**: 2026-09-27
**Status**: 用户已确认并经委托自审冻结；Plan 与 Tasks 已完成，尚未实施
**Supersedes**: `../v1/spec.md`
**Input**: 2026-09-27 对 V1 实际体验问题的只读审查，以及随后逐条完成的 V2 边界质询。

## 版本定位与继承边界

- V2 是同一业务主体上的增量修订，不推倒 V1，也不重做已经完成的后台并行、账号与浏览器隔离、平台独立暂停/继续/停止、失败处理、历史、归档和结果来源能力。
- V1 保持只读。V2 只修正已确认的交互错误、页面状态接线错误和缺失的“全部”统一条件映射。
- V1 中未被 V2 明确替换的需求继续有效；若两版冲突，以 V2 为准。
- 本轮最高目标不是完成若干局部控件，而是让用户从“全部”入口真实跑通 01 → 02 → 03 → 04，并在两条平台线速度不同、刷新、返回旧页面和部分失败时仍能完成主流程。

## A 组：用户原话与已确认边界

- 核心模型是“分轨合流”：BOSS 与智联流程分开推进，在相同页面中按到达阶段合流，任何平台不得等待另一平台。
- 已有成熟逻辑、组件和交互必须优先复用；并行只增加按平台保存状态和在同一页面合流的能力，不得另起炉灶重做原进度条或结果页。
- 02 页继续保留各平台抓取进度和已完成状态；03 页只加入已经进入 AI 阶段的平台；后来平台进入同一阶段时追加在已有进度条下方。
- 第一个平台完成抓取后，页面自动进入 03；第一个平台完成 AI 后，页面自动进入 04。落后平台继续在后台追赶。
- 用户主动返回旧页面后，后续平台完成只更新状态并通过灵动岛提示，不再抢走用户当前页面。
- 第二个平台结果完成后，04 原地加入新结果，不整页重载；保留当前筛选、排序、滚动位置和已展开岗位，并通过灵动岛提示一次。
- 刷新后恢复用户刷新前所在的已解锁页面、已解锁入口及两条平台线状态；刷新本身不触发自动跳页。
- “全部”使用中性黑灰主题；BOSS、智联继续使用各自主题。深色模式使用保证可读性的中性白灰，不继承任一平台品牌色。
- 七类条件不再要求额外“已确认”复选框。当前值即提交值，用户修改后直接生效，点击一次主启动按钮就是最终确认。
- “全部”只展示两平台共同的六类统一字段：薪资、经验、学历、行业、公司规模、招聘者活跃；BOSS 的融资阶段和智联的公司性质只在各自平台页展示并由用户手动选择。
- 统一条件单向、即时映射到 BOSS 和智联；平台页的单独修改不反向改变“全部”。用户再次修改“全部”的某个共同字段时，重新映射并覆盖两个平台该字段的旧选择，不弹确认框。
- 映射采用人工维护的明确表；制定映射时“不漏岗位优先”，用覆盖目标语义所需的最少平台选项，不在运行时临时猜测。
- 简历分析继续为“全部”的六个共同字段提供初始建议；跳过简历时六类默认不限。平台专属字段不由“全部”自动选择。
- 常用配置和历史快照必须保存统一条件、两个平台最终实际条件、用户平台微调与平台专属字段；恢复时按当时值恢复，不按后来映射重新计算。
- 真实应用主流程是最终验收门禁，不能再用单元测试、临时数据库、接口测试或跨层冒烟替代。

## B 组：AI 补充与用户授权复核结论

- `contracts/filter-mapping.md` 根据当前 BOSS、智联 schema 整理了完整映射。用户授权 AI 自审后继续；自审删除了缺少可靠共同语义的行业近似项，并将保留项收窄为可明确解释的统一语义，现作为 V2 冻结契约。
- 映射表采用用户可见标签表达业务语义；稳定代码、存储字段和版本号属于后续 Plan 的实现选择，不在本规格中替用户新增产品字段。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从“全部”直接确定两平台条件 (Priority: P1)

用户默认选择“全部”，在现有“全部 / BOSS / 智联”切换结构中看到六类统一条件。简历分析给出统一建议，用户可以直接使用或修改；统一值立即映射到两个平台。用户如需平台差异，可切换到平台页微调或设置平台专属条件，最后只点击一次主按钮开始。

**Why this priority**: 用户需要减少重复点击，同时必须清楚实际提交给两个平台的条件。

**Independent Test**: 修改“全部”的任一共同字段，切换 BOSS、智联确认映射结果；再单独修改一个平台，确认不反向改变“全部”；重新修改“全部”的同一字段，确认两个平台该字段按新映射覆盖；全程没有额外确认复选框。

**Acceptance Scenarios**:

1. **Given** 两个平台均可新建任务，**When** 用户打开新一轮，**Then** “全部”位于 BOSS、智联之前并默认选中，页面使用中性黑灰主题。
2. **Given** 已完成简历分析，**When** 用户打开“全部”条件页，**Then** 六类共同字段已得到统一建议并立即映射到两个平台；融资阶段和公司性质没有被“全部”自动选择。
3. **Given** 用户跳过简历，**When** 进入“全部”条件页，**Then** 六类共同字段默认为不限，两平台共同字段也不增加限制。
4. **Given** 用户修改统一条件，**When** 切换到 BOSS 或智联，**Then** 能立即看到人工映射表对应的实际选择；无需确认每个平台，也没有“我已确认”复选框或确认状态。
5. **Given** 用户在平台页微调共同字段，**When** 返回“全部”，**Then** 统一条件保持不变；再次修改“全部”的同一字段时，该字段的平台微调被新映射覆盖，其他字段与平台专属字段保持不变。
6. **Given** 用户保存当前条件为常用配置，**When** 再次使用该配置，**Then** 统一条件、两平台最终选择、平台微调及平台专属字段均按保存时原样恢复。
7. **Given** 用户完成条件调整，**When** 点击主启动按钮，**Then** 该点击同时承担最终确认和启动，不要求任何第二次确认动作。

### User Story 2 - 领先平台推动页面、落后平台继续追赶 (Priority: P1)

用户启动“全部”后，BOSS 与智联独立抓取和筛选。进度展示沿用原有单平台进度条的外观、信息和操作，一平台一行纵向排列。领先平台到达下一阶段立即推动页面前进，落后平台继续运行并在到达同一阶段时加入该页面。

**Why this priority**: 这是“全部”主流程能否实际使用的核心，不能再出现后台在运行但页面卡死或入口失效。

**Independent Test**: 分别模拟智联先完成和 BOSS 先完成，确认 02 → 03 → 04 都由领先平台触发，落后平台不被等待；在每个阶段返回旧页面、刷新并继续，入口和进度仍正确。

**Acceptance Scenarios**:

1. **Given** 两平台已启动，**When** 查看 02，**Then** 两个平台分别使用原有单平台进度条纵向展示抓取状态、真实进度和对应操作，不出现并行专用卡片、双列布局或固定假百分比。
2. **Given** 智联先完成抓取，**When** 智联进入 AI，**Then** 页面立即自动进入 03，只展示智联的原有 AI 进度条；BOSS 继续抓取。BOSS 后续进入 AI 时，进度条追加在智联下方。反向顺序遵守同一规则。
3. **Given** 用户返回 02，**When** 查看两平台，**Then** 已完成抓取的平台仍显示完成，未完成平台继续显示实时进度；03 的状态不覆盖或冒充 02 的阶段状态。
4. **Given** 任一平台先完成 AI，**When** 结果可用，**Then** 页面立即自动进入 04 并展示该平台结果；另一平台继续在后台追赶。
5. **Given** 用户主动从 03 或 04 返回旧页面，**When** 落后平台进入下一阶段或完成，**Then** 当前页面不被强制切走，状态照常更新，并在需要告知结果加入时使用灵动岛提示。
6. **Given** 一个平台暂停、继续、停止或失败，**When** 另一平台仍可运行，**Then** 操作和状态只作用于对应平台，不改变另一平台，也不把单轨状态冒充整个流程状态。

### User Story 3 - 结果原地合流且不打断阅读 (Priority: P1)

用户在 04 阅读领先平台结果时，落后平台完成后直接加入同一流程结果。页面不整页重载，不丢失用户正在看的位置和条件，并通过灵动岛告知结果已加入。

**Why this priority**: 先完成结果必须立即可用，后完成结果也不能通过强制刷新破坏用户当前工作。

**Independent Test**: 在 04 设置筛选和排序、滚动并展开一个岗位，再让第二平台完成；确认结果数量和平台数据更新，原筛选、排序、滚动位置和展开状态不变，灵动岛只提示一次。

**Acceptance Scenarios**:

1. **Given** 智联结果先可用，**When** 用户进入 04，**Then** 只展示本流程已有的智联结果，不等待 BOSS，也不混入其他流程。
2. **Given** 用户正在阅读智联结果，**When** BOSS 结果完成，**Then** BOSS 结果原地加入“全部”，不整页重载，并通过灵动岛提示一次“BOSS 结果已加入”；反向顺序遵守同一规则。
3. **Given** 04 已设置筛选、排序、滚动位置或展开岗位，**When** 第二平台结果加入，**Then** 上述阅读现场保持不变，新结果按当前规则进入结果集合。
4. **Given** 一个平台失败且已有部分岗位，**When** 用户查看 04，**Then** 保留该平台已持久化岗位并明确标注平台失败与尚未完成 AI 筛选；没有岗位时仅显示失败状态。

---

### User Story 4 - 刷新、返回和历史始终恢复同一流程 (Priority: P1)

用户在任意已解锁页面刷新或重新打开时，仍看到同一个流程、同一页面和两条平台线。已经解锁的入口不会重新锁住，运行结果、常用配置和历史均使用当时冻结的条件与来源。

**Why this priority**: 流程可恢复性决定长时间任务是否可信，也是 V1 实际卡死问题的直接修复目标。

**Independent Test**: 分别在 02、仅一平台进入 03、仅一平台结果进入 04、两平台都完成四种现场刷新；确认当前页面、所有已解锁入口、进度、结果和操作均恢复正确。

**Acceptance Scenarios**:

1. **Given** 用户停留在一个已解锁页面，**When** 刷新或重新打开，**Then** 恢复刷新前页面；刷新本身不自动前进，也不重新锁住此前已经解锁的 02、03、04。
2. **Given** 一个平台在抓取、另一个在 AI，**When** 刷新，**Then** 02 保留各自抓取阶段状态，03 保留已进入 AI 的平台，并继续根据真实流程状态更新。
3. **Given** 一个平台结果已可见、另一个仍运行，**When** 刷新 04，**Then** 已有结果立即恢复，落后平台完成后仍按原地合流规则加入。
4. **Given** 两个平台都进入终态，**When** 用户打开历史，**Then** 一个外层流程包含两个平台内层状态与各自结果；保存的条件快照按运行当时值展示，不因后来映射表变化而改变。
5. **Given** 一个“全部”流程结束，**When** 随后开始单平台或新的“全部”流程，**Then** 当前结果、恢复、归档和历史均不跨流程混入。

### Edge Cases

- 两个平台近乎同时进入同一阶段时，每个平台只出现一条进度，顺序稳定且不会重复跳页。
- 第一个平台触发自动前进后，第二个平台到达同一阶段不得再次强制跳页。
- 用户主动返回旧页面后，刷新仍恢复该旧页面；落后平台完成不会夺走页面焦点。
- “不限”与其他档位遵守现有互斥规则；映射结果合并时去重，不提交重复平台选项。
- 平台专属字段不因“全部”共同字段变化而被清空。
- 映射表或平台 schema 版本变化后，旧常用配置和历史使用已冻结值，不静默重算。
- 任一平台被系统禁用新建任务时，“全部”仍阻止启动并指出不可用平台；可用单平台仍可单独启动。
- 跨平台去重继续由 B106 决定，V2 不改变默认值、开关或取舍。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 新一轮默认平台选择必须为置顶“全部”，并保留 BOSS、智联单平台选择与既有单平台行为。
- **FR-002**: “全部”场景必须使用中性黑灰主题；BOSS、智联单平台场景继续使用各自主题，任何“全部”页面不得继承平台品牌色。
- **FR-003**: “全部”必须展示六个共同统一字段；BOSS 融资阶段和智联公司性质不得出现在“全部”或被统一映射自动选择，只能在对应平台页手动调整。
- **FR-004**: 简历分析必须给出统一六类初始建议；跳过简历时六类默认为不限。统一值必须按 `contracts/filter-mapping.md` 立即、单向投影到两个平台。
- **FR-005**: 平台页共同字段的手动修改不得反向改变统一值；统一字段再次变化时，必须覆盖两平台对应共同字段的旧选择，不弹确认框，不影响其他字段和平台专属字段。
- **FR-006**: “全部”启动不得存在独立确认状态、确认复选框或二次确认门禁；用户点击一次主按钮即按当前值启动。
- **FR-007**: 常用配置和运行历史必须冻结统一值、两平台最终值、平台微调、平台专属字段及映射版本；恢复时不得使用当前映射覆盖历史值。
- **FR-008**: 一次“全部”启动必须形成一个流程和两条独立平台运行线；V1 已完成的并发、身份隔离、平台操作、失败、历史、归档和结果来源能力必须保留。
- **FR-009**: 02、03 必须逐平台复用原有单平台进度展示和操作，一平台一行纵向排列；不得用新卡片、双列布局、原始英文阶段或固定百分比替代原有用户可读进度。
- **FR-010**: 02 必须保留两平台各自抓取阶段事实；03 只展示已进入 AI 的平台。平台按进入当前阶段的先后顺序追加，已显示进度条不得因后来平台加入而换位。
- **FR-011**: 第一个平台进入 AI 时必须自动进入并解锁 03；第一个平台结果可用时必须自动进入并解锁 04。任一已解锁页面在本流程结束前不得因状态投影或刷新重新锁住。
- **FR-012**: 用户主动返回旧页面后，后续状态变化不得强制前进；刷新必须恢复用户所在的有效页面、所有已解锁入口及两条运行线状态。
- **FR-013**: 第二个平台结果必须原地加入当前 04，不整页重载，并保持筛选、排序、滚动位置和已展开岗位；灵动岛必须只提示一次相应平台结果已加入。
- **FR-014**: 04、历史、归档和岗位操作必须继续以显式流程及平台来源为边界，不得混入此前或后续流程。
- **FR-015**: 任一平台运行或暂停时不得开始新一轮；一条线的暂停、继续、停止、失败或完成不得改变另一条线。
- **FR-016**: 跨平台去重现有策略继续由 B106 独立处理，V2 不新增去重默认值、开关或取舍规则。
- **FR-017**: V2 实施不得以重写 V1 为路径；除修复本规格明确列出的行为外，V1 已完成且未冲突的能力必须保持兼容。
- **FR-018**: 源码运行与打包后的 EXE 必须遵守同一套条件映射、页面推进、刷新恢复、结果合流和灵动岛提示行为，不得为 EXE 保留降级或另一套流程。

### Key Entities

- **流程**：一次“全部”或单平台启动形成的整体边界，承载页面解锁、平台运行线、结果、恢复和历史归属。
- **平台运行线**：一个平台独立的抓取、AI、操作、进度、错误、结果和终态。
- **统一条件**：“全部”页面中的六个共同业务条件，不属于任一平台，作为本次映射的源值。
- **条件映射表**：统一选项到 BOSS、智联实际选项的人工维护契约，遵守“不漏岗位、最小覆盖”。
- **平台最终条件**：统一映射后再叠加用户平台微调和平台专属字段得到的最终提交值。
- **条件快照**：常用配置或运行创建时冻结的统一值、平台最终值和映射版本，恢复与历史不重新计算。
- **流程结果**：当前流程已产生的各平台岗位、筛选结论和失败说明，可随落后平台完成而原地扩充。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在“全部”中最多调整一套六类共同条件并点击一次主按钮，即可启动一个包含两条平台线的流程；不存在平台确认复选框或第二次确认。
- **SC-002**: 在“智联先完成”和“BOSS 先完成”两种顺序中，领先平台均能推动 02 → 03 → 04，落后平台无需等待且最终加入相同页面；全程没有已完成页面重新锁住。
- **SC-003**: 02、03 中每个平台始终只占一行原有样式进度条；第二个平台加入时追加在下方，已经显示的进度条不换位。
- **SC-004**: 第二个平台结果加入 04 时，当前筛选、排序、滚动位置和已展开岗位全部保持，结果数量与平台集合更新，并出现一次灵动岛提示。
- **SC-005**: 在 02、03、04 各刷新一次后，用户均回到刷新前页面，所有此前解锁入口仍可进入，两平台进度与结果均属于同一流程。

## Known Defects After Close *(用户实机反馈，V2 后续统一返修，不在本轮修)*

以下条目由用户在真实应用跑新一轮时逐项反馈，监督者已用真实运行库与代码取证定位到文件行号。归属标注遵循"树枝适配树干"：树干条目不得写入平台名称、平台字段或平台特例。

- **D-01（树枝 · 强阻断）统一经验条件映射过窄且自相矛盾。** 树干未选经验（不限）或选「1 年以下」时，BOSS 侧映射得到 `108 在校生 + 102 应届生 + 101 经验不限 + 103 1年以内` 四档同时选中，其中"经验不限"是哨兵值，与具体档并存语义矛盾；智联侧只得到「在校/应届 + 1 年以下」两档。后果：本轮 BOSS 651 条被字段粗筛刷掉 620 条、智联 382 条刷掉 381 条，AI 精筛输入几乎清空，"几十秒筛完"是映射造成的假完成。修法只允许落在各平台映射表，并要求"哨兵值与具体档互斥"。
- **D-02（树干 · 强阻断）AI 批次判定把整包 JSON 写进 `verdict` 字段。** `webui/store_runs.py:593-613` 的 `save_verdict_and_checkpoint_atomic` 用 `json.dumps(verdict)` 整包入库，而同文件 :565-591 的正确写法会拆成 `verdict / verdict_reason / caveats_json / flags_json`；实测两条轨道的 AI 明细行都存成 `{"verdict":"match",...}` 原文，同轮结果快照 run 却是干净枚举。后果：按 `verdict` 白名单分桶的界面（AI 明细、历史行）把已判定岗位归进「待确认」或吐出原始 JSON。
- **D-03（树干 · 违反"复用不重建"）并行轨道动作条另起炉灶。** 单平台成熟动作条 `ScreenRoundActions`（暂停 / 继续 / 结束并保存 / 放弃本轮，含忙态文案与禁用理由）被 `DiscoveryView.vue:900`、`:937` 的 `v-if="!parallelMode"` 挡在门外；并行轨道改为自写三个裸按钮（`ParallelPlatformProgress.vue:126-146`，显隐规则另起 `visibleButtons()` :88-99，样式仅边框与 4px 内边距）。后果：并行态缺少"结束并保存"等动作、状态判定出现第二套口径（本轮状态错位与死锁由此长出）、按钮视觉与卡片脱节。根因是动作派生仍按"单份现场"建模，未按轨道各算一份；修法是把派生改成轨道级并让并行直接渲染 `ScreenRoundActions`，删除自写动作条。
- **D-04（树干 · 中阻断）轨道动作条没有归属容器。** 动作条是 `article.parallel-platform-item` 的直接子节点，而卡片边框来自子组件 `TaskProgress`，外层无边框（`padding: 10px 0`），因此按钮必然落在卡片边框之外、贴页面左边缘、与卡内文字左边距不对齐；两条轨道各一对同形按钮，只能靠上下位置猜控制对象。期望：动作行收进该轨道卡边框内部，左右与卡内内容对齐。
- **D-05（树干 · 中阻断）并行轨道模块未占满整行。** `DiscoveryView.vue:864-865` 的 `ParallelPlatformProgress` 位于 02 页左列内（与右侧「高级执行设置」面板并排），继承左列宽度，右侧约 600px 完全空白；底部动作行却是整行宽，对比出空洞。期望：轨道进度模块横跨整行、与底部动作行同宽，进度条随之走满一行。
- **D-06（树干 · 中阻断）新一轮收尾后灵动岛通知不失效。** 点「开始新一轮」并已成功把中断轨道收尾为 `cancelled` 之后，灵动岛仍显示「任务已中断，请处理后继续」并写「可重新开始筛选」，而界面上不存在"重新开始筛选"入口（该恢复能力已定案记延期，服务重启后轨道级"继续"必然 503）。通知必须随轮次终态一并失效。
- **D-07（树干 · 中阻断）本轮范围锁定时 03 页汇总与界面自相矛盾。** 七类条件因锁定全部置灰，卡片右上角汇总却写「未设置筛选条件」，与芯片上已选中的「不限 / 全部」冲突；该轮快照实际存在。汇总必须如实反映"已按本轮确认条件锁定，当前只读"。
- **D-08（树干 · 待补提示）04 页在整轮未完成时开放属设计如此，但缺少说明。** 分轨合流要求先出结果的平台可即时查看（`useDiscoveryFlowPresentation.ts:522` 的 `hadResult` 解锁），因此 BOSS 仍在抓取时 04 开放不违反规格；缺陷在于页面没有说明"本轮仍在进行，当前仅含某一条平台线的结果"，用户会误读为整轮已完成。

### 复用与重建的盘点结论

对照本规格"复用现有组件与逻辑，不重建"的要求：展示层（`TaskProgress` 卡片本体、`partitionPipelineResult` 分桶）确实复用了；**交互与状态层（动作条、轨道状态口径、页面导航投影）基本是另写的一套**。D-03 是这一偏差的集中体现，也是本轮多轮返修的共同来源；后续新增平台或扩展轨道时，必须先完成 D-03 的轨道级派生，不得再在并行分支上就地补通用逻辑。
