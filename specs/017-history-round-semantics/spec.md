# Feature Specification: 历史轮次与流程终结语义修复

**Feature Branch**: `017-history-round-semantics`

**Created**: 2026-08-22

**Status**: Draft

**Input**: User description: "历史模块污染治理：只有走到终点的流程才进历史；一条流程一条轮；重抓/补筛更新原轮；时间与标签诚实展示；存量全清重来；快照写入收敛为单一机制。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 没走到终点的流程，历史里绝不多一条 (Priority: P1)

我跑一轮"抓取 + AI 筛选"的流程。中途我点了暂停、或者系统出错把任务强制停下、或者我直接取消、甚至我强杀了整个程序——只要这条流程没有走到终点，历史列表里就不会出现任何新轮次。历史里的每一条轮，都对应一次我亲眼看到过结果页（04 页）的完整决策过程。

**Why this priority**: 这是用户最初的抱怨——"流程没有结束，为什么会在历史里记录"。历史列表的可信度是历史模块存在的意义；只要半成品还能混进去，用户就无法信任这个列表。

**Independent Test**: 构造已有岗位产出的任务，分别触发用户暂停、错误强制暂停、用户取消、进程强杀重启四种中断，断言每次中断后历史列表数量不变；再让流程自然跑完，断言历史恰好新增一条轮。

**Acceptance Scenarios**:

1. **Given** AI 筛选已判定部分岗位，**When** 我点暂停，**Then** 任务显示已暂停、可继续，历史列表数量不变。
2. **Given** 筛选中途触发硬阻断错误（如验证码）被强制暂停，**When** 我打开历史，**Then** 没有新轮次；点"继续"可从断点恢复。
3. **Given** 筛选进行中，**When** 我点取消，**Then** 任务终止、历史无新轮次；底层已抓岗位数据仍保留，可对同一批抓取结果重新发起筛选。
4. **Given** 抓取或筛选进行中，**When** 我强杀程序后重新打开，**Then** 任务显示被中断，历史无新轮次；我可以结束保存或重新开始。
5. **Given** 筛选自然跑完，**When** 结果页出现，**Then** 历史恰好新增一条轮。

---

### User Story 2 - 一条流程永远只有一条轮，结束保存是唯一的定稿动作 (Priority: P1)

一条流程不管经历多少波折——暂停几次、出错几次、续跑几次——最终在历史里只占一条轮。我点"结束保存"，流程定稿、进历史、不能再继续；这是唯一能让我"半途留稿"的动作。想看暂停期间已筛出的岗位明细，就点结束保存（代价是流程终结）；想继续就忍住不点。自然跑完与结束保存互斥：跑完的流程再点结束保存会被拒绝并明确提示。

**Why this priority**: 现状中"暂停后再结束"或"暂停后续跑跑完"会产生两条几乎一样的轮（双快照缺陷），历史被同一流程的残影占据。一条流程一条轮是用户对"轮"的基本心智。

**Independent Test**: 构造暂停→结束保存、暂停→继续→自然跑完、暂停→再暂停→结束保存三条操作序列，断言每个序列最终历史里只有一条轮，且轮内数据为最终状态。

**Acceptance Scenarios**:

1. **Given** 任务已暂停且已有部分判定，**When** 我点结束保存，**Then** 历史新增一条轮，任务终结不可继续；重复点结束保存被拒绝并提示已完成。
2. **Given** 任务已暂停，**When** 我点继续并让筛选自然跑完，**Then** 历史里只有一条轮（即最终结果），无暂停时期的残影轮。
3. **Given** 筛选已自然跑完，**When** 我再点结束保存，**Then** 被拒绝并提示任务已完成，历史不新增。
4. **Given** 历史里存在一条"已抓取，未筛选"的轮，**When** 我对它补跑 AI 筛选，**Then** 该轮原地升级为筛选完成状态，不新增轮，且它在列表中的位置（按创建时间排序）不变。

---

### User Story 3 - 历史轮的信息诚实：标签只有三种，时间显示定稿时刻 (Priority: P2)

我打开历史抽屉，每条轮的标签只有三种可能：完成、部分结果、已抓取，未筛选。"失败但有 N 个岗位"这种文案永久消失。每条轮显示的时间是它的**定稿时间**——正常轮是筛选完成时间；被重抓或补筛过的轮，显示最后一次动作的完成时间，重抓/补筛一完成时间就刷新；列表排序仍按创建时间，轮不会因更新而跳动。

**Why this priority**: 标签和时间是用户判断"这轮是什么、新鲜不新鲜"的唯一线索。取消被写成"失败"、重抓后毫无痕迹，都是信息不诚实。

**Independent Test**: 依次产生三种状态的轮并核对标签文案；对一条含待确认岗位的轮执行重抓，断言历史中该轮的计数与显示时间更新、总轮数不变、排序位置不变。

**Acceptance Scenarios**:

1. **Given** 历史中存在完成、部分结果、已抓取未筛选三种轮，**When** 我查看列表，**Then** 标签恰为"完成""部分结果""已抓取，未筛选"，无其它文案。
2. **Given** 一条轮含待确认岗位，**When** 我在结果页重抓并完成，**Then** 历史中该轮的匹配/待确认计数更新，显示时间变为重抓完成时刻，轮总数与排序位置不变。
3. **Given** 升级到本版本，**When** 我首次打开历史，**Then** 存量历史轮已被一次性清空，从零开始积累（每平台保留上限维持 30 条）。

---

### User Story 4 - 历史更新永远落在正确的轮上 (Priority: P3)

我在结果页对待确认岗位发起重抓时，系统必须明确知道要更新哪一条轮；不允许"猜一个最新的"。缺省目标被移除：不带目标的重抓请求被直接拒绝。旧的重复归档入口被删除，归档与删除只有一个入口。这套约束保证未来不再出现"重抓写进了半成品"或"两条轮各改一半"的错乱。

**Why this priority**: 这是防御性收敛——当前前端已挡住主要路径，但后端口子不关，任何旁路调用或未来改动都可能踩中。修掉后历史模块的写入面只有一个可信入口。

**Independent Test**: 直接调用重抓接口且不指定源轮，断言被拒绝且返回明确错误；调用已废弃的旧归档接口，断言不存在。

**Acceptance Scenarios**:

1. **Given** 任意状态，**When** 重抓请求未携带目标轮标识，**Then** 请求被拒绝并提示必须指定目标结果。
2. **Given** 任何调用方，**When** 尝试访问旧的结果清空接口，**Then** 该接口已不存在，归档与删除统一走历史接口。

---

### User Story 5 - 一套话术贯穿始终：任务状态与"最新结果"都只有一个口径 (Priority: P3)

不管从哪个页面、哪个接口看，同一个任务状态永远用同一个词——列表页说"已暂停"，详情页、轮询、历史页就不会说成"等待"或别的。同样，"最新结果是哪一条"整个系统只有一个判定规则，不存在 A 页面认这条、B 页面认那条的分叉。状态词两本词典、最新结果三套口径这两处平行真相被合并为一。

**Why this priority**: 与错误码模块"三套码并一套"同源——一个概念两处定义，早晚漂移出"接口 A 说暂停、接口 B 说等待"的诡异现象。用户现在看不到错，是因为前端两头兼容硬扛着；收掉后这类矛盾从根上不可能发生。

**Independent Test**: 构造暂停、完成、失败等各状态任务，逐一调用任务列表、任务详情、任务轮询接口，断言同一任务在所有接口返回的状态词一致；分别从结果页与历史页取"最新结果"，断言判定结果一致。

**Acceptance Scenarios**:

1. **Given** 一个处于暂停状态的任务，**When** 前端同时从任务列表、任务详情、轮询接口读取状态，**Then** 三处得到完全相同的状态词。
2. **Given** 存在多条候选结果（不同平台、已归档与未归档），**When** 任何功能询问"最新结果"，**Then** 系统按唯一口径返回同一条，无第二套判定路径。
3. **Given** 全部代码检索，**When** 检查状态翻译与最新结果判定，**Then** 各自只存在一份实现，无平行版本。

---

### Edge Cases

- 强杀进程后数天才重新打开：任务按"被重启中断"恢复，历史无轮，结束保存与重新开始两条路都可用。
- 结束保存时流程实际产出 0 个岗位：不成轮，任务照常终结，历史不变（沿用现有空结果不成轮规则）。
- 补筛升级的目标轮此前已被归档：原地升级时解除归档状态，轮重新可被"最新结果"查询命中（沿用现有行为）。
- 清空存量历史时恰有任务在跑：只清历史轮，不影响任何活动任务的进度与断点。
- 重抓过程中暂停：已完成的判定与 JD 保留在断点、不写原轮；继续并跑完后统一回写原轮并刷新定稿时间；未完成部分保持待确认，可继续重抓。
- 跳过筛选时抓取结果为 0 个岗位：不产生"已抓取，未筛选"轮（沿用现有规则）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 历史轮次的产生时机必须且仅有三种：AI 筛选自然跑完、用户点"结束保存"、跳过 AI 筛选直接查看结果。
- **FR-002**: 用户暂停、错误强制暂停、用户取消、进程重启中断这四种情况 MUST NOT 产生任何历史轮次。
- **FR-003**: 取消必须保留底层已抓岗位数据（可对同一批抓取结果重新发起筛选），但 MUST NOT 为其生成历史轮；"结束保存"是唯一的人工定稿动作，定稿后流程终结、不可继续。
- **FR-004**: 同一条流程在任意操作序列下（多次暂停、续跑、结束后重复操作）MUST 最多产生一条历史轮；自然跑完后再请求结束保存 MUST 被拒绝并给出明确提示。
- **FR-005**: 对"已抓取，未筛选"轮补跑筛选 MUST 原地升级该轮（不新增轮、列表排序位置不变）；对待确认岗位重抓 MUST 原地更新该轮的判定与计数。
- **FR-006**: 历史轮状态标签必须只有三种：完成、部分结果、已抓取，未筛选；MUST NOT 再出现"失败但有 N 个岗位"类文案。
- **FR-007**: 历史轮显示的主时间必须为定稿时间（内容最后一次落定的时刻）；重抓或补筛完成时必须刷新该时间；列表排序必须保持按创建时间不变。
- **FR-008**: 历史轮的写入必须收敛为单一机制：三个合法入口共用同一条写入路径，防重守卫只存在一处。
- **FR-009**: 升级到本版本时必须一次性清空全部存量历史轮；每平台历史轮保留上限维持 30 条不变。
- **FR-010**: 重抓请求必须显式携带目标轮标识，缺失时必须拒绝；系统 MUST NOT 自行推断缺省目标。
- **FR-011**: 旧的结果清空/归档重复接口必须删除，归档与删除操作只保留历史模块的统一入口。
- **FR-012**: 任务状态对前端的报告必须统一为一套词汇表：同一任务在任何接口（列表、详情、轮询、恢复）返回同一状态词；系统内 MUST NOT 存在第二份状态翻译。
- **FR-013**: "最新结果"的判定必须收敛为唯一口径（同一状态集合、同一归档过滤规则），全局与按平台等所有询问路径 MUST 使用同一判定；无调用方的旧判定入口必须删除。

### Key Entities *(include if feature involves data)*

- **流程（一轮筛选）**: 从发起抓取到最终定稿的完整过程，可能经历暂停、续跑、中断、取消；一条流程对应零条（未定稿）或一条（定稿）历史轮。
- **历史轮**: 一次走到终点的流程的结果档案，含判定明细、计数、状态标签（完成/部分结果/已抓取未筛选）、创建时间与定稿时间；可被补筛升级或重抓原地更新。
- **定稿（结束保存）**: 用户显式发起的流程终结动作，产生历史轮并关闭继续可能；与自然跑完互斥。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 暂停、取消、错误强停、强杀重启四种中断发生后，历史列表轮数零增长。
- **SC-002**: 任意操作序列走完一条流程，历史恰好新增一条轮（可重复验证不产生第二条）。
- **SC-003**: 历史列表中不存在"失败但有 N 个岗位"文案及任何无法对应到 04 页经历的轮。
- **SC-004**: 重抓或补筛完成后 5 秒内刷新历史列表，对应轮的计数与时间已更新，轮总数与排序位置不变。
- **SC-005**: 版本升级后首次启动，历史轮从零开始积累，每平台上限 30 条。
- **SC-006**: 同一任务状态在所有接口与前端展示中用词完全一致；"最新结果"在全系统只存在一个判定口径。

## Verification Scope *(mandatory)*

- 功能/重构/拆分交付：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。

## Assumptions

- 不新增"暂停期间预览已筛岗位明细"功能：想看明细只能结束保存（流程随之终结），现状交互保持。
- 前端结果页对"暂停任务期间不加载最新结果"的现有守卫保持不变。
- 收藏、反馈、任务日志等全局数据不受历史清空影响，沿用现有保留规则。
- 存量历史轮不做精细识别与选择性保留，按用户决定一次性全清。
- 状态词汇统一不涉及存量数据迁移：run 状态是活任务的即时报告，历史轮状态已随存量清空归零；唯一外部消费方是本产品自带前端，随本 spec 一同调整。
- 实现时序（与错误模块重构 016 的先后与冲突处理）由用户掌控，本 spec 不约束排期；本 spec 仅交付至任务分解，不执行实现。
