# Feature Specification: 测试体系低噪音瘦身

**Feature Branch**: `040-test-suite-slimming`

**Created**: 2026-09-11

**Status**: 已冻结（2026-09-11 经用户六轮边界质询逐项确认；五批范围、顺序、节奏与死代码机制均锁定，实施期间不得偏离）

**Input**: 用户原话："我认为现在的测试代码太过繁重，想优化。但是优化不代表将有用的优化，我只想进行低噪音的优化。""我作为用户视角，我只知道现在繁重，想减轻。但是减轻我又不想本来正确覆盖的地方出现漏洞。我只想看那种没有必要或者做的多余的地方，或者什么地方逻辑耦合，逻辑错杂了，可以优化逻辑，简化逻辑，但是不影响任何使用。"

## 用户原话与已确认边界

以下边界经 2026-09-11 边界质询逐项确认冻结：

1. **范围**：覆盖全项目测试代码与测试基建；**一个 Spec 装五批**，顺序冻结为：①假保护必修 → ②零风险删除 → ③重复选边 → ④缠结小修 → ⑤死代码回收。
2. **三条验收硬标准**（缺一不可）：
   - **保护不变**：往产品代码里故意埋同一处故障，改动前后"变红的测试集合"必须完全一致；
   - **判定不变**：什么情况算失败、失败时报什么，不因优化而改变；
   - **连累面小**：每一刀小到能一眼看懂、能单独提交、能单独回退。
3. **实施节奏**：每批完成后停止并汇报（改了什么、减了多少、验证结果）；下一批是否实施由用户当轮决定。任务清单（tasks）完成后同样停止，等待用户明确下令才进入实施。
4. **死代码机制**：第 1~4 批发现死代码只记不动，逐条记入本 Spec 内「死代码登记册」；第 5 批实施前将登记册整理为待删清单交用户过目，**经用户逐项同意后才删除**；删除时产品代码与其测试一并删除、小步推进、以全量测试与前端构建兜底。实施中若发现产品代码缺陷，只记录并上报，不得顺手修改。
5. **只动测试侧**：允许修改 `tests/`、`webui/src/**/__tests__/`、`webui/src/test/` 及测试相关配置（vitest/vite 配置、GitHub workflow、git 钩子）；产品代码唯一允许动的地方是第 5 批经用户同意的死代码删除；`tests/sc015_viewport_check.py` 属测试侧，其过期门禁在该批修复。
6. **禁碰红线**：审计报告第 7 节列出的断言是各自业务不变量的唯一保护，不得删除、不得弱化（主题清单见「禁碰红线」小节）。
7. **不做清单**（记入本 Spec、不随本 Spec 实施）：巨型测试文件拆分、CI 流水线重做、测试包加载方式改造——三件均为独立工程，另行立项。
8. **纪律**：除本 Spec 内「死代码登记册」（用户明确要求）外，未经用户要求不创建任何文档/清单；**不触碰用户的本地待办清单（`roadmap/BACKLOG.md`）——该文件是用户私人的待办本，AI 不写入、不新增条目**；未经用户指令不提交、不推送；测试日志与临时产物一律进系统临时目录并当轮清理；所有汇报与说明使用大白话。

## 已核实问题基线

2026-09-11 全量只读审计（后端 127 个测试文件 / 65,697 行；前端 52 个测试文件 / 21,402 行）结论：问题不是"没测"，而是四种病：

| 病症 | 表现 | 规模 |
|---|---|---|
| 重复测 | 同一事实最多在 4 个文件各断言一遍；最重一处同一批全链路（真实线程 + 临时库）整跑 3 遍 | 约 30 组重复事实 |
| 死着测 | 约 100 行桌面壳假替身零引用、样本加载函数零调用、fixtures 文件零引用、未用导入/死参数/死分支若干 | 约 55 条 |
| 假着测 | 断言永不执行（假替身导致循环体零次迭代）、恒真断言、名实不符用例、`unittest.main()` 位置错误导致直跑丢例 | 约 20 条 |
| 缠着测 | 全局猴子补丁不还原、用例顺序依赖、真实端口与真实用户目录被触碰、共享临时日志目录、真定时器泄漏 | 约 15 条 |

本 Spec 开工前复核过、确认仍然成立的关键事实：

- `tests/sc015_viewport_check.py` 的选择器已过期：它查找的界面元素全仓不存在（0 命中），真机门禁必然失败，且 `test_pipeline_state.py` 仍在断言旧选择器存在；
- `tests/test_pipeline_guard.py` 的"白箱事件"用例断言永不执行（假替身不是真服务，异常被吞，循环体零次迭代）；
- `tests/webui_app/test_webui_app_runtime.py` 部分用例真实访问本机端口、真实读取用户目录账号簿；
- `webui/semantic.py` 无任何生产调用方（仅其测试引用；模块后半段连测试都没有），系两次重构后遗留的孤儿。

证据细则：审计报告（本地工作底稿，不随仓库提交）逐条给出文件与行号；实施时逐条复核，行号以内容为准。

## 用户目标

- 让"全绿"恢复可信：清掉"看着在保护、实际保护不到"的假保护；
- 给测试体系真正减重：删掉无人使用的死件、逐字重复的用例与自我重复的断言；
- 同一事实只留一处正本，其余降为冒烟或删除，但一条真实断言都不丢；
- 测试不再触碰真实用户环境、不再互相污染、不再残留全局状态；
- 顺手回收确认无用的产品死代码（经用户逐项同意）；
- 全程不改变失败判定口径，用户感觉不到任何产品行为变化。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 假保护必修（Priority: P1）

仓库维护者发现：一条断言永不执行的用例、一批恒真断言、一个与前端失去联系的真机门禁，长期给"全绿"注入虚假安全感。本批把这些假保护修复为真实有效的测试，或确认无价值后删除，并同步修复被它们锁死的过期断言。

**Why this priority**: 假保护是"止损"——它让全部测试结果的信任基础受损；先修它，后续的删除与合并才有一把可信的尺子。

**Independent Test**: 对每个被修复的守卫点注入对应故障，验证测试确实变红（修复前不变红、或测试根本不执行）

**Acceptance Scenarios**:

1. **Given** 一条断言永不执行的用例，**When** 修复后用真实替身走通目标场景并注入故障，**Then** 断言真实执行且用例变红；
2. **Given** 恒真断言或名实不符的用例，**When** 修复为真实断言，**Then** 注入对应故障后用例失败（修复前不会失败）；
3. **Given** 真机门禁脚本与测试中的过期选择器，**When** 统一为当前真实名称，**Then** 门禁恢复有效，锁死旧名的断言不再阻拦修复；
4. **Given** 因引用不存在的目录而永久跳过的用例，**When** 处置完毕，**Then** 仓库中不再存在"任何情况下都不执行"的用例。

---

### User Story 2 - 零风险删除（Priority: P2）

删除全仓零引用的死件（假替身类、样本加载函数、fixtures 文件、未用导入、死参数、死分支）与同文件内逐字重复的用例、恒真伪断言。每条删除前重新验证引用为零。

**Why this priority**: 删除是最直接的减重，且几乎无保护风险（删前逐条复查引用即可证明）。

**Independent Test**: 每条删除前重新检索引用确认零命中；批末全量测试、前端测试与构建全绿。

**Acceptance Scenarios**:

1. **Given** 任一拟删条目，**When** 实施删除前复查引用，**Then** 全仓零命中（若有命中则不得删除并上报）；
2. **Given** 同文件内逐字重复的用例，**When** 合并为一条，**Then** 保留覆盖更严的一侧，批末全量测试不变红；
3. **Given** 恒真断言与被更强用例完全覆盖的用例，**When** 删除，**Then** 全量测试结果与删除前一致（证明其从未贡献保护）。

---

### User Story 3 - 重复选边（Priority: P3）

同一事实在多个文件重复断言的约 30 组，逐组选定"正本"（覆盖最全的一处），其余降为单条冒烟或删除。最重的一处（同一批全链路被整跑 3 遍）在本批消除。

**Why this priority**: 收益大（消除全仓最大单笔重复工作量），但每组需要判断与验证，风险高于纯删除，故排在删除之后。

**Independent Test**: 每组收敛后执行"故障注入指纹"验证——改动前后对同一产品逻辑注入同一故障，变红的测试集合完全一致。

**Acceptance Scenarios**:

1. **Given** 一组重复事实，**When** 选定正本并降级其余，**Then** 正本侧断言只增不减，独有断言全部保留；
2. **Given** 一组已完成选边的改动，**When** 执行故障注入指纹验证，**Then** 变红集合与改动前完全一致（不一致则回退该组并上报）；
3. **Given** 同一批全链路被整跑多遍的问题，**When** 本批完成，**Then** 该重复不再发生，全量测试时长不增加。

---

### User Story 4 - 缠结小修（Priority: P4）

测试不再触碰真实用户环境（用户数据目录、真实外部端口），不再互相污染（共享临时目录、顺序依赖），不再残留全局状态（未还原的补丁、环境变量、模块替换、泄漏的定时器）。

**Why this priority**: 解缠关系测试体系的稳定性；影响面最大，放第四位，只做可局部回退的小修，大工程另行立项。

**Independent Test**: 修复后测试在单独运行、换序运行、重复运行下结果一致；真实用户目录与外部端口不再被触碰。

**Acceptance Scenarios**:

1. **Given** 任何做过全局修改的用例，**When** 用例结束，**Then** 全局状态全部还原（补丁、环境变量、模块替换、随机种子等）；
2. **Given** 任何会写文件的用例，**When** 运行，**Then** 写入系统临时目录并当轮清理，真实用户目录零写入，仓库根目录零残留；
3. **Given** 自动测试套件，**When** 运行，**Then** 不再访问真实外部端口（明确保留的手动资产除外）；
4. **Given** 前端测试中的定时器与全局对象，**When** 用例结束，**Then** 已清理，不泄漏到后续用例。

---

### User Story 5 - 死代码回收（Priority: P5）

按「死代码登记册」回收无人使用的产品代码（连同其测试）：先整理清单交用户过目，经逐项同意后删除，删除后以全量测试与前端构建证明"无残留引用"。

**Why this priority**: 唯一需要改动产品代码的一批，授权与验证成本最高，放最后单独进行。

**Independent Test**: 删除后全量测试、前端测试与构建全绿；清单内每一项均有用户同意依据。

**Acceptance Scenarios**:

1. **Given** 第 1~4 批中发现的死代码候选，**When** 登记册整理完毕，**Then** 每条含位置、内容、查证记录与建议处置，无遗漏；
2. **Given** 待删清单，**When** 交用户过目，**Then** 仅用户同意的条目被删除，其余保留并注明原因；
3. **Given** 已删除的条目，**When** 执行全量测试与前端构建，**Then** 全绿（构建即证明无残留引用）；若发现新引用，**Then** 立即恢复并上报。

---

### Edge Cases

- **行号漂移**：审计证据的行号在实施时可能已变化，一律以内容定位为准。
- **疑似恒真断言实为轻微保护**（如断言类型正确）：删除前先判断其唯一性；能改为真断言的不删。
- **合并时发现独有断言**：两侧并非完全重复时，保留独有部分，不得连带删除。
- **指纹验证波动**：变红集合因并行或顺序差异波动时，先重跑三次排除偶发；仍不一致则回退该组，标记"不可合并"并上报。
- **删除后暴露真实依赖**：删除死件后若全量测试或构建变红（说明存在字符串引用等隐性依赖），立即恢复该处删改并记入报告。
- **第 5 批候选在删除前被复查出新引用**（例如中间批次引入了引用）：从清单剔除并上报，不得删。
- **复核与审计结论不符**：审计判定"可删/重复"而实践复核发现不成立的，以复核为准不删，并记入批末报告。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每一处删除（代码、资产、用例）实施前 MUST 重新验证引用为零（全仓文本检索）；引用不为零的一律不得删。
- **FR-002**: 涉及合并、挪动、改写（非纯删除）的改动 MUST 执行"故障注入指纹"验证：改动前后对同一产品逻辑注入同一故障，变红的测试集合 MUST 完全一致；不一致 MUST 回退该处改动。
- **FR-003**: 断言永不执行、恒真、名实不符的用例 MUST 修复为真实断言或删除；修复后 MUST 能被对应故障注入触发变红。
- **FR-004**: 审计确认的重复事实组 MUST 收敛为单一正本（保留覆盖最全的一处），其余 MUST 降级为冒烟级或删除；正本侧覆盖与各处独有断言 MUST NOT 减少。
- **FR-005**: 测试 MUST NOT 触碰真实用户环境（用户数据目录、真实浏览器、真实外部端口）；确需真实环境的手动工具 MUST 与自动测试明确分离并注明。
- **FR-006**: 测试对全局状态的修改（打补丁、环境变量、模块级替换、随机种子等）MUST 在用例结束时还原。
- **FR-007**: 测试产生的临时文件 MUST 位于系统临时目录并当轮清理；MUST NOT 落在仓库根目录或真实用户目录。
- **FR-008**: 什么算失败、失败报什么 MUST 与本规格实施前一致；仓库卫生、构建与既有断言语义 MUST NOT 因本次改动而弱化。
- **FR-009**: 本规格 MUST 以五批推进，顺序为：假保护必修 → 零风险删除 → 重复选边 → 缠结小修 → 死代码回收；每批完成后停止并汇报，下一批 MUST 经用户当轮确认。
- **FR-010**: 第 1~4 批 MUST NOT 修改产品代码；实施中发现的死代码 MUST 只记入「死代码登记册」，发现的产品缺陷 MUST 只记录并上报。
- **FR-011**: 第 5 批删除产品死代码前 MUST 将登记册整理为清单交用户逐项确认；删除后 MUST 以全量测试、前端测试与前端构建验证。
- **FR-012**: 审计报告第 7 节禁碰红线 MUST NOT 被删除或弱化。
- **FR-013**: 每批改动 MUST 保持"可单独看懂、可单独提交、可单独回退"的粒度；提交与推送 MUST 等待用户明确指令。
- **FR-014**: 本规格 MUST NOT 包含：巨型测试文件拆分、CI 流水线重做、测试包加载方式改造——三项记入本 Spec 不做清单，另行立项。
- **FR-015**: 测试规模 MUST 持续统计并汇报（后端/前端各自文件数、行数、用例数、全量时长）；每批收尾给出与基线的对比。

### 禁碰红线（不得删除或弱化）

以下断言是各自业务不变量的唯一保护，本 Spec 全域不得删除或弱化（具体位置在 tasks 逐条列出）：

- AI 调用的阻塞流保护与总超时兜底；
- AI 匹配的熔断、响应截断与测量索引；
- 平台故障传播；
- Chrome 配置脱敏与回滚；
- 抓取退出码映射；
- 智联线程死亡补跑；
- 并发写保护三条；
- 跨平台去重集成对账；
- 白箱唯一断言（写失败恒不可成功、终局原子性、不完整不可成功/B098 回归）；
- 断点损坏 409 契约；
- R2 配额；
- 窗口 toggle 状态镜像；
- 端到端冒烟主链；
- 前端安全边界（安全 URL 规范化、提醒 URL 复验、账号对话框 409、岗位操作无自动写）。

### Key Entities

- **假保护用例**：断言永不执行、恒真、名实不符或与前端断联的测试。
- **重复事实组**：同一业务事实在多个文件各自断言的集合。
- **死件**：全仓零引用的代码、夹具或资产。
- **缠结点**：跨用例的状态污染源（未还原的补丁、真实资源、共享目录、泄漏的定时器）。
- **死代码登记册**：本 Spec 内文件，逐条记录实施过程中发现的产品死代码候选（位置、内容、查证、建议处置）。
- **基线快照**：后端 127 文件 / 65,697 行、全量约 19 分钟；前端 52 文件 / 21,402 行、约 26 秒；全绿。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对审计清单内每个被修复的假保护点执行故障注入，修复后 100% 变红（修复前不能变红或测试不执行）。
- **SC-002**: 重复选边每组收敛后，故障注入的变红测试集合与改动前完全一致；保护丢失的组数为 0（对不上的组已回退）。
- **SC-003**: 五批全部完成后，后端全量测试、前端测试、前端构建、仓库卫生检查全绿；失败判定口径与基线一致。
- **SC-004**: 自动测试对真实用户目录与真实外部端口的触碰清零（明确保留的手动资产除外）。
