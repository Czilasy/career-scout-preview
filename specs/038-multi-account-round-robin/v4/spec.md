# Feature Specification: 多账号轮询分摊抓取可靠性修复（B091 V4）

**Feature Branch**: `038-multi-account-round-robin`

**Spec Version**: `v4`

**Supersedes**: `v3`；运行语义继续继承 `v2`，账号弹窗与限流标记交互继续继承 `v3`

**Status**: 已冻结，待实施

**Input**: 用户确认本轮属于已有多账号轮询能力的增加与修复补丁，需求边界已明确，要求直接形成 V4 并交由后续 AI 执行。

## 用户原话与已确认边界

- 用户加入多个账号的目的，是让 R2 详情岗位从一开始就由多个选中账号按配额真实分摊，而不是只在界面或日志中显示账号已加入。
- 平台验证码、平台限流等外部风控不属于本轮修复对象；本轮修复的是本地轮询、账号级熔断、接力、留痕、产物与恢复状态。
- 本轮是对 038 已冻结目标的纠错，不新增独立产品入口，不改变账号池配置方式，不改变 R1/R2 串行抓取原则。
- 必须覆盖已查明的同类缺陷，不能只修复最先暴露的一处而留下另一条路径继续让账号“看似接管、实际未抓”。

## 已核实问题基线

最近一次正式 R2 详情抓取最终得到 1048 个详情岗位，但按实际成功来源核对后，第一个账号完成 1046 个、第二个账号完成 2 个，其余四个账号均为 0。账号池存在且账号切换记录成功，并不等于这些账号实际启动过详情抓取。

已核实的本地缺陷为：

1. R2 轮询状态在外层详情分块之间被重新开始，导致第一个账号的配额反复恢复，正常配额轮换没有发生。
2. 不同账号的抓取源共享本地熔断状态；一个账号打开熔断器后，后续账号会在真正请求前被本地短路。
3. 白箱把“预留/分配”记录成了足以被误解为实际抓取的事实；本次任务累计记录 1146 个分配单位，但最终实际详情成功为 1048 个。
4. 撞墙接力可能复用同一尝试产物，后一次账号尝试覆盖前一次证据。
5. 暂停后恢复成功只清理内存失败状态，数据库中仍残留 16 条已被后续成功结果取代的旧 JD 失败记录。
6. 既有测试覆盖了单次轮询或单抓取源，却没有覆盖“多账号 + 多个外层分块 + 局部成功后撞墙 + 接力 + 暂停恢复”的真实组合；其中一项测试还把共享熔断状态固定成了预期行为。

## 用户目标

用户选中多个账号并开始详情抓取后，系统必须让这些账号按照用户配置的顺序和每轮配额真实承担工作。分块、重试、撞墙和暂停恢复都不能暗中重置轮询或把一个账号的本地熔断传播给其他账号。

任务结束后，用户和维护者必须能够区分“计划分配”“实际开始请求”“实际成功”“实际失败”和“本地短路”，并按账号核对真实抓取数量。任何账号只有在自身实际请求产生平台阻断信号时，才可被标记为限流；任何后续成功结果都必须清理对应的旧失败状态。

## User Scenarios & Testing

### User Story 1 - R2 全程按配额真实轮询（P1）

用户选择多个账号执行一个包含多个详情分块的 R2 任务。无论内部把岗位拆成多少批或多少块，轮询配额都在整个 R2 阶段连续累计，不能因一次内部函数调用结束而重新从第一个账号开始。

**Why this priority**: 这是 038 的最高目标。若配额不能跨分块累计，多账号从一开始主动分摊就没有真正生效。

**Independent Test**: 使用六个账号、每账号 R2 配额 200、1048 个无失败模拟岗位执行完整阶段；实际请求分布依次为 200、200、200、200、200、48。

**Acceptance Scenarios**:

1. **Given** 两个账号的 R2 配额均为 200，内部每块 20 条，**When** 连续处理 11 块，**Then** 前 10 块由第一个账号承担，第 11 块由第二个账号承担。
2. **Given** 六个账号、每账号 R2 配额 200、共 1048 个无失败岗位，**When** 完成 R2，**Then** 六个账号的实际请求数量依次为 200、200、200、200、200、48。
3. **Given** 不同账号配置不同配额，**When** 总量跨越一轮并进入下一轮，**Then** 每个账号每轮不超过自身配额，下一轮仍按选中顺序开始。
4. **Given** R2 被拆成多个内部调用，**When** 任一内部调用正常结束，**Then** 下一次调用沿用当前轮次、当前账号和剩余配额，不因调用边界重置。

### User Story 2 - 账号级熔断隔离与真实接力（P1）

某一账号真实遇到平台阻断时，系统只停止该账号的后续请求，并把未完成岗位交给下一个选中且可用的账号。其他账号必须拥有独立的本地阻断状态，并真正启动接力请求。

**Why this priority**: 若本地熔断跨账号共享，撞墙换号只能产生虚假切换，无法保护任务完整性。

**Independent Test**: 第一个账号在 20 条中成功 18 条、剩余 2 条产生硬阻断；第二个账号必须实际请求且完成这 2 条，第一个账号被标记限流，第二个账号不被误标。

**Acceptance Scenarios**:

1. **Given** 第一个账号已经打开本地熔断，第二个账号未产生任何阻断信号，**When** 系统切换到第二个账号，**Then** 第二个账号可以启动真实请求，不受第一个账号熔断状态影响。
2. **Given** 一批 20 条中已有 18 条成功、2 条撞墙，**When** 切换账号接力，**Then** 只转移未完成的 2 条，18 条成功结果不丢失、不重复抓。
3. **Given** 一个账号只发生账号绑定失败或本地执行环境失败，**When** 系统尝试下一个账号，**Then** 前一个账号不会被误标为平台限流。
4. **Given** 后续账号自身也真实产生硬阻断，**When** 继续接力，**Then** 只标记实际产生阻断信号的账号，并按账号池顺序继续。
5. **Given** 所有选中账号均已通过自身实际请求产生硬阻断，**When** 没有可用账号，**Then** 任务进入既有暂停状态并保留全部已成功结果。

### User Story 3 - 按账号核对真实工作与完整证据（P1）

用户或维护者查看任务记录时，可以明确知道哪些只是计划分配，哪些账号真正开始请求，以及每个账号实际成功、失败、本地短路和移交了多少岗位。重试证据不会互相覆盖。

**Why this priority**: 账号分摊必须可证明；否则系统仍可能在日志看起来正常、实际全部压在一个账号上。

**Independent Test**: 构造一次包含正常轮换、局部成功、撞墙接力和一次本地短路的任务，按账号汇总真实终态，并核对每次尝试均有唯一证据。

**Acceptance Scenarios**:

1. **Given** 系统为某账号预留一段岗位，**When** 尚未启动真实请求，**Then** 记录只能表达“已预留”，不能表达为“已抓取”。
2. **Given** 账号开始并结束一次请求，**When** 查看任务记录，**Then** 可以看到账号、尝试序号、请求数量、成功数、失败数、本地短路数和未完成数。
3. **Given** 同一批岗位发生跨账号重试，**When** 查看产物，**Then** 每个账号、每次尝试都有独立证据，后一次尝试不覆盖前一次。
4. **Given** 任务完成或暂停，**When** 查看按账号汇总，**Then** 各账号唯一详情成功数之和等于任务详情抓取成功总数，重试失败与重复分配不计入成功数。
5. **Given** 白箱记录缺失或写入失败，**When** 任务收尾，**Then** 不得把无法证明的账号工作报告为已完成，并明确标识记录不完整。

### User Story 4 - 暂停恢复后状态一致（P1）

用户处理阻断并继续任务后，系统保留已经完成的详情、正确恢复轮询位置，并删除已被后续成功取代的旧 JD 失败记录。

**Why this priority**: 若恢复重置账号压力或保留过期失败，任务结果、待确认和后续补抓都会继续失真。

**Independent Test**: 任务在局部成功后暂停，继续后由正确的可用账号完成剩余岗位；完成岗位不重复抓，对应旧 JD 失败记录归零，其他尚未解决的 AI 或 JD 失败不被误删。

**Acceptance Scenarios**:

1. **Given** R2 在中途暂停并保存了轮询位置，**When** 用户继续且未显式选择其他账号，**Then** 从暂停前的下一可用位置和剩余配额继续，不因恢复返回第一个账号。
2. **Given** 用户通过既有继续流程显式选择了另一个可用账号，**When** 任务恢复，**Then** 尊重该选择，并从该账号开始继续，同时保留已有成功结果。
3. **Given** 某岗位此前写入 JD 抓取失败，之后恢复成功取得有效 JD，**When** 成功结果落定，**Then** 所有由本次 JD 失败写入的对应待处理记录被删除。
4. **Given** 某岗位仍未取得 JD，或其 AI 精筛仍未完成，**When** 清理恢复状态，**Then** 这些尚未解决的待处理记录继续保留。
5. **Given** 恢复所需的轮询状态缺失或损坏，**When** 系统无法安全确定接续位置，**Then** 明确暂停并报告可恢复错误，不静默从第一个账号重新开始。

### Edge Cases

- 单账号任务继续保持既有单源行为，不为了轮询引入额外切换。
- 某账号配额小于内部批大小时，只领取其剩余配额，尾部由下一个账号继续。
- 一次请求既有成功结果又有硬阻断时，只接力未成功项；成功项的最终归属为真正产出有效详情的账号。
- 本地熔断短路不等同于该账号新产生平台阻断；不得据此继续污染后续账号的限流状态。
- 账号切换成功但抓取源创建失败时，记录为绑定或环境失败，不伪造请求开始。
- 账号池在任务中途发生人工修改时，运行中的任务继续使用冻结账号池；用户通过既有恢复入口明确变更账号时除外。
- 任务停止、取消或异常退出时，已落定的轮询状态、实际成功结果和尝试证据必须保持一致。
- 旧版本任务没有 V4 轮询状态时，不回写或伪造历史账号归属；只对 V4 之后的新执行提供完整保证。

## Functional Requirements

- **FR-001**: V4 MUST 继承 v2 的多账号轮询业务语义和 v3 的账号弹窗行为；不得新增独立页面、账号池或另一套限流 UI。
- **FR-002**: R2 MUST 在一个逻辑任务的整个详情阶段使用连续的轮询状态，内部批次、分块和函数调用边界不得重置轮次、当前账号或剩余配额。
- **FR-003**: R2 MUST 按用户冻结的账号顺序与每轮配额累计实际请求数量；无失败情况下，实际请求分布必须与标准轮询计算完全一致。
- **FR-004**: R2 MUST 保持串行执行，一次只允许一个账号实例承担真实请求；本轮不引入多账号并行抓取。
- **FR-005**: 每个账号 MUST 拥有独立的本地熔断状态；一个账号的登录墙、验证码、限流或阻断信号不得打开其他账号的本地熔断。
- **FR-006**: 账号克隆 MUST 只共享安全的不可变配置与任务级取消信号；账号级可变运行状态和执行探针不得跨账号泄漏。
- **FR-007**: 账号只有在自身实际请求产生平台硬阻断信号时才可被标记限流；绑定失败、环境失败和继承自其他账号的本地短路不得触发该标记。
- **FR-008**: 局部成功后撞墙 MUST 只把未完成岗位移交给下一可用账号，已成功详情不得丢失、覆盖或重复请求。
- **FR-009**: 切换记录成功后，系统 MUST 进一步证明目标账号实际开始请求或明确记录未开始的原因；仅有账号切换或预留记录不得视为接力完成。
- **FR-010**: 所有选中账号都已通过自身实际请求产生硬阻断时，任务 MUST 使用既有暂停状态收尾，并保留成功详情和可恢复断点。
- **FR-011**: 暂停恢复 MUST 恢复轮询位置、轮次、当前账号剩余配额和已阻断账号集合；用户通过既有继续流程显式选择其他账号时，以用户选择为准。
- **FR-012**: 恢复状态缺失或损坏且无法安全推导接续位置时，系统 MUST 明确暂停并报告可恢复错误，MUST NOT 静默从第一个账号开始。
- **FR-013**: 白箱 MUST 明确区分预留、请求开始、请求终态、接力和任务汇总；“预留/分配”不得再冒充实际请求或实际成功。
- **FR-014**: 每次真实请求终态 MUST 记录账号、尝试序号、输入数量、成功数量、失败数量、本地短路数量、未完成数量和安全失败分类。
- **FR-015**: 任务完成或暂停时 MUST 生成按账号汇总；各账号唯一成功详情数之和必须与任务详情抓取成功总数一致。
- **FR-016**: 每个账号的每次真实尝试 MUST 使用唯一证据标识；同一逻辑批次的跨账号接力、浏览器恢复和再次尝试不得覆盖先前产物。
- **FR-017**: 后续成功取得有效 JD 时，系统 MUST 删除所有由该次 JD 失败链路写入的对应待处理记录；尚未解决的 JD 或 AI 失败记录不得误删。
- **FR-018**: 白箱、产物和失败记录 MUST 保持任务关联、时间顺序和敏感信息边界，不记录 Cookie、Token、密码、密钥、完整简历或完整 JD 正文。
- **FR-019**: BOSS 与智联 MUST 采用相同的账号级熔断隔离和 R2 轮询生命周期语义。
- **FR-020**: R1 的既有轮询、撞墙接力和白箱行为 MUST 保持兼容，并增加防止共享账号级可变状态回归的验证。
- **FR-021**: 旧任务记录 MUST 保持只读；V4 不根据不完整旧日志伪造历史账号实际抓取数量。
- **FR-022**: V4 MUST 提供自动化组合回归，覆盖跨分块配额累计、六账号 1048 条分布、账号级熔断隔离、18 成功 + 2 接力、产物唯一、暂停恢复和待处理清理。

## Key Entities

- **R2 轮询状态**：一个详情任务在整个 R2 阶段的连续调度事实，包含冻结账号顺序、各账号每轮配额、当前轮次、当前位置、剩余配额和已阻断账号。
- **账号级熔断状态**：只归属于一个账号的本地保护状态，由该账号自身真实请求产生的源级硬信号推进。
- **预留段**：调度器计划交给账号的一组岗位；在真实请求开始前不代表账号已经抓取。
- **详情尝试**：某账号对一个预留段实际启动的一次请求，具有唯一尝试身份和独立产物。
- **详情终态**：一次尝试的成功、失败、本地短路和未完成数量；用于接力与最终核对。
- **账号工作汇总**：按账号聚合的实际尝试与唯一成功数量，必须与任务详情总数相互核对。
- **R2 恢复断点**：暂停或异常退出时保存的轮询位置和已完成事实；继续任务时用于恢复而不是重置。
- **JD 待处理记录**：岗位因未取得有效 JD 产生的可重试状态；同一岗位后续成功后应清除，其他未解决状态继续保留。

## Success Criteria

- **SC-001**: 六个账号、每账号配额 200、1048 个无失败模拟岗位的完整 R2 任务，实际请求分布精确为 200、200、200、200、200、48。
- **SC-002**: 两个账号、每账号配额 200、每块 20 条的任务中，第 11 块由第二个账号承担；任何内部调用边界都不会把第一个账号恢复为剩余 200。
- **SC-003**: 第一个账号在 20 条中成功 18 条并对 2 条产生硬阻断时，第二个账号实际请求并完成这 2 条；最终成功 20 条且无重复抓取。
- **SC-004**: 任一账号打开本地熔断后，未产生自身阻断信号的其他账号仍能真实启动请求，且不会被误标限流。
- **SC-005**: 任一任务的按账号唯一成功数之和与详情抓取成功总数完全一致；预留、重复重试和本地短路不会抬高成功数。
- **SC-006**: 任一跨账号或浏览器恢复重试场景中，每次尝试均保留独立证据，文件内容和事件数量可逐次核对且无覆盖。
- **SC-007**: 暂停恢复后，已成功岗位重复请求数为 0；成功补回 JD 的岗位对应旧 JD 待处理记录数为 0，未解决记录保留率为 100%。
- **SC-008**: BOSS 与智联的账号克隆隔离测试均证明账号级熔断和其他可变运行状态不共享。
- **SC-009**: 组合回归能够在修复前稳定暴露已核实缺陷，并在修复后通过；不得以只覆盖单次调用的测试替代。
- **SC-010**: 聚焦测试、后端全量测试、前端测试、前端构建、仓库卫生检查和差异检查均通过；真实账号端到端验收必须另行明确记录其输入范围、实际账号请求分布和未验证边界。

## Assumptions

- V4 是对 v2 已确认业务语义的修复，不重新讨论账号池 UI、配额范围、轮询顺序或串行原则。
- 暂停恢复默认延续保存的轮询状态；用户通过既有继续入口明确选择账号时，该选择优先。
- 旧任务缺少完整真实请求证据，因此只保留历史记录，不追溯补造账号归属。
- 本轮不改变平台抓取脚本的反风控策略、页面解析、请求间隔或平台信号定义。
- 本轮不新增数据库业务表；如需保存恢复状态，优先复用既有任务断点或同任务产物边界，具体落点由 V4 Plan 约束。

## Out of Scope

- 绕过、规避或削弱招聘平台风控。
- 多账号并发抓取或以提速为目标的并行调度。
- 修改账号池弹窗设计、配额输入范围、账号添加删除或手动清除限流标记的交互。
- 重写 R1 列表抓取、BOSS/智联页面解析或平台请求脚本。
- 根据旧任务不完整日志重建历史账号成功数量。
- 提交、推送、发布、版本打包或修改正式运行数据库。

## Verification Boundary

- 自动化验证必须使用可控替身和隔离数据证明全部组合行为，不能把简单调度函数测试冒充完整链路。
- 正式真实账号验收必须通过项目对外入口执行，并以实际请求终态和账号汇总为准；仅看到账号切换、预留或页面总数不算通过。
- 未完成真实账号端到端验收前，只能报告“实现及自动化验证完成，真实账号验收待执行”，不得报告 V4 已完全验收。
