# Research: 桌面壳原生窗口控制能力拆分（R0）

**Date**: 2026-09-14

## 现场核查结论

- `packaging/desktop.py` 当前 1019 行，已超项目 800 行红线；其中三项原生窗口控制实现分别位于「窗口句柄定位」「最大化工作区钳制」「无边框尺寸修正」三个函数的连续区段。
- `packaging/window_controls.py` 当前 117 行，只承载窗口原语与一个占位适配位，职责单一且有充足空间。
- 三项实现当前只被桌面入口自身的 `events.shown` 回调使用，没有其它调用方；迁移面清晰。

## D1：迁移方式采用“实现下沉 + 入口保留兼容导入面”

**Decision**: 三项实现整体迁入 `packaging/window_controls.py`，`packaging/desktop.py` 只保留调用与既有私有别名。

**Rationale**:

- 036 v2 要求同一 HWND 只有一条 WndProc 链，且窗口控制模块是唯一所有者；实现必须真正离开超限文件，否则所有权仍然分裂。
- 项目宪法原则 II 要求“拆文件只搬代码、不改行为、保留原入口兼容导出”；保留别名即可保证既有调用面与既有测试不被破坏。

**Alternatives considered**:

- 只做 re-export（实现留在原位）：不解决超限文件继续增长的问题，且所有权仍在桌面入口，违反 036 v2 的阻断前提。
- 新建第三个模块承载原生控制：会把同一 HWND 的消息所有权分散到两个模块，036 v2 明令禁止新增平行模块。

## D2：工作区数据由入口注入，模块不反向依赖

**Decision**: 最大化钳制需要的显示器工作区改为函数参数注入，入口在调用点传入既有工作区提供者。

**Rationale**:

- 原实现直接引用桌面入口中的工作区符号（该符号本身是窗口状态模块的 re-export），迁移后若照搬会形成窗口控制模块 → 桌面入口的反向依赖。
- 依赖注入不改变运行时取到的数据（同一提供者、同一调用时机），因此行为等价。
- 036 v2 的 Plan 要求后续由窗口控制模块自己按当前显示器取工作区；届时只需替换注入实现，调用方向不变。

**Alternatives considered**:

- 窗口控制模块直接 import 窗口状态模块：可接受但不必要，会让状态域渗入原生控制层，也偏离“工作区由调用方决定”的既有接线方式。
- 窗口控制模块自己调用 Win32 枚举显示器：属于 036 v2 的当前显示器工作区能力，本拆分不得提前实现（会改变行为）。

## D3：诊断日志通过延迟 import 桌面日志出口

**Decision**: 窗口控制模块提供 `log_desktop_error()`，内部延迟 import 桌面入口的日志函数；导入失败或调用异常一律静默。

**Rationale**:

- 诊断记录是既有行为（写 `desktop.log`，前缀 `[clamp]`/`[fixsize]`），必须保留，否则真机排障能力下降。
- 迁移函数均工作在 Windows 真机路径，延迟 import 不与模块导入顺序冲突，也不会在非 Windows 环境引入额外依赖。
- 静默兜底与拆分前的写法一致，不新增纯 pass 吞异常（日志函数自身已有兜底）。

**Alternatives considered**:

- 把日志实现一并迁入窗口控制模块：会把入口的错误日志职责拆散，超出本拆分范围。
- 直接 import 桌面入口日志函数：形成反向依赖，违反 FR-005。

## D4：默认尺寸由调用方传入

**Decision**: 尺寸修正函数继续接收目标宽高参数；入口传入既有默认尺寸常量。

**Rationale**: 尺寸口径属于窗口状态域与入口，原生控制模块不应持有窗口尺寸常量；原实现也是由调用点传入。
