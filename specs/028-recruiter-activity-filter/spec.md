# Feature Specification: 第 7 类筛选条件：招聘者活跃时间（028）

**Feature Branch**: `028-recruiter-activity-filter`

**Created**: 2026-08-29

**Status**: Draft

**Input**: User description: "在现有六类筛选条件之外新增第 7 类「招聘者上次活跃」：岗位本身匹配但负责人上次在线已是几个月甚至半年前，投递石沉大海（Boss 常见；智联搜索排序天然压低陈旧岗，现象较轻）。筛的是招聘者（人）上次活跃时间，不是岗位发布时间。对应 BACKLOG B081；需求范围 2026-08-28 边界质询对齐，档位/存量策略/说明生成方等 7 项决策 2026-08-29 grill-me 冻结；Boss 活跃文本值域 2026-08-29 实测收齐（18 详情页 18 成功，7 种文本）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 选中档位后陈年岗位自动归入不匹配 (Priority: P1)

用户在 AI 筛选条件区看到第 7 类「招聘者上次活跃」（单选四档：近一周 / 近一个月 / 近三个月 / 近半年）。选中某一档提交筛选后，凡「招聘者上次活跃距今超过所选档位」的岗位在本次筛选运行中自动归入「不匹配」桶（岗位不出现在匹配结果，也不消失），判定说明写明「负责人上次活跃 X 前，超过要求的 Y」。两平台（Boss / 智联）在同一档位下判定口径一致。

**Why this priority**: 这是本功能的唯一核心价值——陈年岗位不再混进匹配结果浪费投递；没有它功能不成立。

**Independent Test**: 提交一个选中「近一周」档位的筛选运行，构造/准备一个招聘者半年前活跃的岗位，运行后该岗位在不匹配桶且说明可复核；一个招聘者活跃正常的岗位不受影响。

**Acceptance Scenarios**:

1. **Given** 选中「近一周」（7 天），**When** 某岗位招聘者上次活跃距今超过 7 天（如半年前活跃），**Then** 该岗位归入不匹配桶，判定说明包含实际活跃距离与所选档位。
2. **Given** 选中「近三个月」（90 天），**When** 某岗位招聘者上次活跃距今 30 天内，**Then** 该岗位不因第 7 类被拦，正常进入后续判定。
3. **Given** 同一天数事实（如「上次活跃 200 天前」），**When** 分别在 Boss 与智联的运行中选中同一档位，**Then** 两平台判定结果一致（都拦或都不拦）。

---

### User Story 2 - 拿不到活跃数据时不误拦 (Priority: P1)

招聘者活跃数据拿不到的情况——存量已抓岗位没有该字段、详情页没有招聘者名片、名片上没有活跃文本、活跃文本不在已知形态内、解析失败——这些岗位被标注「活跃时间未知」，不因第 7 类被拦截，照常按其余条件判定。

**Why this priority**: 「未知不误拦」是冻结口径里的安全底线；误拦匹配岗位比漏拦陈年岗位伤害大。

**Independent Test**: 准备若干无活跃数据的岗位（存量无字段、无名片、未知文本各一），选中任意档位运行，全部不被第 7 类拦截且带有「活跃时间未知」标注。

**Acceptance Scenarios**:

1. **Given** 存量岗位（升级前抓取、无活跃字段），**When** 选中任意档位运行筛选，**Then** 该岗位不被第 7 类拦截。
2. **Given** 新抓取岗位详情页无招聘者名片或名片无活跃行（实测 18 个中出现 1 个），**When** 判定，**Then** 标注活跃时间未知且不拦截。
3. **Given** 活跃文本不在已知值域映射内（未来平台新增形态），**When** 判定，**Then** 按未知处理不拦截，不误判。

---

### User Story 3 - 活跃数据仅对新抓取生效 (Priority: P2)

升级后新抓取的岗位（列表+详情抓取流程产生）自动携带招聘者活跃数据；存量岗位不做回填重抓、无任何后台补数据动作。用户手动对某岗位执行重抓详情后，该岗位自然带上最新活跃数据。

**Why this priority**: 冻结决策「仅新抓取生效」；回填重抓成本高且有限流风险（B005 因此缓行），缺字段存量本就走「未知不拦」兜底，行为等价。

**Independent Test**: 升级后不触发任何抓取，检查存量岗位数据不变；新跑一次抓取后检查新岗位带活跃数据；手动重抓一个存量岗位详情后其活跃数据出现。

**Acceptance Scenarios**:

1. **Given** 升级完成，**When** 用户不做任何抓取操作，**Then** 存量岗位数据无任何变化（无回填任务、无自动重抓）。
2. **Given** 新执行一次搜索+详情抓取，**When** 检查新抓取的岗位，**Then** 带有招聘者活跃数据（Boss 有活跃文本解析结果 / 智联有时间戳）。
3. **Given** 对一个存量岗位手动重抓详情，**When** 重抓完成，**Then** 该岗位带上活跃数据，后续筛选可正常判定。

---

### User Story 4 - 条件区呈现与默认行为 (Priority: P2)

第 7 类在条件区与现有六类并列呈现：默认不选 = 不限（不出现显式「不限」复选框，与现有六类一致）；同一时刻只能选中一个档位（单选，选新档位自动替换旧档位）；取消已选档位回到不限。选了第 7 类不会减少详情页抓取量（数据在详情页才能拿到），界面上对此不做特殊提示，它就是一个普通筛选条件。

**Why this priority**: 交互完整性；schema 驱动下大部分为自动呈现，单选交互需落实。

**Independent Test**: 打开条件区看到第 7 类四档；点选 A 再点选 B 后仅 B 生效；取消后提交等效于不限；全部六类照旧。

**Acceptance Scenarios**:

1. **Given** 打开 AI 筛选条件区，**When** 查看第 7 类，**Then** 四档（近一周/近一个月/近三个月/近半年）可见且默认全部未选。
2. **Given** 已选中「近一周」，**When** 点选「近三个月」，**Then** 「近一周」自动取消，仅「近三个月」生效。
3. **Given** 不选第 7 类提交筛选，**When** 运行完成，**Then** 结果与未提供该功能时的既有行为一致（任何岗位不因活跃被拦）。

### Edge Cases

- **Boss 下界型文本**：`半年前活跃` 表示上次活跃距今 ≥180 天（实测唯一下界形态）。选「近半年」（180 天）时不拦（180 不严格大于 180），选近一周/近一个月/近三个月时拦。
- **上界型文本跨档位**：`2周内活跃` 表示距今 ≤14 天。选「近一周」（7 天）时无法确定是否超过（可能 3 天也可能 10 天），按保守口径不拦——只有「确定超过」才拦。
- **智联无状态文本**：不活跃岗位列表名片无状态文本，但详情接口时间戳仍有值；判定一律以时间戳为准，文本仅作展示（2026-08-28 浏览器实测核验）。
- **判定时机**：活跃数据在详情抓取后才存在，第 7 类判定发生在 JD 详情抓取之后、AI 精筛判定之前；粗筛（列表阶段）不涉及该维度。详情抓取失败的岗位沿用既有「未抓到 JD 无法精筛」语义，不新增行为。
- **判定说明生成方**：第 7 类命中由确定性规则直接判不匹配，判定说明由后端模板生成；AI 不参与该判定，AI 精筛提示词中不出现第 7 类（六类口径不变）。
- **续跑复用**：第 7 类纳入筛选运行复用的一致性比对——档位变了不再复用旧运行。
- **条件 schema 版本**：新增字段使两平台筛选 schema 版本递增，旧版本冻结条件的续跑请求按既有版本不匹配机制处理（提示重新提交），不做静默兼容。
- **工作区纪律**：实测产生的临时文件在系统临时目录，不进入仓库；`roadmap/` 不随 Git 提交。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在现有六类筛选条件之外提供第 7 类「招聘者上次活跃」，两平台语义统一为一个字段；单选四档：近一周=7 天、近一个月=30 天、近三个月=90 天、近半年=180 天；默认不选=不限。
- **FR-002**: 系统 MUST 在岗位详情抓取时采集招聘者活跃数据：Boss 取详情页招聘者名片的活跃文本（现有抓取流程可看到该文本但解析后即弃，需截获持久化）；智联取详情接口的 `staff.lastOnlineTime` 毫秒时间戳（状态文本仅作展示）；系统 MUST NOT 采集/使用岗位发布时间作为第 7 类依据。
- **FR-003**: 两平台活跃数据 MUST 归一为统一的上层语义（来源平台 + 原始文本 + 活跃距今天数信息），随岗位记录持久化；仅对新抓取生效，MUST NOT 提供存量回填。
- **FR-004**: 选中档位后，系统 MUST 将「招聘者上次活跃距今超过所选档位天数」的岗位判为不匹配（归入不匹配桶，岗位不消失），判定说明 MUST 由确定性规则模板生成，格式含实际活跃距离与所选档位（如「负责人上次活跃 6 个月前，超过要求的近三个月」）。
- **FR-005**: Boss 活跃文本 MUST 按 2026-08-29 实测值域建立「文本 → 活跃距今天数区间」映射表（上界型：在线/刚刚活跃→[0,0]、今日活跃→[0,1]、昨日活跃→[1,2]、N日内活跃→[0,N]、N周内活跃→[0,7N]、N月内活跃→[0,30N]；下界型：半年前活跃→[180,∞]，防御性支持 N月前活跃→[30N,∞)、N年前活跃→[365N,∞)）；仅当区间下界超过所选档位天数才判不匹配；映射表外文本 MUST 按未知处理。
- **FR-006**: 智联 MUST 以 `lastOnlineTime` 时间戳换算活跃距今天数做精确判定（距今 > 档位即不匹配）；状态文本 MUST NOT 作为判定依据。
- **FR-007**: 拿不到活跃数据（无字段/无名片/无活跃行/解析失败/映射外文本）时系统 MUST 标注「活跃时间未知」且 MUST NOT 拦截，照常按其余条件判定。
- **FR-008**: 第 7 类判定 MUST 发生在 JD 详情抓取之后、AI 精筛判定之前，作为确定性规则与六类硬规则同层执行；粗筛阶段 MUST NOT 使用该维度。
- **FR-009**: 第 7 类 MUST 纳入筛选运行续跑复用的一致性比对；两平台筛选条件 schema 版本 MUST 递增。
- **FR-010**: 条件区交互 MUST 为单选（选新档位替换旧档位，可取消回不限）；第 7 类 MUST NOT 进入 AI 精筛提示词；界面 MUST NOT 为该维度添加「详情后生效」类提示（用户拍板静默）。
- **FR-011**: 交付前 MUST 通过宪法验证门禁：相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。

### Key Entities

- **招聘者活跃事实（recruiter activity fact)**: 一个岗位的招聘者上次活跃观测：来源平台、原始文本（Boss）或时间戳（智联）、归一化后的活跃距今天数信息（区间或精确值）、是否可判定；随岗位记录存储，仅新抓取产生。
- **第 7 类筛选条件（recruiter activity filter）**: 用户在筛选运行中选定的档位（四档之一或不选），随运行冻结；运行内判定口径的唯一依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一天数事实在同一档位下，Boss 与智联判定结果一致（同拦/同不拦），由测试用例证明覆盖全部四档。
- **SC-002**: 拿不到活跃数据的岗位（无字段、无名片、无活跃行、映射外文本）在第 7 类任何档位下被拦截数为 0，且均带「活跃时间未知」标注。
- **SC-003**: 所有因第 7 类判为不匹配的岗位，其判定说明均含实际活跃距离与所选档位，人工可复核。
- **SC-004**: 升级后存量岗位在未做任何抓取操作时数据零变化；新抓取岗位带活跃数据；实测值域（2026-08-29，7 种文本 + 无活跃行 1 例）全部落进映射表或未知兜底。

## Verification Scope *(mandatory)*

- 功能交付（本 Spec 主体）：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查（宪法原则 V 全门禁，不豁免）。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。

## Assumptions

- 档位天数按自然日计：近一周=7、近一个月=30、近三个月=90、近半年=180；「距今超过」为严格大于。
- Boss 值域映射表以 2026-08-29 实测（18 详情页，7 种文本 + 无活跃行 1 例）为依据；`昨日活跃` 未在本次实测出现但属已知形态，按既有测试夹具纳入；映射表外形态一律未知兜底，后续遇到新形态再扩表。
- 智联活跃状态文本值域（当前在线/刚刚活跃/今日活跃/昨日活跃/3日内/5日内/7日内活跃及回复类文本）已于 2026-08-28 核验，仅作展示。
- 第 7 类不参与 B071「平台侧前置」——平台搜索不支持按招聘者活跃过滤，该维度永远本地执行。
- 版本语义：新功能且向后兼容，按 minor 提升版本号并生成 CHANGELOG 条目（收口阶段执行）。
