# Feature Specification: 跨平台岗位去重（BOSS+智联）（019）

**Feature Branch**: `019-cross-platform-job-dedup`

**Created**: 2026-08-23

**Status**: Draft

**Input**: 需求经 grill-me 边界质询冻结。用户描述："岗位去重（跨平台）"。质询确认范围 = 跨平台重复（BACKLOG B049）；指纹口径与薪资/发布时间容忍度两问用户未应答，按推荐项代定并在 Assumptions 中声明，可事后翻案。冻结核：同一批关键词和城市先后在 BOSS、智联跑筛选时，两个平台上发布的同一个岗位在结果里只出现一条、只被 AI 筛一次；判定用确定性归一化指纹（公司+标题+城市），不用 AI、不用模糊相似度；宁可漏判（仍显示两条）不可误合（两个不同岗位被并成一条）。

**架构前提**（调查确认，见 plan.md research）：抓取任务、AI 筛选任务、历史轮全部按平台各跑一条（轮次身份 = 抓取任务 + 平台）；两平台结果只在前端合并视图汇合，后端从未跨平台合并。因此跨平台重复出现在「后跑平台 与 先跑平台已完成轮」之间，去重生效点是后跑平台筛选任务的岗位输入组装处。

**基准决策**（2026-08-23 与用户确认）：比对基准为**对端平台近 30 天内全部可见轮的非剔除岗位**，而非仅最新一轮——用户实际使用是两平台交替各跑，历史轮多，岗位可能只出现在对端较早轮次；仅比最新轮会漏掉大量已筛岗位。显示层无回归：只存在于对端旧轮的岗位本来就不在当前合并视图里，后跑平台将其剔除不改变任何可见性。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 后跑平台的重复岗位不再进 AI 筛选 (Priority: P1)

我用同样的关键词和城市先跑了 BOSS 的一键筛选，再跑智联的一键筛选。同一家公司把同一个岗位在两个平台都发了（公司、标题、城市写法略有差异，如「北京字节跳动科技有限公司/字节跳动」「Python开发/python 开发」）。智联筛选开始时，与 **BOSS 近 30 天内所有可见轮**（包括被更新轮顶替的历史轮、仅抓取轮）已保留岗位判定为同一岗位的条目，不再进入 AI 粗筛/精筛、不再抓 JD——AI 额度与抓取时间不被重复岗位浪费。

**Why this priority**: 核心价值（额度与时间）+ 去重主路径；其余故事是它的展示、追溯与一致性保障。

**Independent Test**: 先落多轮 BOSS 结果（岗位 X 只出现在较早轮），再以含岗位 X 的智联岗位列表发起筛选，断言：X 被剔除、剔除原因标注跨平台并指向最近包含它的 BOSS 轮、AI 筛选调用清单不含 X、JD 抓取清单不含 X。

**Acceptance Scenarios**:

1. **Given** BOSS 已有可见完成轮含岗位（公司「北京字节跳动科技有限公司」、标题「Python开发」、城市「北京·朝阳区」），**When** 智联筛选的输入含等价岗位（公司「字节跳动」、标题「python 开发」、城市「北京」），**Then** 该岗位被剔除出筛选输入，剔除记录落在智联轮中，原因明确为跨平台重复。
2. **Given** 岗位 X 只存在于 BOSS 较早的可见轮（最新轮不含 X），**When** 智联筛选输入含 X 的等价岗位，**Then** X 同样被剔除，剔除记录指向最近一个包含它的 BOSS 轮（额度不因轮次更替而漏省）。
3. **Given** 包含 X 的 BOSS 轮定稿时间已超过 30 天，**When** 智联筛选开始，**Then** 该轮不参与比对（X 照常进入筛选，防止拿重新招聘的旧同名岗位误剔）。
4. **Given** BOSS 完成轮含「Python开发」，**When** 智联输入岗位标题为「Python开发工程师」（其余一致），**Then** 不剔除（标题仅做字符级归一，不做同义词/后缀词归并，漏判可接受）。
5. **Given** 两岗位公司、城市一致但标题不同（「销售专员」vs「销售经理」），**When** 智联筛选开始，**Then** 不剔除（不得误合）。
6. **Given** 两岗位标题、公司一致但城市不同（北京 vs 上海），**When** 智联筛选开始，**Then** 不剔除。
7. **Given** 同一平台内部重复（同平台岗位 ID 去重属现状逻辑），**When** 筛选开始，**Then** 现状语义完全不变（指纹合并只在跨平台之间生效）。
8. **Given** 对端平台没有任何可见轮，**When** 智联筛选开始，**Then** 不做跨平台剔除，行为与现状一致。

### User Story 2 - 重复岗位成组展示，来源可见可核对 (Priority: P1)

去重生效后，两平台合并的结果视图里该岗位只出现一行（先跑平台那条带判定）；列表行带「双平台在招」徽标；点开详情能看到**组内两个平台的副本并排**——各自的平台、薪资、岗位链接摆在一起，可核对为什么判定为同一条、也能对比两平台薪资差异。后跑平台那条的剔除台账（原因 + 双方链接）保留在剔除列表中可追溯。

**Why this priority**: 成组展示是去重可见性的主载体——被去重的岗位不再藏在剔除列表角落，而是挂在主条目身上；用户对「为什么少了一条」当场可核对。经用户确认（2026-08-23），这是去重功能不可拆的信任基础。

**Independent Test**: 智联轮含一条跨平台剔除记录，前端合并两平台最新结果后断言：该岗位在列表只有一行且带徽标；详情面板成组区展示两个副本（平台/薪资/链接）；对端保留条目不在当前合并结果中时（其轮已被顶替），退化为剔除台账条目可见，不报错。

**Acceptance Scenarios**:

1. **Given** 智联岗位 X 被判定为跨平台重复并剔除，**When** 智联轮落库，**Then** 剔除行带有对端（BOSS）保留条目的平台、岗位 ID、原始链接与对端轮信息（最近一个包含 X 的轮次及其定稿时间），原因文本含「跨平台重复」与对端平台名。
2. **Given** 前端合并视图拉取两平台最新结果，**When** 渲染，**Then** 岗位 X 在结果岗位列表中只出现一行（BOSS 保留条目）且带「双平台在招」徽标；详情面板成组区并排展示两个平台的副本（各自平台名、薪资、链接）。
3. **Given** 对端保留条目不在当前合并结果中（其轮次已被更新轮顶替），**When** 渲染，**Then** 不成组也不报错：智联剔除台账中 X 条目照常可见（含对端轮时间与链接，可到历史抽屉追溯）。
4. **Given** 对端平台单看（平台分段切到 BOSS），**When** 查看 X，**Then** 正常展示 BOSS 判定（不因去重回改已完成轮次的任何数据）。
5. **Given** 两平台薪资/发布时间写法不同，**When** 判定与剔除，**Then** 差异不参与判定、不报错；成组区如实展示各自写法（不合并薪资）。

### User Story 3 - 中断续跑后口径一致 (Priority: P2)

智联筛选中途暂停/失败后我点继续，或筛选中服务重启后恢复：跨平台剔除确定性重放——被剔除的岗位不复活、不被重复计数，也不因剔除链路产生 018 修复过的终态不一致（幽灵轮、计数对不上）。

**Why this priority**: 筛选任务的输入组装点同时是续跑/重启的重建点，若剔除不落判定或不进计数，续跑与终态校验链会自相矛盾。

**Independent Test**: 构造含跨平台剔除的智联筛选中途暂停后续跑，断言续跑输入仍不含已剔除岗位、最终轮计数（抓取/保留/剔除）一致、终态正常；再构造重启恢复（从抓取快照重建输入）同样断言。

**Acceptance Scenarios**:

1. **Given** 智联筛选首轮已剔除 X 并落判定，**When** 续跑，**Then** X 不复活、不再进入 AI 调用，最终轮里 X 仍为剔除行且原因不变。
2. **Given** 服务重启后从抓取快照重建筛选输入，**When** 重建后继续筛选，**Then** 跨平台剔除按同一规则重新应用，结果与首轮一致（对端轮未变时）。
3. **Given** 一轮筛选含 N 条跨平台剔除，**When** 收尾终态校验与历史轮写入，**Then** 计数自洽（剔除计入剔除数），不触发终态校验失败。

### User Story 4 - 去重判定不跨画像串台 (Priority: P2)

我先给画像 A 跑完 BOSS 筛选，再给画像 B 跑智联筛选：画像 B 的智联岗位不因画像 A 的 BOSS 轮被剔除——跨平台剔除只发生在同一画像摘要的前后两轮之间；没有画像摘要（空）时不做该过滤。

**Why this priority**: 剔除依赖对端轮的判定归属，跨画像串台会让用户发现「画像 B 的结果莫名少了岗位」且无从解释；用画像摘要一致性守住判定归属。

**Independent Test**: 构造对端轮画像摘要与当前任务不同（双非空），断言不做跨平台剔除；构造任一侧摘要为空，断言不因画像过滤而阻断去重。

**Acceptance Scenarios**:

1. **Given** 对端平台任一参与轮（30 天内可见轮）的画像摘要非空且与当前任务画像摘要不同，**When** 组装去重源，**Then** 该轮不参与（逐轮判断；画像不符的轮被跳过，画像相符的轮照常参与）。
2. **Given** 对端轮或当前任务画像摘要为空，**When** 组装去重源，**Then** 该轮不过滤，照常参与去重。

### User Story 5 - 去重过程可见、数字可对账、有退路 (Priority: P1)

去重是后台判定，用户看不到指纹计算——所以它的每一步都要留下用户可见的痕迹（用户明确要求，2026-08-23）：筛选开始时进度消息报出「本批 N 条中 M 条跨平台重复，跳过 AI 筛选」；完成文案与结果统计把数字拆开（抓取 X → 跨平台重复 M → 实际筛选 X−M），任何少岗都能对上账；每次去重判定写入任务事件台账（剔了哪些、各自指向对端哪条）供排查；设置里有「跨平台去重」开关（默认开），怀疑误剔时可关闭恢复旧行为，续跑沿用提交时的开关状态。

**Why this priority**: 静默的后台剔除一旦有 bug 就是「错误漏岗且结果页看不出来」的最坏故障模式；可见性与退路是用户信任此功能的前提，与去重本身同级。

**Independent Test**: 构造含 M 条跨平台重复的筛选，断言：进度事件含去重数量文案；完成文案含三个数字且 X−M 与实际进入 AI 的条数一致；任务事件流含去重台账（岗位与对端指向）；带「关闭去重」提交时无剔除发生、行为与现状一致；关闭状态续跑后仍不剔除。

**Acceptance Scenarios**:

1. **Given** 筛选输入含 M 条跨平台重复，**When** 筛选开始，**Then** 进度消息明确报出「N 条中 M 条跨平台重复，跳过 AI 筛选」（M=0 时不额外打扰）。
2. **Given** 筛选完成，**When** 查看完成文案与结果统计，**Then** 抓取数、跨平台重复数、实际筛选数三个数字可对账（抓取 − 跨平台重复 = 实际进入筛选）。
3. **Given** 一次筛选剔除了若干跨平台重复，**When** 查看任务事件，**Then** 存在去重台账事件，列出被剔岗位与各自的对端指向。
4. **Given** 用户关闭「跨平台去重」开关提交筛选，**When** 筛选执行，**Then** 不发生跨平台剔除（行为与现状一致），成组展示与台账自然为空；续跑沿用关闭状态。

### Edge Cases

- 对端平台 30 天内可见轮的全部岗位均为剔除行（无可剔除对照）→ 视为无可对照岗位，不剔除（防止岗位在两平台都消失）。
- 对端轮里被剔除的岗位（含规则剔除、AI 不匹配外的 dropped 行）不得作为「已保留」判定源；非剔除行（match/not_match/待确认/未筛选）均可作为判定源。
- 同一岗位出现在对端多轮 → 追溯目标取**最近一个包含它的轮次**；多轮均为判定源时指纹索引取首个命中，追溯信息以最近轮为准。
- 对端轮是「仅抓取未筛选」（scraped_only）轮 → 其岗位可作为判定源（岗位身份与是否筛选无关；该岗位由对端轮可见，不会消失）。
- 对端轮定稿时间超过 30 天 → 整轮不参与比对（时间窗兜底，防拿重新招聘的旧同名岗位误剔）。
- 当前平台岗位的标题、公司、城市任一归一化后为空 → 该岗位不参与跨平台判定（保持原样进入筛选）。
- 城市/地点写法差异（「北京·朝阳区」「北京市」「北京-朝阳」）→ 统一取市级（北京）后比较；双方都取不出市级 → 不判定为重复。
- 公司名差异仅在括号注释、组织后缀（有限公司/股份有限公司/有限责任公司/责任公司/集团等）、城市名前缀 → 归一化剥离后相等视为同一公司；剥离后不相等不合并（不做互含、不做相似度）。
- 全半角、大小写、空白差异 → 归一化消除后比较。
- 重抓/补筛回写不触发跨平台判定（回写目标是既有轮，不重走输入组装）；记为边界。
- 功能上线前的旧轮次不做回溯处理：旧轮次间已有的跨平台重复照旧显示；新流程从上线后首轮起生效。
- 两平台筛选并发不存在（现有浏览器互斥保证同一时刻只有一条流水线任务），「先跑平台」由轮次时间自然定序。
- 成组展示依赖「对端保留条目在当前合并结果中」；对端条目随其轮次被顶替而不可见时，组自动退化为剔除台账条目（数据仍在，不报错、不留半截 UI）。
- 关闭去重开关的轮次：不剔除、不成组、无台账；此前已剔除的轮次数据不受开关影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 后跑平台筛选任务的岗位输入组装处 MUST 将与「对端平台判定源」指纹相同的岗位判定为跨平台重复并剔除出筛选输入（不进入粗筛、精筛、JD 抓取）。
- **FR-002**: 指纹与归一化 MUST 为确定性纯函数：全半角统一、去空白、大小写统一；标题仅做字符级归一；公司剥括号注释、组织后缀与城市名前缀；城市取市级；三元组任一为空即无指纹（不参与判定）。不使用 AI 判定、不使用相似度阈值。
- **FR-003**: 对端平台判定源 MUST 为「对端平台近 30 天内全部可见轮（完成/部分完成/仅抓取）中的非剔除岗位」，逐轮参与以下过滤：轮画像摘要与当前任务一致（双非空时比较，任一为空不过滤）、轮全部岗位均为剔除行则该轮跳过；剔除记录的追溯目标 MUST 为最近一个包含该岗位的对端轮。
- **FR-004**: 跨平台剔除 MUST 以当前平台轮次的剔除记录落库：原因文本含「跨平台重复」与对端平台名，extra 携带对端保留条目的平台、岗位 ID、原始链接与对端轮信息（轮次定稿时间）。
- **FR-005**: 跨平台剔除 MUST 走既有判定落库与断点链路（计入剔除计数、被 checkpoint 覆盖），续跑/重启后确定性重放，不复活、不重复计数、不触发终态校验失败。
- **FR-006**: 已完成轮次（先跑平台）MUST NOT 因去重被回改任何数据（判定、extra、计数均不动）；成组展示与徽标仅在前端合并视图按剔除记录动态映射。
- **FR-007**: 指纹判定 MUST 只在跨平台之间生效；同平台流程（run 内合并、抓取快照落库、收藏/反馈身份）现状语义完全不变。
- **FR-008**: 计数口径 MUST 保持可对账：抓取计数含全部抓到的岗位（含跨平台重复），剔除计数含跨平台剔除数；完成文案与结果统计中「抓取 / 跨平台重复 / 实际筛选」三个数字可相互对上；合并视图对两平台计数求和的现有口径不变。
- **FR-009**: 跨平台剔除的岗位 MUST 在对端平台判定源轮次中可见（判定源本就是可见轮的非剔除岗位），保证任何岗位不会在两平台视图中同时消失。
- **FR-010**: 跨平台重复簇在前端合并视图 MUST 成组展示：列表一行（保留条目 + 「双平台在招」徽标），详情面板并排展示组内各平台副本（平台名、薪资、岗位链接，如实展示各自写法）；对端保留条目不在当前合并结果中时 MUST 优雅退化（不成组、不报错，剔除台账条目仍可见）。
- **FR-011**: 去重发生时筛选进度 MUST 报数（「N 条中 M 条跨平台重复，跳过 AI 筛选」；M=0 不打扰）；每次筛选的去重判定 MUST 写入任务事件台账（被剔岗位清单及各自对端指向），任务详情可查。
- **FR-012**: 「跨平台去重」MUST 支持开关（默认开）：提交筛选时可关闭；关闭时不剔除、行为与现状完全一致；开关状态随执行参数冻结，续跑/重启沿用提交时的取值。

### Key Entities *(include if feature involves data)*

- **岗位指纹（Job Fingerprint）**: 归一化公司 + 归一化标题 + 归一化城市三元组；仅在跨平台判定时使用的临时身份，不落库、不建全局表。
- **跨平台剔除记录（Cross-Platform Drop Record）**: 后跑平台轮次的剔除行——原因「跨平台重复：已在 <对端平台> 保留」，extra 含对端条目身份（platform/platform_job_id/source_url）与对端轮信息（最近包含轮定稿时间）。
- **跨平台重复簇（Cross-Platform Cluster）**: 前端合并视图运行时构建——由剔除记录的 extra 反查保留条目，把两平台副本挂到同一组；列表一行 + 详情并排展示（平台/薪资/链接）；不落库、不回写。
- **去重台账事件（Dedupe Ledger Event）**: 任务事件流中的一条记录——本次筛选剔除了哪些岗位、各自指向对端哪条（岗位 ID 与链接）；用于事后审计排查。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一岗位两平台各一轮、后跑平台发起筛选时，AI 筛选调用数与 JD 抓取数均不含该岗位；合并结果视图的岗位列表中该岗位只出现一行。
- **SC-002**: 岗位只出现在对端历史轮（非最新轮）时同样被剔除且额度不被重复消耗；剔除台账可追溯（原因、对端平台、对端岗位链接、最近包含轮）；重复簇在合并视图成组展示（一行 + 详情两平台副本并排）。
- **SC-003**: 含跨平台剔除的筛选经任意次暂停续跑/重启恢复，最终轮数据与一次性跑完完全一致；无终态校验失败、无幽灵轮。
- **SC-004**: 单平台（仅 BOSS 或仅智联）流程行为与改造前完全一致（现有测试全部保持通过）；关闭去重开关时行为与现状完全一致。
- **SC-005**: 数千岗位、数十历史轮量级下，指纹构建与分桶比对为纯内存操作，对筛选总耗时无可感知影响。
- **SC-006**: 去重数量在筛选进度、完成文案、任务事件三处可见且相互一致（抓取 − 跨平台重复 = 实际筛选）。

## Verification Scope *(mandatory)*

- 功能/重构/拆分交付：验证范围为相关模块聚焦测试、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。

## Assumptions

- **已确认决策（2026-08-23）**：比对基准 = 对端平台近 30 天内全部可见轮的非剔除岗位（而非仅最新一轮）——用户实际使用为两平台交替各跑、历史轮多，仅比最新轮会漏掉只出现在较早轮次的岗位；显示层无回归（只在对端旧轮的岗位本就不在当前合并视图）。30 天窗为代定常量，后续可按反馈调成设置项。
- **代定决策（用户未应答质询，按推荐项执行，可翻案）**：指纹口径取「严格归一化精确匹配」——不做模糊相似度、不做 AI 兜底、不做公司名互含；取舍原则为宁可漏判（重复仍显示两条、无伤害）不可误合（不同岗位被并成一条、丢信息）。
- **代定决策**：薪资与发布时间不参与同一性判定，差异容忍度无限；保留先跑平台条目的字段值，不改动。
- **代定决策**：画像过滤用画像摘要文本一致性（轮次无结构化画像 ID）；逐轮判断，双非空才比较，任一为空不过滤。
- 范围只覆盖一键筛选链路的 AI 筛选输入组装点；「仅抓取」（scraped_only）轮自身不去重（保留原始抓取视图，见 Edge Cases），但可作对端判定源；重抓/补筛回写不去重。
- 不修改数据库表结构；抓取快照表、判定表、轮次表的现有键与写入路径全部不动。
- 收藏/反馈流程的跨平台身份合并维持 specs/002 的排除项不动；跨轮（多次筛选之间**同平台**）去重不在本期（B055 另议，届时可评估升级为持久指纹身份库）。
- 功能不回溯旧数据：上线前已存在的跨平台重复照旧，不做迁移。
