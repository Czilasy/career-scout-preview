# Feature Specification: 未收尾流程的一次提醒与轮次数据整条进出

**Feature Branch**: `043-run-lifecycle-cleanup`

**Created**: 2026-09-15

**Status**: 已冻结（2026-09-15；主体需求经连续边界质询由用户拍板；判断类口径经用户授权由 AI 定案，见 Input 第 8 条；最高权威，禁止扩写/收窄）

**Input**: 用户冻结需求（原话口径，逐条锁定）：

1. **起因（2026-09-15 现场查证）**：桌面版打开时曾出现"未主动启动任何任务、却四页全开、第四页显示智联待筛选 39 个"的流程。根查确认：9/13 一次抓取（AI应用开发、Python后端 / 全国 / 各 1 页，抓到 40 个、去重 39 个）跑完但没留下收尾，9/15 13:42 被启动自愈逻辑补收尾，并当作当前最新轮展示。
2. **提醒一次性**：没做完的流程，下一次打开应用可以弹出来（提醒），但只弹一次——按"应用打开次数"算；弹过一次就永远不再弹，无论用户当时取消、开了新流程、还是什么都没做。多枚未收尾时只认最新一枚，更旧的一律沉默、不接力（用户拍板："不可能让所有人都满意"）。
3. **提醒轻量化**：灵动岛一行文字提醒（说明来历），不弹窗、不加流程。
4. **数据不销毁**：提醒只一次；数据按第 5 条管理，不因"不再提醒"而丢失。
5. **整条进出**：一条流程 = 轮 + 其抓取任务（过程记录、岗位明细、任务日志；流程范围的完整定义见 FR-007），整条进、整条出。轮在（含历史归档）→ 背后数据全留（轨迹查看、补筛有根）；轮被用户删除或被 30 轮上限淘汰 → 整条一起走；无主账本（抓取完成但从未形成轮）按每平台最近 30 条兜底淘汰；任务日志与任务同生共死，不单独定规则。
6. **资产底线**：收藏/感兴趣/投递等用户资产在任何清理路径下 0 损失。
7. **页面秩序**：未筛选轮页面"待筛选"标签放左、"确认筛选条件"按钮放右；文案不变，只作用于该场景。
8. **不做与收窄**：步骤条完成标记（AI 筛选打勾）不修、页面副标题文案不改（用户明示）；不引入按时间（3 个月）自动销毁（用户提议时间线，授权 AI 判断后收窄；理由：先把删除修成名副其实、数量兜底见效，时间维度属另一条独立规则）。涉及授权定案的其他口径：有主数据跟轮走、无主账本按每平台 30 兜底；任务日志与任务同生共死；删除连带清除背后全部数据；存量按同一口径回收（均经用户授权 AI 定案，2026-09-15）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 未收尾流程只提醒一次（Priority: P1）

上一次抓取跑完了、却没走到筛选和收尾——这类"没做完"的流程，在用户下一次打开应用时提醒他一次：灵动岛出一行字说清"这是哪天的、多少岗位"，并把结果接回给他看；从这以后，无论他当时取消了、去跑了新流程、还是压根没理，它都不会再主动出现。同一时刻有多枚没做完的，只认最新那一枚；更旧的永远沉默，绝不接力。

**Why this priority**: P1。本规格的起点就是"幽灵流程"——没启动任务却看到具体流程、还被当成当前最新轮；它直接决定"打开应用的第一印象"是否干净可信。

**Independent Test**: 构造一枚未收尾流程（抓取完成、未筛选）→ 打开应用一次（出现灵动岛来历提醒 + 结果接回）→ 关闭重开（不再提醒、不自动展示该流程）→ 再重开（仍不出现）。

**Acceptance Scenarios**:

1. **Given** 存在一枚从未提醒过的未收尾流程，**When** 打开应用，**Then** 灵动岛出现一行来历说明（时间与岗位数口径），且该流程被接回展示，仅此一次。
2. **Given** 上述提醒已经发生过一次，**When** 再次打开应用（无论此前用户取消过、开过新流程、或什么都未做），**Then** 不再出现任何提醒、也不再自动展示该流程。
3. **Given** 同时存在更旧 A、最新 B 两枚未收尾流程，**When** 打开应用，**Then** 只提醒 B、A 不提醒；此后 B 被处理或消失，**Then** A 仍然不提醒（不接力）。
4. **Given** 一枚未收尾流程已被提醒过，**When** 用户在历史等主动入口打开它，**Then** 可正常查看与处理（提醒只约束"主动弹出"，不约束用户主动查看）。
5. **Given** 用户在提醒那次把该流程接续做完（开始 AI 筛选并收尾），**When** 完成，**Then** 它成为正常轮，本规则不再适用。

---

### User Story 2 - 历史数据整条进出（Priority: P1）

一轮流程从生到死都当作一个整体：轮还在（包括归档的历史），它背后的抓取账本、岗位明细、任务日志全都留着——查看轨迹、补筛都有根；轮被用户删除、或被"每平台 30 轮"规则淘汰，就整条一起走，数据库里不再残留半截。从未形成轮的"无主账本"按每平台最近 30 个兜底，超出的整条清掉。任务日志跟任务同生共死，不再单列规则。

**Why this priority**: P1。库两个月已 228MB，大头正是"从不清理的过程账本与日志"，且现行"删除"名不副实（删轮不清背后的数据），体积只增不减。它同时决定用户删除行为的真实语义与数据安全底线。

**Independent Test**: 构造一条流程（轮 + 抓取任务 + 岗位明细 + 日志）→ 删除该轮 → 核对其过程记录、岗位明细、日志均不再残留；另构造一条"轮仍在"的流程 → 确认其背后数据完整保留、轨迹与补筛可用。

**Acceptance Scenarios**:

1. **Given** 一条流程的轮在历史中（含已归档），**When** 查看轨迹或发起补筛，**Then** 相关数据完整可用，清理不得触及有主数据。
2. **Given** 一条流程的轮被用户手动删除，**When** 删除完成，**Then** 该流程的过程记录、岗位明细、任务日志一并清除，数据库中不再有残留占用。
3. **Given** 某平台结果轮超过数量上限（30），**When** 触发淘汰，**Then** 被淘汰轮及其背后数据整条清除。
4. **Given** 某平台无主账本（抓取完成但从未形成轮）超过 30 个，**When** 触发兜底，**Then** 最旧的无主账本整条清除。
5. **Given** 用户收藏/感兴趣/投递过某些岗位，**When** 任何清理路径发生，**Then** 这些资产与标记不受影响。
6. **Given** 升级前的存库中已有大量旧的无主账本与已删轮的残留明细，**When** 新规则首次生效，**Then** 存量按同一口径回收；用户可见的历史轮不受影响。

---

### User Story 3 - 未筛选轮页面的元素秩序（Priority: P3）

未筛选轮的页面上，"待筛选"标签回到左边（与其它状态下的分类标签同一位置），"确认筛选条件"按钮挪到右边。

**Why this priority**: P3。不影响功能，仅修正与其它页面不一致的左右秩序；文案维持现状。

**Independent Test**: 构造一枚未筛选轮 → 查看结果工具行：标签在左、按钮在右；切到常规结果场景，确认该行布局不受影响。

**Acceptance Scenarios**:

1. **Given** 处于未筛选轮页面，**When** 查看结果工具行，**Then** "待筛选"标签在左、"确认筛选条件"按钮在右。
2. **Given** 处于常规结果场景或历史轮场景，**When** 查看同一区域，**Then** 布局与现状一致，不被本次调整影响。
3. **Given** 未筛选轮页面，**When** 查看页面文案，**Then** 文案保持现状（本次不改动）。

---

### Edge Cases

- 提醒那次用户没有看（应用打开后很快关闭）：仍视为已提醒，之后不再弹。
- 提醒过 ≠ 消失：该流程仍在库里/历史里，用户主动翻历史可看可处理。
- 提醒以当前画像为准；其它画像的未收尾流程不得串台提醒。
- 有结果轮引用的抓取数据永远不得被兜底淘汰（有主不动）；"补筛"需要的源数据必须始终在。
- 清理与"补筛/查看轨迹"并发时，以"有主不清理"为准；清理失败不阻断任务主流程。
- 删除即不可恢复（与现行"删轮保留日志"相比是行为变化点）；用户资产在任何路径下 0 损失。
- 同一次打开期间新产生的未收尾流程不算"下一次打开"，提醒留到下一次打开时判断。
- 未筛选轮被提醒后若用户接续完成，则转为正常轮，"30 轮"淘汰规则照常适用。

## Requirements *(mandatory)*

### Functional Requirements

**提醒（一次性）**：
- **FR-001**: 未收尾流程在其形成后的下一次应用打开时，MUST 最多主动提醒一次。
- **FR-002**: 提醒形态 MUST 为灵动岛一行文字（含来历：时间与岗位数口径），MUST NOT 弹窗或打断流程。
- **FR-003**: 提醒次数 MUST 按应用打开次数派生：弹过一次即永久不再弹，与用户当时行为（取消/开新流程/无操作）无关；"一次"覆盖整件事——灵动岛提醒与结果接回展示同进同停，弹过之后两者都不再出现。
- **FR-004**: 多枚未收尾并存时 MUST 只认最新一枚；更旧者 MUST NOT 提醒；最新者被处理或消失后 MUST NOT 由更旧者接力。
- **FR-005**: 被提醒的流程 MUST 可照常接回与处理；完成后进入正常轮生命周期，提醒规则不再适用。
- **FR-006**: 提醒 MUST NOT 影响数据留存；用户 MUST 能通过主动入口（历史等）查看已提醒过的流程。

**数据整条进出**：
- **FR-007**: 一条流程 MUST 作为整体管理：结果轮 + 其抓取账本 + 由该流程派生的全部过程记录（含每次 AI 筛选与重抓的中间过程档，简称"中间档"） + 岗位明细 + 判定证据 + 任务日志；清理 MUST 覆盖该整体的全部足迹，MUST NOT 只清轮而留下中间过程档。
- **FR-008**: 轮存在（含归档）时，其背后数据 MUST 全量保留（轨迹查看与补筛可用）。
- **FR-009**: 用户删除轮时 MUST 连带清除其背后全部数据（含向来保留的日志），使"删除"名副其实。
- **FR-010**: 轮被数量上限淘汰时 MUST 整条清除（轮 + 背后数据）。
- **FR-011**: 无主账本 MUST 按每平台最近 30 条流程保留，超出者整条清除；被任何未结束任务引用的流程 MUST NOT 淘汰；兜底触发 MUST 覆盖"只抓取、从不筛选"的路径（MUST NOT 只挂在筛选收尾动作上）。
- **FR-012**: 任务日志 MUST 与所属任务同生共死，MUST NOT 单独设定保留规则。
- **FR-013**: 用户资产（收藏/感兴趣/投递）MUST 在任何清理路径下无损。
- **FR-014**: 清理 MUST 为尽力而为，失败 MUST NOT 阻断任务主流程。
- **FR-015**: 存量历史数据 MUST 按同一口径回收，用户可见历史不受影响；批量回收执行前 MUST 先做一致性备份（可回退），回收清单 MUST 随执行落盘可供核对。

**页面秩序**：
- **FR-016**: 未筛选轮页面 MUST 将"待筛选"标签置于左、"确认筛选条件"按钮置于右。
- **FR-017**: 该调整 MUST 只作用于未筛选轮场景；其它场景布局 MUST 不变；文案 MUST 保持不变。

**范围边界**：
- **FR-018**: 本次 MUST NOT 引入按时间自动销毁；体积治理以"整条进出 + 无主 30 兜底"达成。
- **FR-019**: 本次 MUST NOT 修改步骤条完成标记与页面副标题文案。
- **FR-020**: 删除或淘汰一条流程时，若同流程存在未结束的任务（进行中/暂停等），系统 MUST 拒绝删除或先终止该任务，MUST NOT 留下"任务仍在跑、其依赖数据已被清"的断链。
- **FR-021**: 本规格"日志随流程清除"的口径 MUST 显式取代既有规格中"删除保留任务日志"的条款（specs/008、specs/010），并同步相应测试与契约文档。
- **FR-022**: 一条流程的结果定稿后，其更早的中间过程档 MUST 清除、只保留最新一次（判定结论、JD 与判定证据保留在轮内，MUST NOT 受影响）；存在未结束任务时 MUST NOT 执行该清除。

### Key Entities

- **未收尾流程**：抓取已完成、未跑 AI 筛选、未收尾的流程；两种形态——只有过程账本（从未形成轮）、或已保存为"已抓取未筛选"轮。
- **提醒记号**：标识某枚流程已被主动提醒过；绑在该流程身份上、随流程生命周期存续。
- **流程闭包**：轮（含归档状态）+ 其全部派生过程记录（含中间过程档与判定证据）+ 岗位明细 + 任务日志；清理的最小整体单位。
- **无主账本**：没有任何轮引用的抓取任务过程记录。
- **用户资产**：收藏/感兴趣/投递标记及关联岗位；任何清理均不得触及。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一枚未收尾流程最多被主动提醒一次；重复打开应用 100% 不再弹出。
- **SC-002**: 多枚并存时提醒对象 100% 为最新一枚；旧枚 0 接力。
- **SC-003**: 删除或淘汰一条流程后，其岗位明细、过程记录、日志残留为 0。
- **SC-004**: 轮存在时，轨迹查看与补筛所需数据 100% 不受清理影响。
- **SC-005**: 任何清理路径后用户资产损失为 0。
- **SC-006**: 未筛选轮页面元素左右位置与常规页一致（标签左、操作右）。
- **SC-007**: 库体积增长与活跃流程数成比例；回收量与存量核对 MUST 按各表行数实测（删除不会立即缩小文件体积，验收 MUST NOT 只看文件大小）。
- **SC-008**: 定稿流程的中间过程档只保留最新一份；更早重试档残留为 0。

## Verification Scope *(mandatory)*

- 开发、调试和返修阶段只运行聚焦测试、原失败用例和直接受影响的必要相邻回归；禁止每次修改或每个子批次机械运行后端全量。
- 同一用户目标的前置拆分与功能实现视为一条交付链；全部收敛后才运行一次干净的后端全量、前端测试、`npm run build` 和仓库卫生检查。
- 全量失败后保存失败清单，先只重跑失败用例与受影响范围；没有相关改动不得重跑全量。修复并重新收敛后才允许下一次最终全量确认。
- 收口发布任务：默认只做卫生测试、hooks、`git diff --check`、`git status` 和 `scripts/release_check.ps1`（若存在）；不自动要求全量测试。
- 只有用户明确要求"全量/全部测试/完整验证"时，收口任务才执行全量测试。
- 界面类验收 MUST 按模拟用户视角真实操作路径走查（035 教训）；数据清理类验收 MUST 用构造数据核对"删干净/留完整"两侧。

## Assumptions

- 现有启动恢复、灵动岛、历史删除与"每平台 30 轮"淘汰机制均可复用；不新增数据库表（提醒记号的承载方式由 Plan 定）。
- "应用打开次数"以一次启动到加载完成的周期计；同一次打开内刷新不重复计数。
- 未收尾流程的判定沿用现有识别口径（抓取完成 + 未筛选 + 无正式结果轮；或已保存的未筛选轮）。
- 30 沿用现有结果轮口径（每平台），便于统一；调整该数值需用户另行拍板。
- 不引入时间维度销毁；"3 个月"提议记录为后续可选方向，不属本次范围。
- 页面元素对调不改变任何交互语义（标签仍可点、按钮行为不变）。
- 存量回收的执行方式（清单落盘、备份与回退）由 Plan 定；备份沿用既有的一致性快照能力，不直接复用旧事故恢复工具。
