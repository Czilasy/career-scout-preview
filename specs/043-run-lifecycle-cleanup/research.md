# Research: 043 未收尾流程的一次提醒与轮次数据整条进出

**Date**: 2026-09-15 | **Plan**: [plan.md](./plan.md) | **Spec**: [spec.md](./spec.md)

决策输入：冻结规格（用户逐条拍板 + 授权定案）、2026-09-15 正式库现场查证、以及一轮独立子智能体评审（123 次工具调用，覆盖数据模型、删除链路、触发器与存量回收）。

评审核心结论：按 spec 原字面实现会出现"轮删干净、约 6 万余行明细仍留、体积不降"。据此已在规格修订 FR-007 / FR-011 / FR-020 / FR-021 / FR-022 与 SC-007 / SC-008。以下为各决策与理由。

## D1 提醒记号的承载

- **Decision**: 给 `screening_runs` 增加一列 `notice_sent_at TEXT`（迁移 v6，ADD COLUMN，无回填）。
- **Rationale**: 记号与流程同生命周期——轮被删除时记号随之消失，无需额外清理；单列迁移代价最小；判定为常数级查询。
- **Alternatives**: ① 独立小表（需联表与额外清理，无收益）；② 前端本地存储（清缓存/换端即丢，不可靠）。

## D2 "不再提醒"的闸门位置

- **Decision**: 后端 `running_task_api` 的"已完成普通抓取恢复"分支不再返回已提醒过的项；`results_api` 的最新轮响应附带"是否已提醒"标记；前端 `useDiscoveryTasks` 的启动自动恢复判定据此跳过已提醒轮。
- **Rationale**: 提醒属于"启动恢复"行为，闸门必须同时覆盖两条路径——"孤儿任务恢复"与"未筛选轮自动落页"；否则会出现"岛不提醒、页面仍落"的半吊子，违反 FR-003（同进同停）。
- **Alternatives**: 只改前端（后端仍会补收尾/返回，语义不清）；只改后端（前端仍可能自动落页）。

## D3 流程闭包的定义与删除顺序

- **Decision**: 以 `execution_params_json.scrape_task_id` 为唯一持久关联键；闭包 = 轮 ← 根账本 ← 其派生的全部过程记录（AI 筛选 / 重抓，按 `scrape_task_id` 与 `source_run_id` 递归） + 白箱证据（owner_kind ∈ {scrape, screening, recrawl}） + 任务日志与占位 `tasks` 行。删除顺序：白箱 → 日志/占位行 → `screening_runs` 行（6 张从表由外键级联自动清除）。
- **Rationale**: 现场核实 6 张从表均声明 CASCADE 且连接开启 `foreign_keys`；真正的残留是 `whitebox_*` 与 `task_logs`；`screening_results` 中 69,802 行挂在过程记录上，必须随闭包清除。
- **死键提示**: `screen_run_id` 只被读、从不被写，禁止用作关联键。
- **Alternatives**: 沿用"删轮只清 `_HISTORY_TABLES`"（即现状，正是 6 万行残留的成因）。

## D4 "有主 / 无主"判定与兜底触发

- **Decision**: "有主" = 根账本被任何 `result_snapshot` 引用（判定不带可见性/状态过滤）；被未结束任务（queued/running/paused）引用的流程一律不淘汰；兜底（每平台最近 30 条流程）补足三处触发：轮保存成功后、抓取收尾后、应用启动早期。
- **Rationale**: 现有裁剪只在筛选收尾触发，"只抓取、从不筛选"的用户永远轮不到清理——而这恰好是无主账本的产生者；判定谓词若照抄可见性口径（EXISTS 结果行、未归档），会出现"轮在但不可见 → 账本被误删"，违反 FR-008。
- **Alternatives**: 沿用现有触发点（存在缺口）；把"有主"判定挂在可见集上（危险，误删）。

## D5 定稿中间档清理（FR-022，用户拍板 A）

- **Decision**: 轮进入定稿（完成/部分完成，且同流程无未结束任务）后，清除该流程更早的筛选/重抓中间档，只保留最新一次；判定结论与 JD 以轮内数据为准；存在未结束任务时不得执行。
- **Rationale**: 8 万结果明细中 69,802 行属于中间档；域内最新一次已满足续跑与排查需要，更早重试档没有保留价值。
- **Alternatives**: 中间档全留（体积大头上不去）；全部清（破坏续跑与排查）。

## D6 删除不释放文件体积

- **Decision**: 默认不引入 VACUUM；验收按各表行数实测（SC-007）。若未来需要回收文件空间，单独评估 VACUUM 的 rowid 变化对既有 `ORDER BY created_at, rowid` "最新"判定的影响。
- **Rationale**: WAL 模式下删行只把页放回 freelist，文件不缩小；VACUUM 会改变无 INTEGER PRIMARY KEY 表的 rowid。
- **Alternatives**: 每次清理后 VACUUM（慢、有副作用）；VACUUM 作为未来独立可选项（保留）。

## D7 存量回收形态（精简定稿：不新增独立工具）

- **Decision**: 存量回收并入**启动兜底**：应用启动早期按同一套清理口径幂等回收（已删轮的孤儿明细、无主账本超 30），执行前自动做一次一致性备份、清理清单落盘留痕；不做独立命令行工具、不做人工确认环节。
- **Rationale**: 用户明确"不要大改、就是几个小东西"——独立 CLI 属于多余工程；启动期无任务运行，天然满足"不与应用内写操作并发"的前提；备份 + 清单落盘已满足"可核对、可回退"。
- **Alternatives**: 独立 CLI 四步流程（被精简掉）；无备份直清（违反 FR-015，弃用）。

## D8 旧条款取代与测试同步

- **Decision**: 在 008 / 010 规格文档中显式标注"删除保留任务日志"条款由 043 取代；同步修改 `tests/test_result_history.py` 中"删除后事件仍保留"的断言。
- **Rationale**: 该条款在三处文档明文存在；不标注则后续复核会以"043 违反 008/010"结案。
- **Alternatives**: 不改旧文档（留下矛盾源）。

## D9 前端页面秩序（US3）

- **Decision**: 只调整未筛选轮页面命令行的元素顺序（"待筛选"标签在左、"确认筛选条件"按钮在右），文案不动；`DiscoveryView.vue` 仅做接线级最小改动。
- **Rationale**: 该文件已超行数红线，按既有先例（spec 010）只允许最小接线；顺序调整与常规页的"分类标签靠左"一致。
- **Alternatives**: 顺带重排该行其它元素或改文案（超出用户明示范围，用户已表态不改）。
