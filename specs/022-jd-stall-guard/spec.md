# Feature Specification: JD 抓取卡死防护与日志查看

**Feature Branch**: `022-jd-stall-guard`

**Created**: 2026-08-24 | **Status**: Draft（第二轮，按冻结需求重写）

**Input**: 用户冻结需求（grill-me 确认，9 条）：
1. 一批 300 秒没动静 = 卡死；2. 卡死自动杀失联抓取工并重抓该批，静默自愈界面无感；3. 总共 3 次（原始 1 + 重试 2），间隔 3~5 秒；4. 3 次失败按原因分流：环境级（浏览器/登录/风控）→ 暂停 + 报错模块接管、处理后点继续；单批偶发 → 跳过该批进待确认、继续下一批、最后统一补抓；5. 范围：JD 抓取段 + 通用防护组件（`webui/pipeline_guard.py`，登记宪法模块地图），不碰门面文件；6. 进度保持按批更新，不改；7. 不补旧日志数据，但卡死/重试/放弃等新事件必须落盘、所有运行模式日志可用；8. 设置页并排新增"日志"按钮 → 黑框浮窗读 career-scout.log、旧到新、实时更新；9. 验收：自动化模拟卡死测试 + 用户真跑一轮端到端。

## User Scenarios & Testing

### User Story 1 - 批次卡死自动恢复，流程自己跑完 (P1)

用户在 AI 筛选 JD 抓取阶段，某一批抓取工失联（任务线程收不到批次结果，界面停在 0/N）。系统在 300 秒无动静后判定卡死，杀掉失联抓取工把任务线程解出来，等 3~5 秒自动重抓该批，全程界面无感、不弹错误，任务继续跑完整个流程。

**为什么是 P1**：这是 12:57 事故的直接场景（抓取工 12:58 已完成工作，任务线程永远收不到）。修好它，"任务自己一路走下去"才成立。

**独立测试**：自动化注入假卡死（抓取工不返回），验证 300 秒后自动重抓并最终完成该批；不依赖真实浏览器。

**验收场景**：

1. **Given** JD 批次开始后无任何产出，**When** 超过 300 秒，**Then** 判定卡死、杀掉失联抓取工、任务线程恢复、自动重抓该批，任务状态保持 running、无错误提示。
2. **Given** 批次在卡死判定前有任何产出（子进程有输出、批返回等），**When** 心跳刷新，**Then** 300 秒计时重置，活批次不被误杀。
3. **Given** 批次重抓成功，**When** 结果正常返回，**Then** 该批 JD 落库、进度按批更新、任务继续下一批直到完成。

### User Story 2 - 3 次重试失败按原因分流收场 (P1)

某一批连续 3 次（原始 1 + 重试 2）都卡死。系统探测环境后分流：环境级（浏览器连不上/登录失效/风控）→ 任务暂停、报错模块给出明确原因、保留断点，用户处理后点"继续"续跑；单批偶发 → 跳过该批、岗位进待确认、继续抓下一批，整轮跑完可统一补抓。

**为什么是 P1**：没有收场就退回"无声悬挂"。分流保证环境问题不浪费后续批次，偶发问题流程不中断。

**独立测试**：注入两类卡死，验证环境级进入暂停+报错、偶发进入跳过+待确认。

**验收场景**：

1. **Given** 某批 3 次卡死且探测为环境级（如 CDP 不可达/登录失效），**When** 第 3 次失败，**Then** 任务暂停、明确提示原因、不关浏览器、断点保留，用户处理后点"继续"从断点续跑。
2. **Given** 某批 3 次卡死但探测为偶发（环境正常），**When** 第 3 次失败，**Then** 该批岗位进待确认、任务继续下一批，最终可对该批单独补抓。

### User Story 3 - 卡死事件日志落盘，所有运行模式可用 (P2)

防护模块每次卡死判定、重试、放弃、分流、兜底，都写入 `~/.career-scout/logs/career-scout.log`（时间、批次、次数、结果）。源码运行与打包 EXE 运行日志都可用。不补写历史数据。

**为什么是 P2**：本次事故全程无日志可查（后端进程日志未生效），是"不报错、无从查证"的直接原因；用户明确要求新事件必须有地方写。

**独立测试**：源码与模拟 EXE 模式下 configure_logging 生效；防护事件行写入日志文件。

**验收场景**：

1. **Given** 防护模块发生卡死/重试/放弃/分流，**When** 事件产生，**Then** 对应事件行写入 career-scout.log（含时间、批次、尝试次数、结果）。
2. **Given** 任意运行模式启动后端，**When** 诊断产生，**Then** 日志文件可写、可读。

### User Story 4 - 设置页"日志"入口，黑框浮窗实时查看 (P2)

用户在设置页看到与"AI 设置""浏览器账号"并排的"日志"按钮。点击弹出有样式的黑框浮窗，从旧到新展示 career-scout.log，默认定位最新，**实时更新**（有新增自动出现），上滑可加载更早的日志。

**为什么是 P2**：让"卡死/重试/放弃"对用户可见可回溯；实时更新保证任务运行中能看到最新进展。

**独立测试**：日志 API 测试 + 前端组件测试；手动验证任务运行中浮窗自动刷新。

**验收场景**：

1. **Given** 设置页存在，**When** 用户点击"日志"，**Then** 弹出黑框浮窗，展示 career-scout.log 旧到新的内容，默认定位最新。
2. **Given** 浮窗打开且日志有新写入，**When** 新日志落盘，**Then** 数秒内自动出现在浮窗（轮询）。
3. **Given** 用户上滑翻旧日志，**When** 到达已加载顶端，**Then** 自动加载更早的分页内容；翻旧时暂停自动跟随，点"回到底部"恢复。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 在 JD 批次 300 秒无任何产出时判定该批卡死（配置可调，默认 300）。
- **FR-002**: 批次进行中任何产出 MUST 刷新心跳、重置 300 秒计时（产出信号：子进程 stdout 输出 / 批次结果返回）。
- **FR-003**: 卡死判定 MUST 由独立于任务线程的监控完成（任务线程失联时监控仍生效）。
- **FR-004**: 判定卡死后 MUST 杀掉失联抓取工（释放任务线程的等待），随后等 3~5 秒自动重抓该批。
- **FR-005**: 每批重试上限 MUST 为 3 次（原始 1 + 重试 2）；批次内重抓不按条去重（接受重复抓取，见 Assumptions）。
- **FR-006**: 第 3 次失败后 MUST 探测环境（CDP 可达性 / 登录态，复用现有 preflight/check_login_state 机制）并按结果分流：环境级 → 暂停 + 报错模块明确原因 + 断点保留可续跑；偶发 → 该批岗位进待确认 + 继续下一批。
- **FR-007**: 若杀进程后任务线程仍不解出（极端死锁），MUST 将任务标记 paused + 明确提示（"任务线程失去响应，请重启应用后继续"），保证不无声悬挂。
- **FR-008**: 防护模块 MUST 将卡死/重试/放弃/分流/兜底事件写入 career-scout.log；所有运行模式（源码/EXE）日志可用。
- **FR-009**: 后端 MUST 提供日志读取 API（读 career-scout.log 尾部/分页/轮询偏移），受本地会话令牌保护；日志轮转后读取端 MUST 能切换回新文件，保证实时更新不失效。
- **FR-010**: 前端设置页 MUST 新增"日志"入口（与 AI 设置/浏览器账号并排），点击弹出黑框浮窗，旧到新展示、默认定位最新、2 秒轮询实时刷新、上滑分页加载更早、翻旧时暂停跟随 + "回到底部"。
- **FR-011**: 新增组件 MUST 登记进 constitution 模块地图；门面文件（app.py/store.py/source.py/boss_cdp_raw.py）不追加逻辑（app.py 仅允许注册 log_api 一行）。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 自动化模拟卡死测试通过：注入卡死批次 → 自动重抓 → 批次完成，无无声悬挂。
- **SC-002**: 分流测试通过：环境级 → 暂停+报错；偶发 → 跳过+待确认。
- **SC-003**: 用户真跑一轮端到端 AI 筛选（含 JD 抓取 100+ 条），流程完整跑完（粗筛→JD→精筛→结果），无 0/N 停滞超过 300 秒。
- **SC-004**: 日志浮窗打开时，任务运行期间新增日志数秒内自动出现（实时更新生效）。
- **SC-005**: 卡死/重试/放弃事件在 career-scout.log 中可查（源码与 EXE 模式均验证）。

## Verification Scope

- 功能交付：聚焦测试（防护模块、日志 API、日志浮窗组件）、后端全量测试、前端测试、`npm run build`、仓库卫生检查。
- 用户端到端真跑验证（SC-003）在交付后进行。
- 不涉及版本提升/打包/发布。

## Assumptions

- 批次卡死以"300 秒无任何产出"判定；慢批次可能被误判，重抓可恢复、代价是一次重复抓取（可接受，用户已确认 300 秒余量）。
- 批次内重抓不按条去重：已成功的岗位会被重抓，浪费少量时间但结果正确（不做去重，避免过度设计）。
- 环境级判定复用现有 SYSTEMIC_BLOCK_CODES 语义与 preflight/check_login_state 探测，不新建错误码体系。
- 待确认/补抓复用现有 screening pending + recrawl 机制，不新建补抓流程。
- 日志浮窗只读当前 career-scout.log，不做轮转备份翻页；ai_raw.log 不进浮窗。
- 防护组件本次只挂 JD 抓取段（按用户确认范围）；组件按通用设计，后续阶段可复用。
- 不补写历史日志数据；仅保证新机制运行后日志落盘。
- 进度保持按批更新，不改（用户确认）。
