4这些通用 Agent 一般分几层功能？
速答一般分四层：底层是模型和工具，中间是任务规划与记忆，上层是执行与调用，最外层是交互入口。核心就是把理解、规划、执行、反馈串成循环。
1 分钟版我理解大体分四层。最底层是模型和工具，负责理解和执行；再往上是规划层，负责拆解任务、决定步骤；然后是执行和记忆层，负责调用工具、保存中间结果；最外层是交互层，接收用户输入和展示结果。这几层串起来就是一个循环：理解需求、规划、执行、看结果、再调整。实际系统里不一定每层都很重，但边界要清楚，方便单独调试。
5有没有构建过多智能体（Multi-Agent）架构？
速答做过比较简单的，比如一个主 Agent 负责理解需求，再分给检索、生成、质检几个子 Agent，各干各的活，最后汇总。复杂调度做得不算深。
1 分钟版做过比较简单的多 Agent：一个主 Agent 负责理解用户需求，然后把任务分给检索、生成、质检几个子 Agent，各干各的，最后汇总结果。我当时主要为了解决一个问题：单个 Agent 又要理解、又要检索、又要写答案，上下文太长容易乱，出错了也不好定位。拆开之后每个 Agent 的职责和 Prompt 更干净，哪个环节出问题可以直接看哪个 Agent 的日志，后面也方便替换和扩展。
6什么是多 Agent？
速答多 Agent 就是让多个有不同职责的智能体协作，比如一个当规划者、一个当执行者、一个当检查者，通过分工和消息传递一起完成任务。
1 分钟版多 Agent 就是多个有不同职责的智能体一起协作完成一个任务，而不是一个模型从头干到尾。比如一个 Agent 当规划者，把大任务拆成步骤；一个 Agent 当执行者，负责检索或调工具；一个 Agent 当检查者，看结果对不对。它们之间通过消息或共享状态传递信息。本质上是把复杂任务拆成多个小任务，每个 Agent 只做自己擅长的一部分，让整体更可控。
7为什么需要多 Agent？
速答因为单个模型做复杂任务容易乱，拆成多个角色后每个 Agent 专注一件事，提示词更清晰、上下文更短，出错也更好定位和重试。
1 分钟版因为单个模型处理复杂任务时，上下文太长、角色太多，容易互相干扰，结果不可控。拆成多 Agent 之后，每个 Agent 只负责一小块，提示词简单、上下文干净，出问题能精确定位，还能单独重试或换模型。另外多 Agent 更符合真实团队的分工逻辑：有人规划、有人执行、有人检查。所以需要多 Agent 的核心原因不是模型不够强，而是任务太复杂时需要分工和约束。
8什么场景下需要多 Agent 架构？
速答任务链条长、涉及多类能力或者需要人审的时候比较适合，比如从需求分析到代码生成到测试，或者资料检索到报告生成，拆开效果更稳。
1 分钟版我的判断是三类场景比较适合。第一，任务链路长，比如从需求分析、代码生成到测试，中间涉及多个步骤；第二，任务需要多种能力，比如既要查资料又要调工具又要生成报告；第三，结果要求高、需要有人检查和返工。反过来，如果只是一个简单问答或单步任务，用多 Agent 反而增加延迟和成本，所以要先判断复杂度再决定要不要拆。
9单个 Agent 其实也可以分配多个职能，为什么还要多 Agent？
速答单个 Agent 职能太多时提示词互相干扰，上下文也容易超限，出问题不好定位。拆开之后每个 Agent 上下文更干净，可以单独调优、单独重试，也更方便扩展。
1 分钟版单 Agent 确实可以承担多个职能，但职能太多时 Prompt 会互相冲突，比如让它既要严谨检索又要自由发挥，它容易摇摆；上下文也会越来越长，费用和延迟都上去了。多 Agent 是把职责拆开，每个 Agent 专注一件事，提示词干净、上下文短、出错定位准。而且拆分之后可以独立升级：检索 Agent 换策略，不影响生成 Agent。代价是系统复杂度变高，所以一般只在中大型任务里用。
10多 Agent 主要是为了解决什么问题？
速答主要解决复杂任务里的上下文混乱、错误难定位、能力难组合的问题，让系统更可控、可扩展。
1 分钟版核心解决三个问题：一是上下文问题，单个 Agent 承载太多信息容易超限和混乱；二是错误定位问题，职责混在一起时不知道错在哪一环；三是能力组合问题，不同任务可能需要不同模型和工具。多 Agent 让系统变成一条流水线，每个环节可单独观察、重试、优化。但它不是银弹，拆不好反而增加延迟和成本，所以要按任务复杂度决定。

14有没有考虑过怎么节约 AI 成本？

2ps 网页版实现方案？

3canvas 无限画布是怎么实现的？
速答无限画布一般不是真的无限，而是用视口加缩放换算坐标，只渲染可视区域内的内容，配合平移缩放矩阵，数据存在一个大的逻辑坐标系里。
1 分钟版无限画布不是真的无限，而是逻辑坐标无限、渲染只画看得见的。做法是维护一个世界坐标，视口有自己的位置和缩放，画布重绘时把视口内的对象按坐标换算后绘制。平移缩放改视口参数，不需要移动所有元素。对象数据还是存在列表或树里，只是渲染时做裁剪。这样就算有几万个节点，也能保证流畅。

5docker 和 k8s 的关系？
速答Docker 负责把应用打包成容器，解决在我机器上能跑的问题；K8s 负责管理这些容器，做部署、扩容、故障恢复和服务发现，两者是打包和编排的关系。
1 分钟版Docker 是打包工具，把应用和依赖装进镜像，跑成容器，解决环境一致问题；K8s 是容器编排平台，管理很多容器，负责部署、扩容、服务发现、故障恢复。两者不是竞争关系，而是上下游：Docker 负责造好箱子，K8s 负责怎么摆放、怎么调度、坏了怎么换。实际项目里我们通常用 Docker 打镜像，推到仓库，再通过 K8s 的部署文件管理运行。
6docker 中容器和镜像的关系？怎么进行挂载的？
速答镜像是只读模板，容器是镜像运行后的实例，可以读写。挂载就是把宿主机的目录或数据卷映射进容器，比如 -v /host:/container，这样容器删了数据还在。
1 分钟版镜像是只读模板，包含代码、运行时和依赖；容器是镜像跑起来后的实例，可读可写。镜像可以有多层，容器运行时的修改只在可写层，删掉容器就没了，所以持久化数据要挂载出来。挂载就是把宿主机的目录或数据卷映射进容器，比如 -v /data:/app/data，这样容器重启或删除后数据还在。数据库这类有状态服务，一定要把数据目录挂到宿主机或云盘。
7k8s 中多个服务怎么进行通讯？
速答一般通过 Service 提供稳定的虚拟 IP 和 DNS 名，Pod 之间用服务名访问；跨服务调用可以走 HTTP/gRPC，服务发现和负载均衡由 K8s 内部完成。
1 分钟版K8s 里 Pod 的 IP 是会变的，所以一般不直接访问 Pod IP，而是通过 Service。Service 提供稳定的虚拟 IP 和 DNS 名，Pod 之间用服务名访问，比如 http://user-service:8080，K8s 内部做负载均衡。跨服务调用走 HTTP 或 gRPC；外部访问通常再包一层 Ingress。理解这个的关键是：服务发现和负载均衡都交给平台，业务代码里只写服务名。

1 分钟版我们的检索链路是：先离线把文档切块、向量化；在线收到问题后，先做查询改写，再向量化，从向量库召回 Top N，同时用关键词检索补充，合并去重后经过重排，把最相关的片段交给模型。之所以加关键词和重排，是因为纯向量检索在专业名词、编号这类场景会漏。检索质量是整个 RAG 效果的核心，模型只是最后一步。
9海豚工作流同步数据时：MySQL IO 爆红怎么排查？场景：三连表、每小时同步、查一个库、插另一个库、插入时报错、IO 爆高

1 分钟版我会按这个顺序查：先看慢查询日志和 show processlist，确认是查询慢还是写入慢；如果是三表联查，explain 看有没有走索引、有没有笛卡尔积；如果是批量插入，看是不是一次插太多、有没有死锁或主键冲突。定位后再改：加索引、拆批次、事务改小、错峰执行。IO 爆红通常是某个 SQL 全表扫或大量回表，先抓到具体 SQL 再优化。
10MySQL 大表优化怎么做？百万级数据后出现慢插入
速答先看慢在哪：索引太多会拖慢插入，可以精简索引；大批量插入拆成小批次，必要时先关掉非必要索引或校验再重建；归档冷数据、分表也能减轻压力。
1 分钟版先定位慢在哪：查询慢还是插入慢。插入慢常见原因：索引太多、每次插入数据太大、锁竞争、表碎片多。我的做法：精简冗余索引，大批量插入拆成小批次或分批提交，必要时先禁用非关键索引再重建；数据按时间归档到历史表，冷热分离；超过一定量再考虑分区或分表。优化前先用 EXPLAIN 和慢查询日志看实际情况，不能上来就分表。

1怎么保证数据库和缓存之间的数据一致性？
速答常用 Cache Aside：先更新数据库，再删缓存；删除失败就靠延迟双删或消息队列补偿。要求高的场景可以订阅 binlog 同步缓存，核心是别让缓存先于数据库更新。
1 分钟版我用的是 Cache Aside：读的时候先查缓存，没有就查库并回填；写的时候先更新数据库，再删缓存。删缓存失败会导致旧数据，所以会加延迟双删或消息队列重试。对一致性要求更高的场景，可以订阅数据库 binlog 同步缓存，或者直接读主库。核心原则是缓存允许短暂不一致，但不能长期不一致；顺序一定是先改库，后动缓存。

9动画有没有做过打开、抖动、浮动、阴影、缩放这类效果？

10WebSocket 前端连接流程是什么？
速答先 new WebSocket(url)，监听 onopen、onmessage、onclose、onerror；连接成功后在 onopen 里发业务消息，收到消息在 onmessage 里处理，断开时根据状态重连。
1 分钟版前端先创建 WebSocket 实例并传 URL，然后监听四个事件：onopen 表示连接成功，onmessage 接收数据，onclose 处理断开，onerror 处理错误。连接成功后发送业务消息，比如登录、订阅；收到消息后解析 JSON 并分发到对应处理函数。还要处理连接状态，防止在未连接时发消息。整体流程就是：建连、监听、发消息、收消息、断线重连。
11WebSocket 怎么监听消息？
速答监听 onmessage 事件，或者用 addEventListener('message')；后端发来的消息一般是 JSON 字符串，前端解析后分发到对应业务处理函数。
1 分钟版主要通过 onmessage 事件，也可以 addEventListener。后端发来的一般是 JSON 字符串，前端 JSON.parse 后根据消息类型分发，比如 type=heartbeat 走心跳逻辑，type=chat 走聊天逻辑。消息处理要统一入口，方便加日志和异常处理。如果消息很大或频率高，还要考虑节流和队列，避免频繁触发渲染。
12WebSocket 怎么和后端约定事件？
速答会定一个消息协议，比如 type、data、id，type 表示事件类型（join、chat、heartbeat 等），data 是内容，id 用于请求响应关联；前后端共用一份文档。
1 分钟版前后端会约定一个消息协议，比如 type、data、requestId。type 是事件名，比如 join、leave、message、heartbeat；data 是业务数据；requestId 用来关联请求和响应。协议定义好后，前后端共用一份文档或类型定义，避免各写各的。心跳、重连、错误这些系统事件也要在协议里统一，业务代码不用关心底层。
13WebSocket 有没有做心跳 / 保活？
速答做了，前端定时发 ping，后端回 pong；超过一定时间没收到 pong 就认为连接异常，主动断开重连，防止代理把空闲连接清掉。
1 分钟版做了。前端定时，比如 30 秒，发 ping，后端回 pong；如果超过一定时间没收到 pong，就认为连接异常，主动关闭并重连。心跳的作用有两个：一是保持连接不被代理或服务器空闲回收；二是尽早发现假连接，很多断开是悄无声息的，不发心跳就发现不了。心跳间隔不能太短，否则浪费资源。
14WebSocket 断开后怎么重连？
速答在 onclose 里启动重连，延迟递增，比如 1 秒、2 秒、4 秒；重连成功后重新订阅或恢复状态，并通知 UI；还会限制最大重试次数避免死循环。
1 分钟版在 onclose 或 onerror 里启动重连，间隔递增：1 秒、2 秒、4 秒、8 秒，最大到 30 秒，用指数退避避免风暴；重连成功后再订阅或恢复状态，并通知 UI。会设置最大重试次数，超过后提示用户手动刷新，避免无限循环。重连期间新消息可以先缓存，恢复后补发。关键是重连要有状态管理，用户能看到正在重连。
15有没有遇到连接不上的情况？
速答遇到过，常见是后端服务没起来、代理限制、网络切换；排查时会先看控制台错误和网络面板，再确认服务端日志和鉴权是否通过。
1 分钟版遇到过。常见原因：后端服务没启动或崩溃、代理不兼容、网络切换、鉴权失败。排查步骤：先看浏览器控制台和 Network，确认 WebSocket 请求状态；再看后端日志有没有连接记录；确认鉴权 token 是否过期。定位后分别处理：服务问题重启、代理问题换协议或配置、token 问题重新登录。我会诚实说踩过这些坑，重点是讲排查思路。
16连接不上时怎么兜底？
速答先显示重连状态，提供手动重试按钮；同时把消息存本地或队列，重连成功后补发；如果 WebSocket 彻底不可用，就降级到轮询。
1 分钟版连接不上时先给用户反馈：显示连接中或网络异常，提供重试按钮；业务上把要发送的消息暂存本地，重连成功后补发；如果 WebSocket 长时间不可用，降级成 HTTP 轮询拉取数据，保证核心功能还能用。兜底的核心是：不能让用户卡死，也不能丢消息。所以状态管理和消息补偿比连接本身更重要。
17是否会降级成 HTTP 轮询？
速答会，作为最后兜底；当 WebSocket 连续重连失败，或者检测到环境不支持时，切换成 HTTP 轮询拉取状态，保证核心功能可用。
1 分钟版会。当 WebSocket 连续重连失败，或环境不支持，比如某些代理拦截，就切换成 HTTP 轮询。实现上会抽一个统一的数据通道接口，上层业务不关心底层是 WebSocket 还是轮询；轮询拉取最近状态和消息，做到功能可用、体验降级。降级是策略不是认输，恢复条件满足后可以再切回 WebSocket。
18轮询频率怎么控制？
速答正常情况低频，比如 5 到 10 秒一次；有任务进行中或检测到异常时调高频率，空闲或失败时降频；用动态间隔而不是固定死，避免浪费请求。
1 分钟版正常情况低频，比如 5 到 10 秒一次；有任务进行中或用户正在看实时数据时提高频率，比如 2 到 3 秒；页面不可见或空闲时降频甚至暂停。频率要动态控制，不能固定死，否则不是浪费请求就是不够实时。还会用条件请求，比如带 lastId，只拉新增数据，减少响应体。轮询是兜底方案，所以成本和实时性要平衡。
19有没有用指数退避？
速答用了，重连间隔按 1 秒、2 秒、4 秒、8 秒递增，最大封顶；轮询失败也会退避，避免服务恢复时所有客户端同时打过来。
1 分钟版用了。重连间隔按 1、2、4、8 秒递增，最大封顶 30 秒，避免所有客户端同时重连造成服务压力；如果重连成功就重置间隔。轮询失败也退避，比如连续失败把间隔拉长，成功后恢复。指数退避的关键是有界：要封顶、要重置、要加随机抖动，防止雪崩。这个细节能体现你确实处理过生产问题。
20弱网情况下怎么提示用户？
速答检测到连接断开或请求超时，会显示轻提示网络不稳定，但不打断操作；状态栏保留重连进度，用户主动刷新也能恢复。
1 分钟版检测到连接断开、请求超时或网络状态变化时，显示轻量提示网络不稳定，但不打断操作；数据加载失败显示重试入口；上传或发送中的任务显示等待状态，避免用户以为成功了。提示要分级：轻微问题不打扰，严重问题才弹窗。核心是让用户知道当前状态，同时提供恢复路径，不能干等着。
21实时数据不准确时，前端怎么做交互提示？
速答会区分加载中、数据延迟、已过期三种状态；延迟时显示时间戳和刷新按钮，过期数据用不同样式标注，不让用户把旧数据当最新。
1 分钟版会区分三种状态：加载中、数据延迟、已过期。加载中显示骨架或进度；延迟显示更新于什么时间和刷新按钮；过期数据用不同样式或角标标注，不能和最新数据混在一起。如果数据差异影响决策，会加警示。核心原则是让用户知道数据的可信度，而不是假装数据永远准确。

23什么是柯里化函数？
速答柯里化是把一个多参数函数拆成一系列单参数函数，比如 f(a,b,c) 变成 f(a)(b)(c)；好处是可以固定部分参数、延迟执行，方便复用。
1 分钟版柯里化是把一个接收多个参数的函数变成接收一个参数、返回接收下一个参数的函数，比如 f(a,b,c) 变成 f(a)(b)(c)。作用是固定参数、延迟执行、方便复用，比如日志函数先固定级别，再传消息。面试问这个一般是想看函数式编程理解，我会讲清楚原理和一个实际例子，再提一句不是所有场景都适合柯里化。
24ES5 和 ES6 构造函数分别怎么写？

36`Object.defineProperty` 和 `Proxy` 有什么区别？
速答defineProperty 只能劫持已有属性，新增属性要额外处理，数组方法也要重写；Proxy 能代理整个对象，支持拦截属性增删、in、遍历等操作，能力更全。
1 分钟版defineProperty 是劫持属性，所以新增属性、删除属性要额外处理，数组方法也要重写；Proxy 是代理对象，增删改查、遍历、in 都能拦截，能力更全。性能上 Proxy 可以懒代理，深层对象用到才代理，比递归一次性劫持更省。兼容性上 defineProperty 支持更老，但新项目不用考虑。理解这两个区别，Vue 2 和 3 的很多差异就通了。
37Vue 3 在性能上做了哪些优化？
速答主要有 Proxy 响应式、编译时静态标记 patchFlag、diff 算法优化、Tree-shaking 减小体积，还有组合式 API 让逻辑复用更清晰。
1 分钟版几个方面：Proxy 响应式更高效，深层按需代理；编译时静态标记 patchFlag，diff 只比较动态部分；静态节点提升，不用反复创建；Tree-shaking 减小打包体积；组合式 API 让逻辑按功能组织，可读性和复用性更好。实际体验是：同样组件，Vue3 渲染和更新更快，包也更小。面试时挑两三个讲透就行，不用全背。
38Vue 2 里数组 / 对象变更为什么可能不触发视图更新？
速答因为 defineProperty 只劫持已有属性，直接新增属性、用索引改数组或改 length 都监听不到；所以要用 Vue.set 或替换数组方法。
1 分钟版因为 Vue2 的 defineProperty 只能监听已有属性：直接给对象新增属性、用索引改数组、修改 length，都不会触发 setter，所以视图不更新。处理：新增属性用 Vue.set 或 this.$set；数组用 splice、push 等重写方法，或直接替换整个数组；对象重新赋值。Vue3 用 Proxy 没有这个问题。这类题要讲原理加解决方案。
39如果数据变了，但是视图没变，可能是什么原因？
速答先看数据是不是响应式的：新增属性没声明、数组索引修改、层级太深被漏掉；再看是否修改了 props 或非响应式对象，最后检查渲染依赖有没有正确收集。
1 分钟版先查数据本身是否响应式：对象新增属性没声明、数组索引修改、层级太深都可能漏；再看是不是直接改了 props 或 Vuex 状态；最后看渲染依赖有没有收集到，比如在方法里用数据而不是模板里。排查顺序：先确认数据确实变了，打印看看；再确认是不是响应式；再确认依赖；最后考虑强制更新。大多数情况是前两类。

6文档、PDF、课件是如何切分、入库、人工审核的？

1 分钟版流程：解析文档，包括 PDF、Word、课件，清洗掉页眉页脚和乱码；按标题和段落语义切块，控制每块长度和重叠；预审检查切分是否合理、内容是否完整；向量化入库；正式发布前抽检。人工审核两道：一道在切分后，一道在入库前，主要防止错误内容进入知识库。切分策略很影响检索效果，所以我通常会对比几种切法。

12假设设计一个秒杀系统，你会怎么设计架构？

1 分钟版设计思路是分层削峰：前端限流、按钮防重；网关按用户和 IP 限流；抢购阶段用 Redis 预扣库存，原子操作防超卖；真正创建订单走消息队列异步落库，数据库只处理最终写入；还要做幂等，比如用户只能抢一次，以及超时兜底。核心是把压力挡在前面、把库存控制在原子操作里、把最终一致性交给异步，而不是让所有请求直接打数据库。
13高并发下如何避免超卖？
速答用原子操作扣库存：Redis 的 DECR 或 Lua 脚本保证判断和扣减一体，数据库用条件更新库存大于 0 或乐观锁；关键是不能先查再改，中间留空隙。
1 分钟版核心是原子扣减。Redis 用 DECR 或 Lua 脚本保证检查库存再减是一步；数据库用条件更新，比如 UPDATE stock SET num=num-1 WHERE id=? AND num>0，影响行数为 0 说明没库存。不能先 SELECT 再 UPDATE，中间并发会超卖。还要配合唯一约束和幂等，防止同一个用户重复下单。方案按量级选：小并发数据库条件更新就够，大并发加 Redis 预扣。
14MySQL 本身怎么实现库存扣减？
速答用单条 UPDATE 条件更新，比如 UPDATE stock SET num=num-1 WHERE id=? AND num>0，受影响行数为 0 就说明没库存，天然避免超卖；事务里配合行锁保证一致。
1 分钟版用条件 UPDATE：UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0。MySQL 行锁保证同一行只有一个事务在改，影响行数 0 就是失败，不会出现负库存。如果扣库存和创建订单要一起成功，就放同一个事务；失败回滚。这个方案简单可靠，缺点是热点行锁竞争，所以并发特别高时用 Redis 预扣。面试时我会先讲数据库方案，再说演进。
15Redis 分布式锁或 Lua 脚本如何使用？
速答锁一般用 SET NX EX 加唯一值，防止误删；扣库存这种多步操作直接用 Lua 脚本原子执行，比如检查库存、减库存、返回结果一次完成。
1 分钟版分布式锁用 SET key value NX EX，value 放唯一标识，释放时用 Lua 比较后删除，防止误删别人的锁；还要设置过期时间防止死锁。扣库存这类多步操作直接用 Lua 脚本原子执行：检查库存、扣减、返回结果，一次完成，避免并发问题。Lua 的优点是原子性和性能，缺点是逻辑多了难维护，所以只放关键操作。
16限流、接口削峰、事务和乐观锁如何落地？
速答限流用令牌桶或固定窗口在网关做；削峰用消息队列把突发请求排队消费；事务保证多表写一致；乐观锁用 version 字段，更新时带上旧版本，冲突就重试。
1 分钟版限流用令牌桶或滑动窗口，在网关或中间件做，超限返回友好提示；削峰用消息队列，请求先入队，服务端按能力消费；事务保证多表写入一致，失败回滚；乐观锁在表里加 version 字段，更新时 WHERE version=旧值，冲突则重试或提示。这些方案组合使用：限流挡外部压力，队列消化峰值，事务和锁保证数据正确。
17如果不用 Redis，只用 MySQL，要怎么保证安全？
速答直接用数据库条件更新和事务，比如 UPDATE 语句里带库存大于 0，配合行锁和唯一约束；把扣减和订单放一个事务里，出错回滚，一样能防超卖，只是并发上限低。
1 分钟版只靠 MySQL 也能保证安全：用条件更新加事务。比如 UPDATE stock SET num=num-1 WHERE id=? AND num>0，行锁保证并发安全；创建订单和扣库存放一个事务，失败整体回滚；再加唯一约束防重复下单。这样并发上限低一点，但数据绝对一致。面试回答的关键是：先理解数据库本身的原子性和锁，再加 Redis 是为了抗更高并发，不是非它不可。
18微信支付接入流程怎么设计？
速答后端先创建订单，调微信下单接口拿 prepay_id，再返回参数给前端拉起支付；支付完成后微信回调后端，后端验签、查单、更新订单状态，再通知业务。
1 分钟版流程：后端先创建本地订单，调微信统一下单接口拿到 prepay_id；后端把签名参数返回给前端；前端调起微信支付；用户支付后微信异步回调后端，后端验签、查单确认金额，再更新订单状态并触发后续业务，比如发积分、发货。关键点：以回调为准但不能只信回调，还要主动查单；回调要幂等；失败要有补偿。前端只是发起和展示结果，状态机在后端。
19如何保证用户支付后积分/虚拟产品到账？
速答以支付回调为准，回调验签通过后更新订单状态，再做幂等处理（订单号唯一）；发积分走事务或消息队列，失败要重试，不能因为重复回调多发一次。
1 分钟版以支付回调为准，验签通过后更新订单状态为已支付；后续发积分、解锁虚拟产品等操作要走事务或队列，并且幂等：用订单号或流水号做唯一键，重复回调、重复消费都不会多发。如果队列失败，要有重试和告警；用户侧可以先显示处理中，最终一致。核心是状态唯一、操作幂等、失败可重试。
20支付为什么要使用异步队列？
速答因为支付成功后要做的动作很多，比如发积分、通知、更新多个系统；同步做容易超时和失败，异步队列可以削峰、重试，还不阻塞用户响应。
1 分钟版因为支付成功后要做的动作很多：更新订单、发积分、通知、可能调用第三方；同步做会拖慢回调响应，而且任何一步失败都要处理。用队列可以削峰、解耦、重试，支付回调只做确认状态、投递消息，后面的动作异步执行。这样即使用户量大，也能稳定处理；失败的任务还能重试和追踪。异步的代价是最终一致，所以要有补偿。
21如果队列挂掉，如何保证支付结果和系统状态一致？
速答订单状态以支付平台回调为准，回调先落库；队列消费前先查订单状态，已经处理过就跳过；队列恢复后重新投递未完成的任务，保证最终一致。
1 分钟版原则是以支付平台为准，本地状态兜底。回调先落库，不能丢；消费前先查订单状态，已处理就跳过，保证幂等；队列恢复后把未完成的任务重新投递。如果队列长期不可用，要有补偿任务扫描已支付但未发货或未加积分的订单，主动重试或告警。核心是消息可能丢，但状态不丢，靠扫描补偿最终一致。

23什么是数据库事务？
速答事务是一组要么全部成功、要么全部回滚的操作，保证 ACID：原子性、一致性、隔离性、持久性；典型场景是转账，扣款和入账必须一起成功。
1 分钟版事务是一组数据库操作，要么全部成功提交，要么全部失败回滚，保证 ACID：原子性、一致性、隔离性、持久性。典型例子：转账，A 扣钱和 B 加钱必须一起成功，中间失败要回滚。事务还能隔离并发，比如两个请求同时改同一行，靠锁避免脏数据。面试时我会用项目例子讲，比如订单、库存、积分一起改，必须放一个事务。
24结合你的项目，举例说明**必须使用事务**的业务场景？
速答比如订单支付成功后，要同时改订单状态、加积分、扣库存，任何一个失败都会数据不一致，所以必须放同一个事务里，失败整体回滚。
1 分钟版比如订单支付成功后，要同时更新订单状态、扣库存、加积分，这三步任何一步失败都会数据不一致：订单付了但库存没扣，或者积分没加。所以放在一个事务里，全部成功才提交，失败整体回滚。还有转账、库存扣减、余额变动这类涉及钱和数量的场景。面试时我会讲这个例子，说明为什么必须事务而不是先试试再补。
25LangChain 不同版本 / 模块的区别？
速答不同版本接口和模块变化比较大，比如旧版用 LLMChain 这类组合链，新版更推荐 LCEL 表达式和 LangGraph 做编排；升级时接口不兼容，需要看迁移文档。
1 分钟版LangChain 迭代快，不同版本差异大：早期是 Chain 组合，比如 LLMChain、SequentialChain；现在推荐 LCEL 表达式，用管道组合；复杂流程用 LangGraph，用节点和边定义状态机。升级时接口不兼容，要按迁移文档改。我的经验：看文档先看版本，网上老教程经常对不上。选型时也要锁定版本，避免隐式升级。
26多智能体中动态路由如何根据条件分配任务分支？
速答路由本质是条件判断：根据意图、内容类型或规则选择下一个 Agent；可以用 LLM 做分类，也可以用结构化规则，把路由结果作为节点跳转条件。
1 分钟版路由就是根据条件决定下一个节点。实现方式：用 LLM 分类意图，把问题分给对应 Agent；或写规则，比如关键词、权限、数据类型；也可以在 LangGraph 里定义条件边，根据路由结果跳转。关键：路由结果要可观测、可回退，比如分类置信度低就进默认分支。动态路由解决的是一个问题该谁处理，而不是所有问题都走同一条链。
27什么是查询改写？作用是什么？
速答查询改写是把用户原问题改得更适合检索，比如补全指代、拆复合问题、转成关键词；作用是提高召回准确率，常见做法是用 LLM 生成多个改写版本再检索。
1 分钟版查询改写是把用户原问题改得更适合检索。比如它的价格是多少改成产品 X 的价格；复合问题拆成多个子查询；口语转成关键词。作用：提高召回准确率，尤其是省略、指代、口语化问题。实现：用 LLM 生成改写版本，或规则处理；改写后可以检索多个版本再合并。注意：改写不能改变用户意图，重要词要保留。
28你们知识库使用什么向量库？
速答用的开源方案，比如 pgvector 或 Milvus；选它是因为跟现有技术栈匹配、部署简单，数据量不是特别大时够用。

29Elasticsearch + 向量库怎么做混合检索？整体流程？
速答ES 做关键词检索，向量库做语义检索，两者结果融合；流程是先把文档同时建索引和向量化，查询时并行召回，再按分数融合、去重、精排，最后交给模型。
1 分钟版流程：离线阶段，文档同时写入 ES 索引和向量库；在线阶段，ES 做关键词检索，向量库做语义检索，两个结果按分数融合，去掉重复，再做重排，最后把 Top N 交给模型。为什么要混合：向量擅长语义相似，关键词擅长精确匹配，比如编号、专业词，互补后召回更全。混合检索的实现复杂度高一些，但效果明显。
30混合检索已经做过分组、排序、去重，为什么还需要再次精排（Re-rank）？
速答因为粗排只解决尽量别漏，分数不准、边界情况多；精排用更强的模型对候选做细粒度相关性打分，把真正相关的排到前面，能明显提升回答质量。
1 分钟版粗排的目的是别漏，所以召回范围大，分数也粗糙；精排是用更强的模型对候选做细粒度打分，把真正相关的排前面。分组、排序、去重解决的是有没有重复、顺序大概对，但解决不了哪个片段对回答最有用。尤其 Top K 直接进 Prompt，前面混一条不相关的，回答就偏了。所以精排是质量最后一道保障。
31项目中有使用领域词典吗？

1 分钟版有用。专业领域比如政策、医疗、法律，很多词通用分词会切错，比如人工智能拆开；词典可以保底：切分时优先保留、查询改写时补充同义词、检索时做精确匹配。实现上可以用自定义词典配合 ES 分词，或向量检索前做词典改写。词典要维护和更新，新词不断出现。面试时讲具体场景，比如政策文件名和编号。
32Vue2 响应式原理，数组方法是如何重写拦截的？
速答Vue2 用 defineProperty 劫持数组的 push、pop、shift、unshift、splice、sort、reverse，重写这些方法，在调用时触发更新；索引修改和 length 修改拦不到。
1 分钟版Vue2 用 defineProperty 劫持属性，但数组的索引和 length 拦不到，所以重写了 push、pop、shift、unshift、splice、sort、reverse 七个方法，调用时触发更新。其他方法比如直接 arr[0]=x、arr.length=0 不会触发。Vue3 用 Proxy 不用重写。面试时我会写一个例子说明，为什么 Vue2 推荐用 splice 而不是索引赋值。
33Vue2 中哪些数组方法无法被原生拦截？如何处理？
速答通过索引直接赋值、修改 length 无法被拦截；处理方式是替换整个数组、用 Vue.set 或 splice，让响应式系统感知变化。
1 分钟版直接按索引赋值 arr[0]=x、修改 length，还有数组新增属性，Vue2 都拦不到。处理：用 splice 替换，或 this.$set(arr, index, value)，或直接重新赋值整个数组。原因是 defineProperty 只劫持已有属性，数组索引和 length 无法预知。Vue3 的 Proxy 没有这个问题。回答时我会给出代码示例和为什么。
34Vue3 Proxy 相比 Vue2 的优势？
速答能拦截整个对象的增删改、属性遍历和 in 操作，数组不用重写方法；懒代理性能更好，深层对象按需代理，代码也更统一。
1 分钟版Proxy 代理整个对象，能拦截增删改查、in、遍历，所以对象新增属性、删除属性、数组索引修改都能响应；不用递归一次性劫持，深层对象按需代理，性能更好；数组也不用重写方法。另外 Proxy 的 API 更统一，代码更简单。代价是兼容性比 defineProperty 差，但现代浏览器没问题。Vue3 的响应式更符合直觉。
35Vue3 中的 WeakMap / 弱引用作用是什么？
速答Vue3 用 WeakMap 存对象到响应式状态的映射，key 是原始对象，value 是代理；弱引用不会阻止对象被回收，避免内存泄漏。
1 分钟版Vue3 用 WeakMap 存储原始对象到响应式代理的映射，key 是原始对象，value 是代理。用 WeakMap 而不是 Map 是因为弱引用：当原始对象不再被使用时，可以被垃圾回收，不会造成内存泄漏。Vue3 还用 WeakMap 做依赖收集，target 到 deps。面试时我会说：WeakMap 的 key 必须是对象，且不阻止回收，适合这种一对一映射场景。
36解释下 Harness 相关概念？
速答Harness 我理解是围绕 AI 的一套约束和执行框架：把目标、步骤、工具、验收标准固定下来，让 AI 按流程干活，而不是自由发挥；核心是可控、可追踪、可验证。
1 分钟版Harness 我理解为 AI 的执行框架和约束系统：把目标、步骤、工具、验收标准定义好，让 AI 按流程工作而不是自由发挥。比如开发任务先拆成规范、计划、任务，每一步有输入输出和验证，AI 完成一步再下一步。核心价值是可控、可追踪、可验证，避免 AI 说完成但没有证据。我理解这和 Agent 的规划执行很像，但 Harness 更强调约束和验收闭环。

18Vue2 和 Vue3 最大的区别是什么？

1 分钟版最大区别是响应式机制和 API 组织：Vue2 用 Object.defineProperty 加 Options API，Vue3 用 Proxy 加 Composition API。响应式让 Vue3 能监听增删改，性能更好；组合式 API 让逻辑按功能复用，不用 mixin。还有 TypeScript 支持、体积和性能优化。面试时我会说：如果只记住一个点，就是 Proxy 加 Composition 带来的能力和组织方式变化。

1 分钟版做过。直接一次性渲染上万条会卡，方案：虚拟列表只渲染可视区域，比如 20 条，滚动时替换；或者分页、懒加载；表格只渲染需要的列，避免大对象；数据去重、防抖。还要配合后端：分页接口、字段裁剪。优化目标不是能渲染，而是首屏快、滚动顺、内存可控。面试时我会讲具体选虚拟列表的原因。
20WebSocket 和 SSE 有什么区别？
速答WebSocket 双向、实时、需要长连接管理；SSE 单向服务端推送、基于 HTTP、自动重连；选型看场景，聊天用 WebSocket，流式输出和通知用 SSE 更省事。
1 分钟版WebSocket 是双向长连接，客户端服务端都能主动发，适合聊天、协作编辑；SSE 是单向服务端推送，基于 HTTP，自动重连，适合进度、通知、流式输出。选型看交互方向：需要客户端频繁发送用 WebSocket；只是服务端推用 SSE，简单稳定。还要考虑代理兼容和连接管理成本。核心是双向还是单向、实时要求多高。

1 分钟版原生小程序可以用全局变量、事件总线、简单 store，自己封装；复杂项目用 mobx-miniprogram 或 Redux 风格库。setData 是把逻辑层数据同步到视图层并触发渲染，性能问题：频繁 setData、大数据量 setData 会导致渲染卡顿，所以要做节流、合并更新、避免传大对象、用局部更新路径。面试时我会说：setData 不是随便用，要控制频率和数据量。
